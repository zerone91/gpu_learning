# 推理服务：一个请求的一生

> **所属模块**：模块 09 · 系统视角（从一张卡到一个集群）
> **状态**：🟨 学习中（第一版。知识截至 2026-08）
> **本节主旨**：前面所有模块讲的都是"**给定一批数据，怎么算得快**"。推理服务面对的是一个性质完全不同的问题：**请求一个一个来、长短不一、随时到达随时结束，而且每个请求都带着自己的延迟要求。** 这一节从一个请求进入系统的那一刻开始跟踪它，把服务层的骨架讲清楚：**KV cache 是怎么把"显存"变成"并发数"这个业务指标的**、**为什么静态批处理会浪费一半以上的算力而连续批处理不会**、**为什么 prefill 和 decode 混在一起会互相伤害、以及业界为此走到了"用两种芯片分别伺候它们"这一步**、**为什么把 GPU 跑到 95% 利用率反而是错的**（这是一道排队论的账，也是本节最反直觉的一段）。最后把 TTFT、TPOT、吞吐、goodput 这几个总被混用的指标理清楚——**它们之间是取舍关系，不可能同时最优。**

## 1. 基础词汇：先把本节要用的词讲清楚

**请求（request）与 token**。一个请求就是用户发来的一次调用：一段输入文本（提示词）加上"请继续生成"的要求。模型处理的最小单位是 **token**（可以粗略理解为一个词或半个词）。一个请求的完整生命周期是：把输入的 P 个 token 一次性处理完（**prefill**），然后一个一个地生成 D 个输出 token（**decode**）。

**TTFT（Time To First Token，首 token 延迟）**。从请求到达到用户看到第一个字的时间。它主要由 prefill 阶段的耗时和排队等待时间决定。**在交互式场景里它是用户体感最直接的指标**——聊天界面里那个"等了多久才开始出字"。

**TPOT（Time Per Output Token，每输出 token 时间；也叫 ITL，inter-token latency）**。生成第一个 token 之后，后续每个 token 之间的间隔。它决定了"出字的速度"。人的阅读速度大约是每秒 5 到 10 个 token，所以 TPOT 低于 100 毫秒时用户基本感觉不到等待。

**吞吐（throughput）与 goodput**。吞吐是"每秒总共吐出多少 token"，它是运营方关心的量（决定单位成本）。**goodput 是"每秒吐出多少满足了延迟要求的 token"**——如果一个请求的 TPOT 超了标准，它产出的 token 虽然计进吞吐，但对业务没有价值。第 8 节会看到，**优化吞吐和优化 goodput 会给出不同的配置**。

**SLO（Service Level Objective，服务水平目标）**。对延迟的量化承诺，通常写成分位数形式："P99 的 TTFT 低于 1 秒、P99 的 TPOT 低于 50 毫秒"。注意用的是分位数而不是平均值——**平均延迟好看而尾部延迟糟糕，是服务系统最典型的失败形态**。

**批（batch）**。同时被送进 GPU 一起算的请求集合。批越大，权重被复用的次数越多（模块 01 附录 A2 那笔"每专家 token 数"的账在这里换了个名字），吞吐越高；但批越大，每个请求等待同伴的时间也越长。**服务系统的核心工作，就是在每一个瞬间决定"这一批放谁进来"。**

**KV cache**。模块 01 附录 A2 介绍过：decode 阶段每生成一个新 token 都要对全部历史 token 做注意力，历史的 K、V 缓存在显存里避免重算。**在服务层，它不再只是一个性能优化，而是直接决定了"这张卡能同时装下几个用户"**——第 2 节把这笔账算出来。

## 2. 第一笔账：KV cache 就是并发数

### 2.1 一个 token 的 KV 占多少字节

公式很直接：

> **每 token 的 KV 字节数 = 2（K 和 V 各一份）× 层数 × KV 头数 × 每头维度 × 每个数的字节数**

**代进一个 70B 量级的配置手算**（80 层、每头维度 128、bf16 即 2 字节）：

| 注意力结构 | KV 头数 | 每 token 字节数 | 4096 token 的一个请求 |
| --- | --- | --- | --- |
| **MHA**（标准多头，64 个头） | 64 | 2×80×64×128×2 = **2.62 MB** | **10.7 GB** |
| **GQA**（分组查询，8 个 KV 头） | 8 | 2×80×8×128×2 = **328 KB** | **1.34 GB** |

**现在把它换算成并发数。** 一张 80 GB 的 H100，模型权重（bf16）占 140 GB——放不下，所以先假设用 TP=4 分到四张卡上，每卡权重 35 GB，**剩下约 45 GB 给 KV cache**：

| 注意力结构 | 每请求 KV（4K 上下文） | **这张卡能同时服务几个请求** |
| --- | --- | --- |
| MHA | 10.7 GB | **4 个** |
| GQA | 1.34 GB | **33 个** |

**八倍的并发数差距。** 模块 04 第 5 节讲 GQA 时算的是"decode 延迟除以 4"（因为每步要读的 KV 字节少了四分之三）。**这里是同一个改动的第二笔收益，而且在服务场景里往往更重要**：延迟改善四倍是体验问题，并发数提升八倍是**成本问题**——同样的机器多服务八倍的用户，每个用户的成本降到八分之一。

**这条账值得单独立成一句话记住**：

> **在推理服务里，KV cache 的大小不是一个性能参数，它是一个业务参数——它直接等于并发数，也就直接等于单位成本。**

**这也解释了为什么"砍 KV 字节数"这条技术线（GQA → MLA → KV 量化 → 稀疏注意力）这几年如此密集**：它同时改善延迟、并发数和成本三件事，是算法侧杠杆率最高的改动之一（模块 04 第 5 节的传导链三）。

### 2.2 上下文长度是这笔账的乘数

上面算的是 4K 上下文。**KV cache 随上下文长度线性增长**，所以：

| 上下文长度 | 每请求 KV（GQA 配置） | 45 GB 能装几个 |
| --- | --- | --- |
| 4 K | 1.34 GB | 33 |
| 32 K | 10.7 GB | **4** |
| 128 K | 43 GB | **1** |

**上下文拉到 128K 时，一张卡的 KV 预算只够服务一个用户。** 这就是"长上下文很贵"这句话的精确含义——**贵在并发数塌到 1，而不是贵在计算量**。理解了这一点，就能理解为什么长上下文场景下所有的技术努力（KV 量化、稀疏注意力、KV 卸载到主机内存或闪存）都集中在"怎么让 KV 小一点"上。

## 3. 连续批处理：为什么静态批浪费一半以上

### 3.1 静态批的问题：所有人陪最长的那个等

最朴素的做法是**静态批处理**：攒够 B 个请求，一起送进去，全部生成完毕后再收下一批。

**问题在于每个请求的输出长度不同。** 走查一个例子——4 个请求组成一批，输出长度分别是 20、100、40、200 个 token：

| 请求 | 输出长度 | 真正在产出的步数 | 陪跑的步数 |
| --- | --- | --- | --- |
| A | 20 | 20 | 180 |
| B | 100 | 100 | 100 |
| C | 40 | 40 | 160 |
| D | 200 | 200 | 0 |
| **合计** | | **360** | **440** |

**这一批总共跑了 200 步 × 4 个槽位 = 800 个槽位·步，其中只有 360 个在产出，有效率 45%。** 剩下 55% 的算力花在了已经结束的请求上——它们的槽位空着，但批的形状是固定的，新请求进不来。

**而且这还不是最糟的。** 更糟的是**新到的请求必须等整批跑完才能开始**：如果 D 要生成 200 个 token、每个 20 毫秒，那么在第 1 步之后到达的请求，最坏要等 4 秒才能开始 prefill——**TTFT 直接被别人的输出长度绑架了。**

### 3.2 连续批处理：以 token 为粒度进出

**连续批处理（continuous batching，也叫 in-flight batching）的做法是：不再以"批"为单位进出，而是以"一步"为单位。** 每完成一步 decode，调度器就检查一遍：

1. 哪些请求已经生成完毕（吐出了结束符或达到长度上限）？**立刻把它们移出批、释放 KV cache。**
2. 队列里有没有等待的新请求？**如果 KV cache 有余量，立刻把它们加进来。**

**同一个例子重跑一遍。** 假设队列里源源不断有新请求，那么 A 在第 20 步结束时，它的槽位立刻被新请求 E 顶上；C 在第 40 步结束时被 F 顶上……**任何时刻四个槽位都在产出有效 token，有效率接近 100%。**

**收益是两方面的，而且都很大**：

- **吞吐**：从 45% 提到接近 100%，**翻一倍以上**（真实系统里公开报告的提升在 2 到 20 倍之间，取决于输出长度的离散程度——长度越参差，静态批浪费越多，连续批的收益越大）。
- **TTFT**：新请求不再等整批，**平均等待时间从"最长输出的时间"降到"一步的时间"**，也就是从秒级降到十毫秒级。

**这个机制之所以能成立，依赖一个前提：批的形状可以每步改变。** 而这正是 GPU 相对静态调度芯片的优势（模块 00 那条光谱）——**如果 kernel 要求批大小编译期固定，连续批处理根本无法实现。** 现代推理引擎的 kernel 全都做成了"批大小是运行时参数"的形态，这是一个为服务场景专门付出的设计代价。

**它也带来了一个新的技术需求，正好接下一节**：请求随时进出，意味着 KV cache 的分配和释放是**高频、变长、不可预测**的——用连续的显存块管理它必然产生严重碎片。

## 4. PagedAttention：把操作系统的页表搬进显存

### 4.1 问题：碎片，而不是带宽

**先说清楚这一节要解的问题和前面几节都不同。** 模块 06 讲的布局问题都是为了带宽（合并访存、bank 冲突、通道拥挤）。**PagedAttention 解的是分配问题**——它对带宽几乎没有帮助，纯粹是为了把显存用满。

**问题的来源是"边生成边增长"。** 一个请求刚进来时只有输入的几百个 token，随着生成，它的 KV 会一直长到几千甚至几万个 token，而**谁也不知道它会生成多长**（模型什么时候吐结束符是运行时才知道的）。于是连续分配面临一个两难：

- **按最大可能长度预留**（比如每个请求预留 32K 的空间）：一个只生成 50 个 token 的请求也占着 32K 的坑，**利用率可能只有百分之几**。
- **按当前长度分配、不够了再扩**：显存里很快布满大小不一的空洞，新请求要的连续块找不到，**明明总量够却分配失败**。

**这两个问题在操作系统的内存管理里出现过一模一样的版本，而且答案早就有了：分页。**

### 4.2 机制：固定大小的页加一张页表

**做法**：

1. 把 KV cache 的显存切成**固定大小的页**（block），每页存固定数量的 token 的 KV——典型是 16 个 token。
2. 每个请求持有一个**页表**（block table），记录"我的第 0 到 15 个 token 在物理页 47，第 16 到 31 个在物理页 12……"。**逻辑上连续的序列，物理上散落在任意页里。**
3. 请求增长时，从空闲页池里取一页挂上去；请求结束时，把它的所有页还给池子。
4. attention kernel 读 KV 时，先查页表把逻辑位置翻译成物理页——**多一次间接寻址，换来分配的完全灵活。**

**走查一个数**：一个已经生成到第 700 个 token 的请求，持有 ⌈700/16⌉ = **44 页**，这 44 页在物理上互不相邻。它下一步再生成一个 token，正好是第 701 个——**页内还有空位（700 mod 16 = 12，这一页只用了 12 个位置），不需要新分配**；再生成 4 个之后这一页满了，才去池子里要第 45 页。

**收益**：显存利用率从静态预留方案的百分之几十提到接近 100%。**按第 2.1 节那笔账，利用率翻倍就等于并发数翻倍、单位成本减半**——这是 vLLM 这类推理引擎最初的核心卖点。

**代价有三条，都要说清**：

1. **间接寻址**：kernel 每次读 KV 都要多查一次页表。这个开销不大（页表在 shared memory 里），但 attention kernel 必须重写成"支持分页"的形态——**FlashAttention 的标准实现不能直接用，要用 paged 变体**（模块 04 附录 A1 讲的 FlashMLA 就是为 MLA 结构写的 paged decode kernel）。
2. **尾页浪费**：最后一页平均只用一半。页越大浪费越多，页越小页表越长、间接寻址开销越大。**这是模块 02 第 5 节"形状税"在显存分配上的又一次出现**，只是这里的"阵列边长"换成了页大小。
3. **调度器要管这个池子**：什么时候准入新请求、显存不够时抢占谁，都变成了调度器的工作。

### 4.3 分页带来的意外红利：前缀共享

**页表还有一个当初可能没预料到的用途**：**两个请求如果有相同的前缀，它们的页表可以指向同一批物理页。**

这件事在真实业务里价值极大，因为**前缀相同是常态而不是例外**：

- 所有请求共享同一段系统提示词（几百到几千个 token）。
- 多轮对话里，第 n 轮的输入包含了前 n−1 轮的全部内容。
- 少样本提示里，那几个示例对所有请求都一样。

**算一笔账**：系统提示词 2000 个 token，100 个并发请求。不共享时这段前缀的 KV 要存 100 份（按 GQA 配置，100 × 2000 × 328 KB ≈ **64 GB**）；共享时只存 1 份（**0.64 GB**）。**省下的 63 GB 直接变成更多并发。** 而且**这些请求的 prefill 也不用重算**，TTFT 随之大幅下降。

**这个机制叫前缀缓存（prefix caching）**。它需要页是**写时复制**的——两个请求共享前缀页，一旦某个请求要往里写新内容，就复制一份自己改。**这又是操作系统里的老概念（copy-on-write）被原样搬过来。**

**值得记住的一个观察**：PagedAttention 这类工作的价值不在于发明了新算法，而在于**认出了"这是一个已经被解决过的问题"**——显存管理和操作系统的内存管理是同构的，页表、写时复制、碎片整理这些几十年前的答案可以直接迁移。**遇到系统层的新问题时，先问一句"操作系统或数据库里有没有同构的问题"，往往能省很多力气。**

## 5. prefill 与 decode 的互相伤害，以及业界给的三个答案

### 5.1 问题：它们的性质完全相反

模块 01 附录 A2 论证过：**prefill 是计算受限的（算术强度约 N/2），decode 是访存受限的（算术强度约 1）**。在服务系统里，这两种性质完全相反的工作**要在同一批里、同一个 kernel 里、同一张卡上**同时发生——冲突是必然的。

**冲突的具体形态：一个长 prefill 会把同批所有 decode 卡住。** 算一笔时间账：

| 工作 | 计算量 | 在 H100 上的耗时量级 |
| --- | --- | --- |
| 一步 decode（批 32，每请求 1 token） | 读一遍权重 + 读 KV | **约 20 毫秒**（被带宽卡死） |
| 一个 4096 token 的 prefill | 4096 × 6N 量级 | **约 500 毫秒**（被算力卡死） |

**如果把这个 prefill 和这批 decode 放进同一步，这一步就要 500 毫秒。** 对那 32 个正在生成的请求来说，它们的 TPOT 从 20 毫秒突然变成 500 毫秒——**用户看到的是"出字出到一半，卡了半秒"**。这个现象在服务里非常显眼，术语叫 **prefill 对 decode 的干扰**，也常被叫做"生成卡顿"。

**而且这不是偶发的**：只要有新请求进来就会发生一次，而新请求是持续到达的。

### 5.2 答案一：chunked prefill（把长 prefill 切碎）

**做法**：不再把一个 prefill 一次做完，而是把它切成固定大小的块（比如每块 512 个 token），**每一步只做一块，和 decode 混在同一批里**。

**同一个例子重算**：4096 个 token 的 prefill 切成 8 块，每块约 62 毫秒；每一步的时间从"20 毫秒或 500 毫秒"变成稳定的"20 + 62 = 82 毫秒"。

**收益与代价的取舍很清楚**：

| | 不切 | 切成 8 块 |
| --- | --- | --- |
| decode 的 TPOT | 平时 20 ms，被干扰时 **500 ms** | 稳定 **82 ms** |
| 该请求的 TTFT | 500 ms | **8 × 82 = 656 ms**（略长） |
| 整体 goodput | 尾延迟差，很多 token 超 SLO | **好得多** |

**一句话总结：chunked prefill 用"每个人都稍慢一点"换掉了"少数人极慢"**。这正是 §1 里强调"SLO 用分位数而不是平均值"的原因——**平均延迟可能没变甚至变差，但 P99 大幅改善，业务价值是后者。**

**它还有一个副作用值得记**：把 prefill 的块和 decode 混在一起之后，**每一步的批里同时有"算力受限的活"和"带宽受限的活"**——两者用的是不同的硬件资源，混在一起反而让两种资源都用得更满。**这是模块 04 附录 A1 那条"藏延迟"配方在服务层的又一次出现**：找到两件性质互补的事，让它们同时进行。

### 5.3 答案二：分离式部署（prefill 和 decode 分开跑）

**更彻底的做法是：干脆用不同的机器分别做 prefill 和 decode。** 一个请求先在 prefill 集群上做完预填充，把生成的 KV cache 传给 decode 集群，再在那里逐 token 生成。

**为什么这样分是合理的，用 A2 的账就能说明**：两个阶段对硬件的需求正交——

| | prefill | decode |
| --- | --- | --- |
| 瓶颈 | 算力 | 显存带宽 |
| 想要的硬件 | 高 FLOPS，显存带宽不重要 | 高带宽、大容量，算力过剩 |
| 想要的批策略 | 小批就能喂饱（本来就计算受限） | 批越大越好（摊薄权重读取） |
| 想要的并行策略 | TP 度数可以小 | TP 度数大一些以摊薄权重 |

**分开之后，两边可以各自选最优配置**——这是合在一起时做不到的，因为一个批只能有一套配置。

**代价是新增了一跳通信**：KV cache 要从 prefill 机传到 decode 机。**这一跳的量可以算**：4096 token 的请求，GQA 配置下 KV 是 1.34 GB；走 NVLink（1.8 TB/s）不到 1 毫秒，走 InfiniBand（约 100 GB/s）约 13 毫秒。**所以分离式部署要求 prefill 和 decode 之间有高速互连**——它是一个 scale-up 域内的方案，不是随便两台机器就能做的。

### 5.4 答案三：连硬件都分开（Rubin CPX）

**2026 年，这条路线走到了硬件层。** NVIDIA 的 Rubin CPX 是专为 prefill 设计的芯片：单 die、**128 GB GDDR7 而不是 HBM**、30 PFLOPS NVFP4；decode 留给配 HBM4 的 Rubin 本体。Vera Rubin NVL144 CPX 机架里两种芯片各 144 颗。

**为什么 prefill 芯片可以用便宜得多的 GDDR7**，正是 §5.3 那张表第一行的推论：**prefill 是计算受限的，它根本用不上 HBM 的带宽，给它配 HBM 是把钱花在它不需要的地方。** 用模块 07 第 2 节那张 GDDR 与 HBM 的对照表来说——GDDR 是"少而快"、HBM 是"多而慢"，而 prefill 需要的是算力和容量，不是位宽。

**这件事对读这个库的人有一个方法论上的意义**：模块 01 附录 A2 那笔手算（prefill 的 AI ≈ N/2、decode 的 AI ≈ 1）在 2023 年只是一个用来理解性能的分析工具；到 2026 年，它变成了一条**机柜里的物理分界线**。**一个够硬的分析结论，最终会在硬件形态上兑现——这是本库反复出现的那句"算法/系统/硬件在同一张账本上"最生动的一次证明。**

## 6. 排队论：为什么不能把 GPU 跑到 95%

这是本节最反直觉、也最容易被忽略的一段。

**很多人的直觉是"GPU 利用率越高越好"**——毕竟机器是租来的，闲着就是浪费。**但对一个有延迟要求的服务，这个直觉是错的，而且错得可以量化。**

### 6.1 机制：等待时间随利用率非线性上升

设服务器的**利用率 ρ**（到达率除以服务率，即"忙的时间占比"）。排队论里最基础的模型（M/M/1）给出的排队等待时间是：

> **平均排队时间 = 服务时间 × ρ / (1 − ρ)**

**关键在分母那个 (1 − ρ)：当 ρ 趋近 1，等待时间趋于无穷。** 代几个数：

| 利用率 ρ | 排队时间 ÷ 服务时间 | 总延迟（服务时间为 1 时） |
| --- | --- | --- |
| 50% | 1.0 | **2.0** |
| 70% | 2.3 | **3.3** |
| 80% | 4.0 | **5.0** |
| 90% | 9.0 | **10.0** |
| 95% | 19.0 | **20.0** |
| 99% | 99.0 | **100.0** |

**从 80% 提到 95%，吞吐只涨了 19%，延迟却涨了四倍。** 这就是所谓的"排队拐点"——曲线在 70% 到 80% 之间开始急剧上翘。

**为什么会这样，直觉上的解释是：请求的到达是随机的、服务时间也是变化的。** 利用率高意味着系统几乎没有空闲余量，一旦到达出现一个小高峰（或者某个请求特别长），队列就积压起来，而且**没有空闲时间来消化这个积压**。利用率越高，从抖动中恢复得越慢。

### 6.2 对推理服务的具体含义

**这条曲线解释了几件在真实系统里反复出现的事**：

1. **"平时很好，一到高峰就雪崩"**——不是高峰时刻突然出了 bug，而是利用率跨过了拐点，延迟按上表的规律跳变。
2. **容量规划必须留余量**。按 100% 利用率算出来的"这些卡够用"，在实践中会在 80% 的负载上就崩掉 SLO。**行业经验是把稳态利用率控制在 70% 左右**，剩下的 30% 是买给尾延迟的保险。
3. **批大小的调优不是越大越好**。批越大吞吐越高（利用率越高），但每个请求的等待也越长。**最优批大小是让"延迟刚好卡在 SLO 上"的那个值，而不是让吞吐最大的那个值。**

**推理服务还有一个让这条曲线更陡的因素：服务时间的方差极大。** 一个请求可能生成 10 个 token，也可能生成 2000 个——**服务时间差两个数量级**。排队论里方差越大、同样利用率下的等待时间越长（M/G/1 队列的 Pollaczek–Khinchine 公式里方差是直接的乘数项）。**所以推理服务的拐点比标准模型还要靠左。**

**这一段和模块 01 的一个概念形成了有意思的对照**：模块 01 讲 GPU 内部时，结论是"占用率高、执行单元忙 = 好"。**到了服务层，同样是"忙"，结论却相反。** 区别在于**有没有外部的延迟约束**：GPU 内部的 warp 不在乎自己等多久，只要总吞吐高就行；而外面的用户在乎。**"利用率越高越好"这条直觉的适用边界，正好就是"有没有人在等"。**

## 7. 投机解码：制造批量的另一条路

模块 04 第 5 节把投机解码列为"结构层对抗小 M 困境的代表作"，这里把账算完整，因为它在服务层有一个明确的适用边界。

**机制**：

1. 用一个**小模型**（草稿模型，或者模型自己的浅层、或者一个 n-gram 表）快速猜出接下来的 k 个 token。
2. 把这 k 个候选**一次性**送进大模型做一次前向——**注意这一次前向可以并行验证全部 k 个位置**，因为每个位置的输入都已经确定了。
3. 从头逐个比对：大模型认可的前缀保留，第一个不认可的位置用大模型自己的输出替换，后面的丢弃。
4. **数学上可以证明，这样产出的分布和逐个生成完全一致**——它不是近似，是精确的。

**为什么这能加速，回到 A2 的账**：decode 每步只算 1 个 token，算术强度约 1，**读一遍权重只干了一个 token 的活**。投机解码让同一次权重读取服务 k 个 token 的验证——**算术强度提高到接近 k 倍，而 decode 本来就在带宽受限区，所以时间几乎不变**。

**加速比怎么算。** 设接受率为 α（草稿的每个 token 被接受的概率），一次验证的期望产出是：

> **期望接受的 token 数 = (1 − α^(k+1)) / (1 − α)**

代几个数（k = 4）：

| 接受率 α | 期望产出 token 数 | 相对逐个生成的加速上限 |
| --- | --- | --- |
| 0.5 | 1.94 | **1.9×** |
| 0.7 | 2.78 | **2.8×** |
| 0.9 | 4.10 | **4.1×** |

**但这是上限，要减掉两笔成本**：

1. **草稿模型自己的耗时**。如果草稿模型是大模型的十分之一，每次投机要多付 k × 10% = 40% 的时间。
2. **验证时批变宽的代价**——这一条是本节要强调的重点：**投机解码在低并发时几乎是纯赚，在高并发时可能是负收益。**

**为什么？** 因为它的收益来自"让带宽受限的 decode 变得计算密集一点"。**但如果服务已经有很高的并发（比如批 64），那么权重读取早就被 64 个请求摊薄了，算术强度已经不低——这时再加投机，只是让本来就吃紧的算力更吃紧。** 用 A2 的语言说：**投机解码是把算术强度往右推，而高并发已经把它推到右边了，再推就越过平衡点变成计算受限。**

**所以实践中的判据很清楚**：

- **低并发、延迟敏感**（比如单用户的编程助手）：投机解码收益大，值得开。
- **高并发、吞吐优先**（比如批量处理任务）：收益小甚至为负，通常关掉。

**这条判据本身是本库方法论的一次应用**：遇到一个"要不要开这个优化"的问题，先问"它改变的是算术强度的哪一侧"，再问"当前负载在平衡点的哪一边"。

## 8. 指标体系：四个数之间的取舍

最后把散落各处的指标收拢成一张图。**它们不是四个可以同时优化的目标，而是一组此消彼长的量。**

| 指标 | 衡量什么 | 谁关心 | 主要被什么影响 |
| --- | --- | --- | --- |
| **TTFT** | 从请求到首个 token 的时间 | 交互式用户 | prefill 耗时、排队等待、chunked prefill 的块大小 |
| **TPOT / ITL** | 每个后续 token 的间隔 | 交互式用户 | 批大小、prefill 干扰、KV 带宽 |
| **吞吐** | 每秒总 token 数 | 运营成本 | 批大小、并发数、KV cache 容量 |
| **goodput** | 每秒满足 SLO 的 token 数 | **业务真实价值** | 上面三者的组合 |

**三组核心取舍**：

1. **批大小 ↔ 延迟**。批越大，吞吐越高、TPOT 越差。**最优点由 SLO 决定而不是由吞吐决定**（§6）。
2. **TTFT ↔ TPOT**。chunked prefill 把块切小，TPOT 更稳但 TTFT 变长（§5.2）；切大则相反。**块大小就是这条取舍的旋钮。**
3. **吞吐 ↔ goodput**。这一条最容易被误判：**把批开到最大能让吞吐数字最好看，但如果大量 token 的 TPOT 超了 SLO，goodput 反而下降。** 只看吞吐调参，几乎必然调到 SLO 之外。

**一个可操作的调参顺序**：

1. **先定 SLO**（P99 的 TTFT 和 TPOT 各是多少）——没有 SLO 就没有 goodput，一切调参失去方向。
2. **在满足 SLO 的前提下，把批大小往上推到刚好卡住的那个点**。
3. **检查利用率是否在拐点以内**（§6，稳态目标约 70%）。
4. **开 chunked prefill 稳住尾延迟**，调块大小平衡 TTFT 与 TPOT。
5. **算 KV cache 的容量账**（§2），确认并发数不是被显存卡住的。
6. **低并发场景再考虑投机解码**（§7）。

## 10. 最新架构落点（知识截至 2026-08）

- **分离式部署已经从软件方案上升为硬件形态**：Rubin CPX（§5.4）。**对读者的直接意义是：以后评估一个推理方案，"prefill 和 decode 跑在什么硬件上"会成为一个必问的问题**，而不再默认它们在同一张卡上。
- **稀疏注意力进入生产，直接改写 §2 的 KV 账**。DeepSeek 的 DSA（模块 04 第 5 节）在 128K 上下文下把每次 query 的活跃 KV 足迹降到约 0.6 GB。**注意它砍的是"每步要读多少 KV"而不是"要存多少 KV"**——存储仍然要占，所以它主要改善的是 TPOT 和算力，对并发数的改善需要配合 KV 卸载才能兑现。
- **KV cache 的分层存储正在成型**：热的留 HBM、温的放主机内存（经 NVLink-C2C 或 PCIe）、冷的放 SSD。模块 07 第 2 节讲的 HBF（高带宽闪存）也在被讨论用于这一层——**但那一节算过写寿命的账，结论是 KV cache 因为每个 token 都在写，恰恰是最不适合放闪存的数据**。这条判断在服务层同样成立。
- **推理引擎的分工格局**：vLLM、SGLang、TensorRT-LLM 三家覆盖了绝大多数生产部署，它们都把模块 04 第 1 节说的①②⑤层压成一体（调度、显存管理、定制 kernel 深度耦合）。**选型时真正要比的不是"谁的 kernel 快"，而是"谁的调度器在你的负载形状上更合适"**——因为 kernel 层大家都在用同一批开源实现（FlashAttention、FlashInfer、DeepGEMM）。
- **一个值得跟踪的方向**：随着 agent 类负载（多轮、长上下文、大量共享前缀）占比上升，**前缀缓存的命中率正在成为比批大小更重要的调优对象**。这类负载的特征是"输入长、输出短、前缀高度重复"，和传统的聊天负载完全不同，调参结论不能直接搬。

## 12. 术语卡

### KV cache 就是并发数

**定义**：每 token 的 KV 字节数 = 2 × 层数 × KV 头数 × 每头维度 × 精度字节数。它乘以上下文长度就是一个请求占用的显存，而"可用显存除以它"直接等于这张卡能同时服务的请求数。

**为什么存在**（作为一条要背下来的换算）：它把一个技术参数（注意力的头数配置）直接翻译成业务参数（并发数、单位成本）。70B 量级的模型上，MHA 换成 GQA 让并发数从 4 个变成 33 个——**同样的机器多服务八倍的用户**。这是算法改动在服务层杠杆率最高的一类。

**语境例句**："上下文开到 128K 之后并发只能到 1。"——意思是单个请求的 KV 就吃掉了几乎全部可用显存，不是算力不够而是装不下；解法在"砍 KV 字节"而不是"加算力"。

### 连续批处理（continuous batching）

**定义**：以单步 decode 为粒度动态调整批的成员——每步结束时移出已完成的请求、放入排队的新请求，而不是攒够一批一起跑完。

**为什么存在**：请求的输出长度差异极大，静态批里先完成的请求会占着槽位空转到最后一个结束，有效率常常只有百分之四五十；同时新请求要等整批跑完才能开始，TTFT 被别人的输出长度绑架。连续批处理同时解决这两件事，吞吐提升常在数倍量级。

**语境例句**："这个引擎不支持 in-flight batching。"——意思是它还在用静态批，长短混杂的真实流量下会浪费一半以上的算力，而且尾延迟很难看。

### PagedAttention 与前缀缓存

**定义**：把 KV cache 切成固定大小的页（典型 16 个 token）、用页表把逻辑上连续的序列映射到物理上离散的页。副产品是相同前缀的请求可以让页表指向同一批物理页（前缀缓存，配合写时复制）。

**为什么存在**：KV cache 边生成边增长且最终长度不可预测，连续分配要么大量预留浪费、要么产生碎片。分页把显存利用率提到接近 100%，代价是 attention kernel 要多一次页表间接寻址、且必须重写成支持分页的形态。**它解的是分配问题而不是带宽问题——这是它和模块 06 讲的其它布局技术的根本区别。**

**语境例句**："system prompt 两千 token，一百个并发。"——如果没有前缀缓存，这段前缀的 KV 要存一百份约 64 GB；有了它只存一份，省下的显存直接变成更多并发，而且这些请求的 prefill 都不用重算。

### prefill 干扰与 chunked prefill

**定义**：一个长 prefill 混进 decode 批时会把这一步的耗时从几十毫秒拉到几百毫秒，让同批所有请求的出字卡顿。chunked prefill 把 prefill 切成固定大小的块，每步只做一块，与 decode 混合执行。

**为什么存在**：prefill 计算受限、decode 访存受限，两者耗时差一个数量级，同批执行时短的被长的绑架。切块用"每个人都稍慢一点"换掉"少数人极慢"——平均延迟可能不变，但 P99 大幅改善，而业务价值在 P99。副作用是混合批同时用满了算力和带宽两种资源。

**语境例句**："TPOT 中位数 25 毫秒，P99 有 400 毫秒。"——典型的 prefill 干扰指纹；开 chunked prefill 并调小块大小可以把这个尖峰压平。

### 排队拐点（利用率与延迟的非线性关系）

**定义**：排队等待时间随利用率 ρ 按 ρ/(1−ρ) 增长，在 70% 到 80% 之间开始急剧上翘。利用率从 80% 提到 95%，吞吐只涨 19%，而延迟涨四倍。

**为什么存在**：请求到达是随机的、服务时间有方差，利用率高意味着没有空闲余量来消化突发积压。推理服务的服务时间方差尤其大（输出长度可差两个数量级），所以拐点比标准模型更靠左。**这条曲线是"容量规划必须留三成余量"这条运维经验的数学依据。**

**语境例句**："平时都好好的，一上量就雪崩。"——多半不是出了 bug，而是利用率跨过了拐点；正确的做法是把稳态利用率控制在七成左右，而不是等出事再加机器。

### goodput（满足 SLO 的吞吐）

**定义**：每秒产出的、且满足延迟要求的 token 数。区别于总吞吐——超出 SLO 的 token 计进吞吐但没有业务价值。

**为什么存在**：把批开到最大能让吞吐数字最好看，但如果大量请求的 TPOT 超标，用户体验崩塌而账面数字漂亮。goodput 强迫把延迟约束写进目标函数，是服务系统唯一诚实的效率指标——**它在推理侧的地位相当于 MFU 在训练侧的地位。**

**语境例句**："吞吐涨了 30%，但 goodput 掉了。"——意思是批开大了，多产出的 token 大部分超了延迟标准，这个"优化"实际上是负收益。

### 投机解码的适用边界

**定义**：用小模型猜 k 个 token、大模型一次前向并行验证的技术。产出分布与逐个生成完全一致（不是近似）。期望产出 =(1−α^(k+1))/(1−α)，α 为接受率。

**为什么存在**：decode 每步只算一个 token，读一遍权重只干一个 token 的活；投机让同一次权重读取服务 k 个位置的验证，把算术强度往右推。**但正因如此，它在高并发时可能是负收益**——高并发本身已经把算术强度推到了平衡点右侧，再推就变成计算受限。

**语境例句**："投机解码在压测里反而更慢。"——压测通常是高并发场景，权重读取已被大批量摊薄，此时草稿模型的额外开销赚不回来；它的主场是低并发、延迟敏感的交互式负载。
