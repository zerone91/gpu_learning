## 1. 融合（fusion）：图层的头号武器

### 1.1 省的是什么：HBM 往返

未融合的 `y = relu(x + b)`：add kernel 把结果**写回 HBM**，relu kernel 再**读回来**。融合后：数据**在寄存器里**从加法流到 relu，HBM 流量砍半以上。回到 §01-04 的账：**elementwise 链全是 memory-bound（AI≈0.25），融合 N 个 elementwise ≈ HBM 流量除以 N**——这是全栈性价比最高的优化，没有之一。

### 1.2 分类学（黑话对号）

| 类型 | 形态 | 例 |
| --- | --- | --- |
| **纵向融合**（vertical / producer-consumer） | 生产者输出直接喂消费者，不落 HBM | elementwise 链、norm+add |
| **横向融合**（horizontal） | 多个无依赖的同形算子并进一个 kernel（摊 launch/读共同输入） | 多头的 QKV 三个投影并成一个 GEMM |
| **epilogue 融合** | 把 GEMM **后面**的零碎（bias/relu/scale/residual）塞进 GEMM 的写回阶段 | cuBLASLt epilogue、CUTLASS EVT、Inductor 模板融合 |
| **prologue 融合** | 把读入侧的变换（cast/scale）塞进 GEMM 读数阶段 | FP8 缩放读入 |

**epilogue 融合的经济学**（重要直觉）：GEMM 是 compute-bound（Tensor pipe 满载），它写回 C 时**访存通道是闲的**——把 bias+relu 挂上去**近乎免费**（搭车）。**"让 memory-bound 的零活搭 compute-bound 的车"是②层调度的第一原则。**

### 1.3 融合的边界：什么融不动

- **matmul–matmul 融不动（一般情况）**：两个 GEMM 中间结果是 O(N²) 的大矩阵，寄存器/shared 装不下；且两者最优 tiling 不同。**FlashAttention 是这个"不可能"的著名例外**——靠 online softmax 改写算法，让中间结果可以分块丢弃（A2）。**编译器做不到，因为这需要改数学**——这就是 04-01"跨层走私"的精确边界：**编译器只能重排计算，不能改写算法**。
- **归约是天然分界**：reduction 之后所有元素依赖全部前序（softmax 的分母），朴素融合会破坏并行度——要融必须换算法（online 化）。
- **形状/broadcast 不齐**、**动态控制流**处：融合窗口被切断（graph break）。

## 2. layout：全局的"摆放"问题

- **为什么是②层的活**：单个 kernel 只能"接受"某个 layout；**只有看得见全图，才能算"在哪转置一次总代价最小"**——layout propagation 是个全局优化（最小割/传播问题）。
- **和硬件的钩子**（收 §01-04/03-01 的线）：Tensor Core 的 ldmatrix/TMA 对内维连续与对齐有硬要求 → 卷积在 GPU 上 **NHWC（channels_last）优于 NCHW**（C 维连续=按通道向量化访存）；维度 pad 到 8/16 倍数吃满 MMA 形状——**②层负责让张量"以硬件喜欢的姿势"流动**。
- 黑话：layout transformation / propagation、`channels_last`、AoS→SoA（§01-04 的图层版）。

## 3. 显存规划：生命周期的图着色

②层看得见每个中间张量的**生死时刻**（最后一次被读=死亡），于是：

1. **buffer 复用**：生命周期不重叠的张量共享同一块显存——本质是**区间图着色**问题；静态图（XLA/TRT）可全局求解，eager 只能靠 caching allocator 兜底。
2. **inplace 化**：消费者是最后一个读者 → 直接原地写（relu_）。
3. **activation checkpointing（重计算）**：①/②层决策——丢掉中间激活、反向时重算，**用 §01 "算得起"换"存不起"**——它是访存墙哲学在训练显存上的翻版。
4. 运行时侧配合：PyTorch caching allocator（碎片/`expandable_segments`）、CUDA VMM——⑤层的兜底。

> 🔑 三板斧的统一视角：融合=**时间上**不落地（数据在寄存器里穿过算子边界）；layout=**姿势上**贴硬件；显存规划=**空间上**复用地址。**全是"算子关系"这一②层独家信息的变现。**

## 4. 开发者视角

| 想知道/想做 | 手段 |
| --- | --- |
| 融合发生了没 | profiler kernel 名（`triton_fused_...`、`cutlass_..._epilogue`）；`TORCH_LOGS=+inductor` 看融合决策；kernel 数量骤减 = 融合生效 |
| 为什么没融合 | `torch._dynamo.explain()` 看 **graph break**（print/if/自定义算子都会切断） |
| layout 对不对 | `tensor.is_contiguous(memory_format=torch.channels_last)`；profiler 里大量 `transpose/copy_` kernel = layout 抖动红旗 |
| 显存去哪了 | `torch.cuda.memory._dump_snapshot()` 可视化；碎片看 reserved vs allocated 差 |
| 手动打穿 | 用 FA/自定义融合 kernel 替换（`torch.library` 注册）——记得会切断编译器的融合窗口，权衡 |

**红旗清单**：时间线上密密麻麻的小 kernel（该 compile）；`copy_/transpose` 占比高（layout 抖动）；显存 reserved≫allocated（碎片）。

## 5. 最新架构落点（时效锚点 · 知识截至 2026-01）

- **Inductor 的模板融合**成熟：GEMM 模板（Triton/CUTLASS）+ epilogue 自动缝合；CUTLASS **EVT**（Epilogue Visitor Tree）把 epilogue 做成可组合表达树。
- **FP8/FP4 时代 prologue/epilogue 融合更关键**：缩放因子的读写必须搭车，否则低精度省的带宽被 scale 张量吃回去（Transformer Engine 的活）。
- **XLA/StableHLO** 静态全图路线在 TPU 侧持续；GPU 侧 torch.compile 已成主干。
- **推理引擎**（TRT-LLM/vLLM）：图层优化+手工 kernel 深度混合——层规范化后固定 pattern 直接 pattern-match 到手写融合 kernel。
