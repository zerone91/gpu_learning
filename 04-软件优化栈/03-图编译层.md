# 第②层 · 图编译层：在算子之间的关系上做优化

> **所属模块**：模块 04 · 软件优化栈（五层地图的第②层；五层逐层展开的第二章）
> **状态**：🟨 学习中（第四版：按五层地图重排，补入层档案、功能清单、业界项目与 torch.compile 的全过程走查。知识截至 2026-08）
> **本节主旨**：图编译层接收框架层交来的整张计算图，它手里的独有信息是**算子之间的关系**：谁的输出给了谁、每个中间结果要存活多久。本节先按统一格式给这一层建档（定义、为什么在这里切一刀、输入输出、边界接口、功能清单），然后展开它最重要的三项功能：**算子融合**（让中间结果不落显存，全栈性价比最高的优化）、**数据排布**（让张量按硬件容易访问的顺序存放）、**显存规划**（让存活时间不重叠的张量共用同一块显存）。之后介绍业界的典型项目，并**拿 torch.compile 做标本**，跟踪一个小函数从抓图到生成 kernel 的全过程。三项功能的衡量标准是同一个，即模块 01 第 4 节讲的访存开销：**图编译层的优化，本质上是在整张图的范围内减少数据搬运。**

## 1. 基础词汇：先把本节要用的词讲清楚

**计算图（computation graph）**。把一段计算表示成图：节点是算子，边是数据依赖。它是框架层交给图编译层的交付物，也是本层全部工作的对象。

**中间结果（intermediate）**。图里一个算子的输出、下个算子的输入，是用完即弃的临时张量。未经优化时，每个中间结果都要**完整地写进显存再读出来**，这个往返是图编译层首要的优化对象。

**融合（fusion）**。把相邻的几个算子合并成一个 kernel，让中间结果**不落显存**、直接在寄存器里从前一个计算传给后一个。

**数据排布（layout）**。多维张量在一维内存里的存放顺序，比如一张图片按"行×列×通道"还是"通道×行×列"排。数学上等价，访存效率差别很大（模块 01 第 4 节：地址连续才能合并访问）。

**生命周期（liveness）**。一个中间张量从"被算出来"到"最后一次被读"的存活区间。区间结束后它占的显存就可以给别的张量用，这是显存规划的基本依据。

**重计算（recomputation / checkpointing）**。训练时不保存某些中间结果，反向传播需要时**重新算一遍**，是用算力换显存的标准手段。

**后端（backend）**。图编译器里负责"把优化后的图变成可执行代码"的那一部分。同一个图编译器可以有多个后端，分别面向 GPU、CPU 或其它芯片。

## 2. 这一层的档案

### 2.1 定义

**图编译层是接收整张计算图、利用算子之间的关系做优化、并把图划分成若干个 kernel 生成任务的那层软件。** 它处理的最小单位是算子：它可以合并算子、删除算子、调整算子的顺序，但不进入算子内部去改循环的写法。

### 2.2 为什么在这里切一刀

**和上面的框架层之间的一刀：从"程序"变成"数据结构"。** 框架层面对的是 Python 程序，程序里有任意的控制流和副作用，很难整体分析。抓图之后得到的计算图是一个固定的数据结构，节点和边都是确定的，可以被遍历、被改写、被证明等价。全局优化只有在这种形态上才能进行。

**和下面的 kernel 层之间的一刀：从"算子之间"变成"算子内部"。** 图编译层眼里，矩阵乘是一个不可拆开的节点，它关心的是这个节点和谁相连。一旦决定了"这几个算子合成一个 kernel"，接下来的问题（循环切多大的块、数据放在哪一级存储）就和图的其余部分无关了，只和这一个 kernel 有关。两类问题需要的信息不同、用的方法不同，所以分成两层。

### 2.3 输入与输出

| | 内容 |
| --- | --- |
| **输入** | 计算图，附带每条边上张量的形状和数据类型 |
| **输出** | 优化后的图。具体包括三样东西：一组**融合组**（每组对应一个待生成的 kernel 或一次库调用）、这些融合组的**执行顺序**、每个中间张量使用哪块显存的**规划** |

**例子：`y = relu(x @ W + b)` 的输入和输出。** 输入是一张三个节点的图（矩阵乘、加法、relu），每条边上标着形状 8192×4096 和数据类型 bf16。输出是：一个融合组（矩阵乘模板，加法和 relu 并入它的收尾阶段）；执行顺序只有这一步；显存规划是"申请一块 64 MB 的显存存放 `y`，没有中间张量需要显存"。原图里的两个中间结果（矩阵乘的输出、加法的输出）在输出里已经不存在了。

### 2.4 上下边界的接口

| 边界 | 接口形态 | 具体例子 |
| --- | --- | --- |
| **上边界**（从框架层接收） | 一种图格式 | PyTorch 的 FX 图、ONNX、StableHLO、JAX 的 jaxpr |
| **下边界**（交给 kernel 层） | kernel 的源码或中间表示，或者对算子库的调用 | Inductor 生成 Triton 源码（逐元素和归约类算子），矩阵乘和卷积直接调用 cuBLAS、cuDNN；TensorRT 从内置的 kernel 实现里挑选；XLA 生成 LLVM IR 或调用库 |
| **下边界**（交给运行时层） | 执行计划 | 各 kernel 的调用顺序、显存申请和释放的位置 |

**下边界有一个值得注意的事实：图编译层对不同种类的算子采用不同的交付方式。** 逐元素运算和归约的循环结构简单，编译器自己生成 kernel 代码就能达到很好的性能。矩阵乘和卷积的高性能实现非常复杂，编译器通常不自己生成，而是调用算子库，或者套用一个预先写好的模板再把前后的零碎运算接进去。

### 2.5 这一层看得见什么、看不见什么

| 看得见 | 看不见 |
| --- | --- |
| 算子之间的连接关系 | 算子内部的循环结构 |
| 每个中间张量被谁使用、存活多久 | 片上存储（shared memory、寄存器）的使用情况 |
| 每个张量的形状和数据类型 | 线程和 warp 的分工 |
| 整张图的执行顺序 | 训练语义的大部分（抓图时已被转换成图上的普通节点） |

## 3. 功能集合：这一层要做的九件事

| 功能 | 做什么 | 依赖的信息 |
| --- | --- | --- |
| **接入与规范化** | 把框架层的大量算子分解成少数核心算子；把原地修改的写法改成无副作用的等价形式 | 算子的定义 |
| **形状与类型推断** | 算出图上每条边的形状和数据类型 | 输入形状、每个算子的形状规则 |
| **自动微分（训练时）** | 根据前向图生成反向图，两张图一起进入后续优化 | 每个算子的求导规则 |
| **代数化简** | 常量折叠、公共子表达式消除、死代码消除 | 节点之间的依赖 |
| **算子融合** | 把相邻算子合成一个 kernel | 算子的连接关系、中间结果的使用者 |
| **数据排布** | 为每个张量选定存放顺序，使全图的转置开销最小 | 每个算子偏好的排布、全图结构 |
| **显存规划** | 让生命周期不重叠的张量共用显存；决定哪些中间结果保存、哪些重算 | 每个张量的生命周期 |
| **后端分派与代码生成** | 对每个融合组，决定是生成 kernel、套用模板还是调用库 | 算子的种类、目标硬件 |
| **缓存与重编译管理** | 记录编译结果适用的条件，条件不满足时重新编译 | 输入的形状、类型等属性 |

其中融合、排布、显存规划三项对性能影响最大，第 4 到第 6 节逐项展开。自动微分在编译链上的位置、抓图的机制属于编译器内部的话题，放在本模块第 10 节。下面先用一个例子说明"代数化简"这一项，因为它最容易理解，也能直观地看到"图"这种数据结构带来的好处。

**例子：六个节点的图化简成两个。** 假设抓到的图对应下面的代码，`x` 是 fp32 的输入，`n` 是编译时已知的整数：

```python
a = x.float()                        # 节点 1：类型转换
m = torch.ones(n, n).tril()          # 节点 2：构造下三角掩码
s = a * 0.5                          # 节点 3
t = a * 0.5                          # 节点 4
u = (s + t) * m                      # 节点 5
v = a.exp()                          # 节点 6（v 之后没有被使用）
return u
```

编译器在图上逐项检查。节点 1：`x` 已经是 fp32，转换不改变任何东西，删除。节点 2：掩码只依赖常量 `n`，编译时就可以算好存起来，运行时不再计算，这叫**常量折叠**。节点 3 和节点 4：两个节点的算子和输入完全相同，只保留一个，这叫**公共子表达式消除**。节点 6：输出没有任何使用者，删除，这叫**死代码消除**。化简之后运行时只剩两个运算：`s = x * 0.5` 和 `u = (s + s) * m`，而这两个又都是逐元素运算，下一步会被融合成一个 kernel。**这些判断都只需要沿着图的边查看"谁用了谁"，这正是把程序变成图之后才容易做的事。**

## 4. 融合：图编译层最重要的功能

### 4.1 省的是什么：一笔算得出的账

**例子：`y = relu(x + b)`，x 有一亿个元素（bf16，约 200 MB）。** 不融合时是两个 kernel：加法 kernel 读 x（200 MB）、写中间结果（200 MB）；relu kernel 再读中间结果（200 MB）、写 y（200 MB）——显存流量共 **800 MB**。融合成一个 kernel：读 x、加法和 relu 在寄存器里一气呵成、写 y——流量 **400 MB，恰好减半**。这类逐元素运算是典型的访存受限（模块 01 第 1 节：每个数只算一两下），流量减半就是时间减半。链条越长省得越多：三个逐元素算子串联，融合把流量从 6 份砍到 2 份。**融合要消除的，就是每个中间结果写入显存再读出的这一次往返。**

### 4.2 三种融合形态

- **纵向融合**（最常见）：生产者-消费者直连，如上例。适用于逐元素运算、归一化的链条。
- **横向融合**：几个互不依赖、形状相同的算子并成一个 kernel——省启动开销、共享输入的读取。典型：注意力里 Q、K、V 三个投影矩阵乘并成一个大矩阵乘。
- **epilogue 融合**：把矩阵乘**后面**的零碎运算（加偏置、激活、缩放）并入矩阵乘 kernel 的收尾阶段（epilogue 指 kernel 里"计算完成之后、写回结果"的那一段代码）。它的成本特别低，原因是：矩阵乘是计算受限的（Tensor Core 满负荷工作），而它写回结果的那段时间**访存通道本来就有空余**。零碎运算在结果写回之前顺带完成，不增加任何显存读写，**几乎零成本**。让访存受限的零碎运算并入计算受限的 kernel，是图编译层安排融合时的第一原则。

### 4.3 融合的边界：什么融不动

融合有两条硬边界：

**边界一：两个矩阵乘之间融不动（一般情况）。** 原因有二：中间结果是一整个大矩阵（比如注意力里 QKᵀ 的结果是"序列长×序列长"），寄存器和 shared memory 装不下；而且两个矩阵乘各自的最优分块方式冲突。**著名的例外是 FlashAttention**——但它不是靠编译器：它**改写了 softmax 的数学**（分块在线更新），让中间矩阵可以一块一块地算完就扔。这划出了一条重要的能力边界：**编译器只能重排计算，不能改写算法**——需要改数学的融合，只能由人来完成（第 1 节 §3 说的"跨层优化只能靠人"指的就是这种情况）。

**边界二：归约是天然的分界线。** 归约指把很多个数合并成一个数的运算，比如求和、求最大值。softmax 的分母要等所有元素加完才有——后续计算依赖**全部**前序结果，朴素融合会把并行度掐死。要跨过归约做融合，同样得改数学（在线化），回到边界一。

此外还有工程性的断点：图里夹着 print、数据相关的 if、自定义黑盒算子，都会让抓图在这里中断（这种中断叫 graph break，图被切成两段分别编译），跨越断点的融合机会随之丢失。

## 5. 数据排布：全图统筹的问题

单看一个算子，它只是"偏好"某种排布（比如卷积在 Tensor Core 上偏好通道维连续的 NHWC 格式，因为那样访存能合并、能喂进矩阵指令）。但排布是**全图**的问题，原因看一个例子：

**例子：转置在图里的传染。** 图中有 10 个连续的算子，第 3 个偏好排布甲、其余偏好排布乙。如果只顺着第 3 个的意思，它前后各要插一次转置（重排整个张量，纯搬运开销）；如果让第 3 个将就用乙排布（性能略降），一次转置都不用。哪种划算？**取决于转置的成本与将就的损失之比**——这必须看着整张图算总账，一个算子一个算子地局部决定必然次优。图编译器做的"排布传播"就是这道全局账：目标是**全图转置总成本最小**。实际工程里的红旗信号也由此而来：性能时间线上出现大量转置/拷贝类 kernel，说明相邻算子要求的排布互相冲突，值得查。

## 6. 显存规划：让生命周期不重叠的张量共用显存

图编译层看得见每个中间张量的生命周期（第 1 节词汇），于是可以做一件运行时做不到的事：**让生命周期不重叠的张量共用同一块显存**。

**例子：五个张量，两块显存。** 某段图产生五个中间张量，生命周期（以算子序号计）分别是：A 活在 1–3、B 活在 2–4、C 活在 4–6、D 活在 5–7、E 活在 6–8。朴素分配要五块显存。看重叠关系：A 和 C 不重叠（A 在第 3 步就死了，C 第 4 步才生）——可以共住一块；同理 B 和 D 共住一块；E 和 A 也不重叠可以回收 A 的……排下来**两到三块显存就够了**，省了将近一半。这本质上是个"区间不重叠就同色"的图着色问题，静态图上可以全局求解。配套手段还有**原地操作**（消费者是最后一个读者时直接覆写输入，零新增）和**重计算**——后者值得单算一笔账：

**例子：重计算的交换比。** 训练时每层的激活值都要留到反向传播用，长序列大模型的激活显存动辄几十 GB、常常超过权重本身。开启重计算：只在每层边界存一份"检查点"，中间激活全部丢弃、反向时从检查点重新算一遍前向。代价是**多算约三分之一的前向计算**；收益是激活显存**降到原来的几分之一**。按模块 01 的定调（算力便宜、搬运和容量贵），这笔"用计算换容量"的交易几乎总是划算的——它是那个定调在训练场景的直接应用。

## 7. 业界的典型项目

| 项目 | 主导方 | 接收的图格式 | 编译时机 | 交付物 | 主要场景 |
| --- | --- | --- | --- | --- | --- |
| **torch.compile**（Dynamo + AOTAutograd + Inductor） | PyTorch | FX 图 | 运行时，首次调用时编译 | Triton kernel 加库调用 | PyTorch 训练与推理的默认编译路径 |
| **XLA** | Google | StableHLO / HLO | 运行时或提前 | LLVM 生成的代码加库调用 | JAX、TensorFlow，TPU 的必经之路 |
| **TensorRT** | NVIDIA | ONNX 等 | 提前，离线构建 | 引擎文件（绑定具体 GPU 型号） | NVIDIA GPU 上的推理部署 |
| **ONNX Runtime** | 微软 | ONNX | 加载时优化 | 分派给各执行后端 | 跨硬件的推理部署 |
| **Apache TVM** | 开源社区 | Relax / Relay | 提前，可带自动调优 | 各后端的可执行模块 | 多种硬件，含端侧芯片 |
| **IREE** | Google 发起 | MLIR 的各级 dialect | 提前 | 可移植的字节码加硬件后端 | 端侧与多后端 |
| **CANN 图引擎** | 华为 | MindIR、ONNX 等 | 提前 | 昇腾的离线模型文件 | 昇腾芯片 |
| **OpenVINO** | Intel | 自有 IR、ONNX | 提前 | Intel 硬件上的执行计划 | Intel CPU、GPU、NPU |

**MLIR 不在表里，因为它不是图编译器，而是用来构造编译器的基础设施。** 表里多个项目（IREE、Triton 的编译器、各家新版本的内部实现）都建在它上面。它的内容在本模块第 10 节 §3。

**看这张表可以抓住两条区分线。**

第一条是**编译时机**。运行时编译（torch.compile）能看到真实的输入形状，对用户代码限制少，代价是首次调用有编译延迟，形状变化会触发重新编译。提前编译（TensorRT、CANN）在部署之前把所有工作做完，运行时没有编译开销，可以花很长时间搜索最优方案，代价是形状等信息必须在构建时给定。

第二条是**kernel 从哪里来**。torch.compile 对逐元素类算子现场生成 kernel；TensorRT 自带一批预先写好的 kernel 实现，构建引擎时为每一层挑选其中一个，挑选的方法是在目标 GPU 上实际运行各个候选并计时。前者灵活，能处理任意的算子组合；后者在它覆盖的算子上性能有保证。

## 8. 拿 torch.compile 讲透：一个函数的六步

这一小节跟踪一个具体的小函数，看 torch.compile 内部依次做了什么、每一步之后图变成什么样、最后生成的 kernel 长什么样。

**设定**：输入 `x` 的形状是 8192×4096（8192 个 token，隐藏维度 4096），bf16，一个这样的张量占 64 MB。函数先做一次带偏置和 relu 的线性变换，再做一次 RMSNorm（用每行的均方根做归一化）并乘上逐通道的缩放系数 `g`：

```python
def f(x, W, b, g):
    h = torch.relu(x @ W + b)
    r = torch.rsqrt(h.pow(2).mean(-1, keepdim=True) + 1e-6)
    return h * r * g

f_compiled = torch.compile(f)
y = f_compiled(x, W, b, g)       # 首次调用：触发下面的六步
```

### 第 1 步：抓图

Dynamo（torch.compile 的抓图部件）接管函数的执行，把其中的张量运算记录成图，得到 9 个节点：

```
matmul → add → relu → pow → mean → add(1e-6) → rsqrt → mul(h, r) → mul(·, g)
```

同时它记录下这次抓图依赖的假设，例如"`x` 的形状是 8192×4096""数据类型是 bf16"。这些假设叫 **guard**，之后每次调用都要先检查。

### 第 2 步：规范化

图上的算子被分解成核心算子。本例里 `x @ W` 变成二维矩阵乘算子，`pow(2)` 被改写成 `h * h`（一次乘法比通用的幂运算便宜）。如果是训练，自动微分也在这一步生成反向图；本例按推理处理，跳过。

### 第 3 步：融合决策

编译器按算子的种类给节点分组：

| 融合组 | 包含的节点 | 种类 | 交付方式 |
| --- | --- | --- | --- |
| K0 | matmul | 矩阵乘 | 调用 cuBLAS |
| K1 | add、relu | 逐元素 | 生成 kernel |
| K2 | h*h、mean | 归约（逐元素的平方并入归约的循环里） | 生成 kernel |
| K3 | add(1e-6)、rsqrt、mul、mul | 逐元素 | 生成 kernel |

分组的依据是第 4.3 节讲的边界。K1 不能和 K2 合并成一个循环，因为 `h` 有两个使用者（K2 和 K3），它必须作为一个完整的张量存在。K2 是归约，它的输出是每行一个数（8192 个），形状和 K3 要处理的 8192×4096 不同，K3 的每个元素都要等它所在行的归约结果，所以 K2 和 K3 之间是一条分界线。

**9 个算子变成了 4 个 kernel。** 如果开启更激进的编译模式，矩阵乘可以不调用库而改用一个矩阵乘模板，K1 作为 epilogue 并入其中，kernel 数降到 3 个。

### 第 4 步：算显存流量的账

只看矩阵乘之后的部分（矩阵乘自己的流量三种情况下相同）。每个 64 MB 的张量读一次或写一次记 64 MB，每行一个数的小张量（约 16 KB）忽略不计。

| 方案 | 逐项流量 | 合计 |
| --- | --- | --- |
| **不融合**（8 个 kernel） | add 读写各一次、relu 读写各一次、pow 读写各一次、mean 读一次、两个 mul 各读写一次 | 11 × 64 = **704 MB** |
| **融合成 K1、K2、K3** | K1 读写各一次；K2 读一次；K3 读写各一次 | 5 × 64 = **320 MB** |
| **K1 再并入矩阵乘的 epilogue** | K1 的读写消失（矩阵乘直接写出 `h`）；K2 读一次；K3 读写各一次 | 3 × 64 = **192 MB** |

这部分运算全是访存受限的，时间大致和流量成正比。**融合把这一段的时间降到原来的一半以下，epilogue 融合再降到四分之一左右。**

### 第 5 步：代码生成

对 K1、K2、K3，编译器各生成一份 Triton 源码。下面是 K3 的大致样子（做了简化，保留了结构）：

```python
@triton.jit
def triton_poi_fused_add_mul_rsqrt_2(in_ptr0, in_ptr1, in_ptr2, out_ptr0,
                                     xnumel, XBLOCK: tl.constexpr):
    xoffset = tl.program_id(0) * XBLOCK
    xindex  = xoffset + tl.arange(0, XBLOCK)     # 这个 kernel 实例负责的一段下标
    xmask   = xindex < xnumel                    # 边界掩码
    x1 = xindex // 4096                          # 行号
    x0 = xindex % 4096                           # 列号
    tmp0 = tl.load(in_ptr0 + xindex, xmask)      # h：每个元素一个值
    tmp1 = tl.load(in_ptr1 + x1, xmask)          # 本行的均方：每行一个值
    tmp2 = tl.load(in_ptr2 + x0, xmask)          # g：每列一个值
    tmp3 = libdevice.rsqrt(tmp1 + 1e-06)
    tmp4 = tmp0 * tmp3 * tmp2
    tl.store(out_ptr0 + xindex, tmp4, xmask)
```

读这段代码能看到融合的实质。四个算子（加常数、求平方根的倒数、两次乘法）变成了同一个循环体里的四行，它们之间的中间值 `tmp3`、`tmp4` 是寄存器里的临时量，没有任何一个写入显存。整个 kernel 对显存的访问只有开头的三次读取和最后的一次写入。

**kernel 的名字是编译器按固定规则起的，值得认识**，因为性能工具里看到的就是这些名字。`triton` 表示由 Triton 生成；`poi` 表示逐元素（pointwise），归约类是 `red`；`fused` 后面跟着被融合的算子名；最后的数字是序号。在时间线上看到 `triton_poi_fused_add_mul_rsqrt_2`，就知道这是一个融合了加法、乘法和 rsqrt 的逐元素 kernel。

### 第 6 步：生成调用代码并缓存

编译器再生成一段调用代码，它按顺序做这些事：申请 `h` 的显存，调用 cuBLAS，调用 K1，申请归约结果的显存，调用 K2，申请输出的显存，调用 K3，然后立刻释放 `h` 和归约结果。释放的位置是编译器根据生命周期确定的：`h` 的最后一个使用者是 K3，K3 执行完它就没有用了。这就是第 6 节讲的显存规划在代码里的样子。

编译结果连同第 1 步记录的 guard 一起存入缓存。第二次调用时先检查 guard：形状、类型都没变，就直接执行缓存里的代码，不再编译。如果 `x` 的形状变成了 4096×4096，guard 不满足，六步重新走一遍。这解释了第 1 节排查表里"形状一变就卡顿几秒"的现象。

### 对照：TensorRT 处理同类问题的方式

TensorRT 是提前编译的代表，把它和上面的过程对照，可以看清两种编译时机的差别。

| 环节 | torch.compile | TensorRT |
| --- | --- | --- |
| 什么时候编译 | 首次调用时 | 部署之前，离线构建引擎 |
| 输入形状 | 从真实输入得到，变了就重编译 | 构建时指定一个范围（最小、常用、最大） |
| 融合规则 | 按算子种类通用地融合 | 按预定义的模式匹配，如"卷积 + 归一化 + 激活" |
| kernel 来源 | 现场生成，或调用库 | 从内置的实现里选，选法是在目标 GPU 上实测计时 |
| 编译耗时 | 秒级 | 分钟到小时级 |
| 产物的可移植性 | 缓存只在本机有效 | 引擎文件绑定 GPU 型号和软件版本 |

**TensorRT 有一种融合是纯粹的常量折叠，值得单独举例。** 推理时的批归一化（BatchNorm）对每个通道做 `y = γ × (x − μ) / σ + β`，其中 γ、β、μ、σ 都是训练好的常数。如果它前面是一个卷积 `x = w * input + b`，把两式合并，得到一个新的卷积：权重是 `w × γ / σ`，偏置是 `(b − μ) × γ / σ + β`。新的权重和偏置在构建引擎时就算好，运行时批归一化这个算子完全消失，没有任何开销。这种优化只有同时看见两个相邻算子及其参数才能做，是图编译层独有信息的又一个例子。

## 9. 开发者视角

| 你想确认什么 | 怎么看 |
| --- | --- |
| 融合发生了没 | 性能时间线上 kernel 数量骤减；kernel 名字带 `fused` 字样；`TORCH_LOGS=+inductor` 直接打印融合决策 |
| 为什么没融合 | `torch._dynamo.explain()` 列出 graph break 的位置和原因 |
| 生成的 kernel 长什么样 | `TORCH_COMPILE_DEBUG=1` 导出中间产物，里面有生成的 Triton 源码 |
| 是否在反复重编译 | `TORCH_LOGS=recompiles` 打印每次重编译的原因（哪条 guard 不满足） |
| 排布是否冲突 | 时间线上转置/拷贝 kernel 的占比；显式检查张量的内存格式 |
| 显存去哪了 | PyTorch 的显存快照工具（`memory snapshot`）可视化每块显存的归属与生命周期 |
| 三个红旗信号 | 密密麻麻的小 kernel（该开 compile）；转置占比高（排布冲突）；显存"已保留"远大于"已分配"（碎片） |

## 10. 最新架构落点（知识截至 2026-08）

- **Inductor 的模板融合**日趋成熟：矩阵乘用现成模板、epilogue 自动缝合——第 4.2 节的 epilogue 融合已高度自动化。
- **低精度时代 epilogue 更关键**：fp8/fp4 的每块缩放因子读写必须并入矩阵乘 kernel，否则低精度省下的带宽被缩放张量吃回去。
- **推理引擎的定式**：vLLM/TensorRT-LLM 对固定的模型结构直接模式匹配到手写融合 kernel——图编译层的优化与 kernel 层的手工实现深度混合。
- **融合的边界被往前推了一格，但推的方式值得注意**。§4.3 的结论是"需要改数学的融合编译器做不到"。FlexAttention 加 FA-4 的组合（本模块第 4 节 §11、附录 A1）**没有推翻这条**——它的做法是**把已经被人改写好的数学（在线 softmax）做成一个骨架，让用户只填打分和掩码**。**这是把边界那一侧的成果搬到这一侧来复用，不是突破边界。** 判断任何"编译器现在也能做 X 了"的说法，用的都是这个判据：**它是发现了新数学，还是复用了已知数学？**
- **训练侧的图层优化正在和另外两件事耦合求解**。过去融合、显存规划、重计算选择是分三步各做各的；现在的方向是把三者放进同一个优化问题——**因为它们抢的是同一笔显存预算**（模块 09 第 1 节 §5 算过这笔账，本模块第 10 节 §7 讲了为什么自动微分的位置让这件事成为可能）。

## 12. 术语卡

### 算子融合（operator fusion）
**定义**：把相邻算子合并成一个 kernel，中间结果在寄存器里直接传递、不落显存。每融合掉一个中间结果，省两趟它全尺寸的显存读写。
**为什么存在**：逐元素类算子是访存受限的，时间几乎全花在中间结果的往返上——融合直接砍掉往返，是全栈性价比最高的优化。
**语境例句**："这条链 compile 后融成了一个 kernel，快了 40%。" —— 意思是：几个逐元素算子的中间结果不再落显存，流量降到原来的几分之一——访存受限负载的标准收益。

### epilogue 融合
**定义**：把矩阵乘之后的零碎操作（偏置、激活、缩放）并入矩阵乘 kernel 的写回阶段执行。
**为什么存在**：矩阵乘计算受限、写回时访存通道有空余，零碎操作并入之后不增加显存读写，成本接近于零。
**语境例句**："bias 和 gelu 都进 epilogue 了。" —— 意思是：这两个操作不再是独立 kernel，在矩阵乘写结果之前顺带完成——时间线上看不到它们了，这是好事。

### graph break
**定义**：自动抓图被打断的位置（触发者常是 print、数据相关分支、不被识别的自定义算子）。图被切成两段，跨断点的融合机会全部丢失。
**为什么存在**（作为现象）：抓图机制只能处理"可静态化"的代码，遇到必须真执行才知道结果的东西就得停下——这是动态语言的灵活性带来的代价。
**语境例句**："先跑 dynamo.explain 看看 break 在哪。" —— 意思是：融合效果不如预期时，第一件事是找出图在哪断了、为什么断——常常挪走一行日志打印就能连上。

### guard（编译结果的适用条件）
**定义**：抓图时记录下来的一组假设，例如输入的形状、数据类型、某个 Python 变量的值。编译结果和这组假设一起缓存，每次调用前先检查假设是否仍然成立。
**为什么存在**：编译器针对具体的形状和类型生成代码，换了形状这份代码就可能不正确。guard 保证缓存的代码只在它适用的条件下被使用。
**语境例句**："日志里全是 recompile，guard 一直在失败。" —— 意思是：输入的某个属性每次调用都在变（多半是形状），导致每次都重新编译——应该把形状归并到少数几种。

### 数据排布（layout）与排布传播
**定义**：张量在内存里的存放顺序，及编译器在全图上统筹"谁转置、谁将就"使总转置成本最小的优化。
**为什么存在**：排布决定访存能否合并、能否直接喂进矩阵指令；而局部最优的排布选择会让转置在图里传染——必须全局算账。
**语境例句**："时间线上 copy 类 kernel 占了 15%。" —— 意思是：相邻算子要求的排布不一致，编译器被迫插入大量转置搬运——检查模型里有没有混用排布约定的层。

### 重计算（activation checkpointing）
**定义**：训练时丢弃中间激活、反向传播需要时从检查点重算的技术。多花约三分之一前向算力，激活显存降到几分之一。
**为什么存在**：激活显存随序列长度和模型深度暴涨，常是训练的第一瓶颈；而算力相对便宜——用便宜的换紧缺的。
**语境例句**："开了 checkpoint 才塞得下这个序列长度。" —— 意思是：显存不够时的第一个标准动作——代价是每步慢一点，换来能跑。

### 提前编译与运行时编译（AOT / JIT）
**定义**：图编译器的两种工作时机。提前编译在部署之前完成全部编译工作，产出一个可直接加载的文件；运行时编译在程序运行、真实输入到达之后才编译。
**为什么存在**：提前编译可以花很长时间搜索、运行时无开销，但必须预先知道形状；运行时编译能看到真实形状、对代码限制少，但首次调用慢、形状变化要重编译。两种需求对应不同的部署场景。
**语境例句**："引擎要在目标机器上重新 build，换了卡型号不能直接拷过去。" —— 意思是：提前编译的产物里包含了针对具体 GPU 型号挑选的 kernel，换硬件必须重新构建。
