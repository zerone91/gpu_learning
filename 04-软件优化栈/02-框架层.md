## 1. 基础词汇：先把本节要用的词讲清楚

**张量（tensor）**。框架里的基本数据对象：一个多维数组，加上一份描述信息（形状、数据类型、放在哪个设备上、是否需要求梯度）。要注意张量对象本身很小，它只是一份描述加一个指针，真正的数据放在一块单独申请的内存或显存里。

**算子（operator）**。框架定义的一个基本运算，比如矩阵乘、加法、relu。每个算子有固定的名字、固定的输入输出约定。算子是框架层和下面各层之间通用的"货物单位"：框架把模型拆成算子，下面各层负责把每个算子执行得快。

**即时执行（eager execution）**。写一行代码就立刻执行这一行对应的算子、立刻得到结果的工作方式。PyTorch 默认如此。好处是可以随时打印中间结果、用普通的 Python 调试器；代价是框架在执行某一行时，看不见后面还有哪些行。

**抓图（graph capture）**。把一段 Python 代码对应的全部算子调用先记录成一张计算图（节点是算子、边是数据依赖），整体交给编译器处理之后再执行。它和即时执行是框架的两种工作方式。

**自动微分（automatic differentiation）**。框架根据前向计算的过程，自动生成梯度计算的能力。训练时每个参数的梯度都靠它得到，用户只写前向代码。

**分发器（dispatcher）**。框架内部的一个查表机构。同一个算子名（比如矩阵乘）在不同设备、不同数据类型下有不同的实现，分发器根据输入张量的属性决定调用哪一个实现。

## 2. 这一层的档案

### 2.1 定义

**框架层是用户用来表达模型结构和训练过程的那层软件。** 它向上提供 Python 接口（张量运算、神经网络模块、优化器），向下把用户写的程序翻译成算子的序列。它自己不实现高性能的数值计算，具体的矩阵乘、卷积都交给下面的层去做。

### 2.2 为什么在这里切一刀

五层地图里每一刀的位置都有理由。框架层和下面的图编译层之间这一刀，有三个理由。

**理由一：使用者不同。** 框架层的用户是算法工程师，他们关心模型结构和实验效率；下面各层的用户是性能工程师和编译器工程师。把接口切在这里，算法工程师可以完全不了解 GPU 而写出能跑的模型。

**理由二：这一层握有别处拿不到的信息。** 框架层知道哪些张量需要梯度、现在是训练还是推理、模型由哪些模块组成、用户希望用什么精度计算。这些信息统称**训练语义**。它们在交给下一层时大部分会被丢弃，所以依赖这些信息的功能（自动微分、混合精度策略、参数管理）只能放在这一层。

**理由三：上下两侧的变化速度不同。** 模型结构每周都有人提出新的，硬件和 kernel 的更新周期以年计。中间用一个相对稳定的**算子集**隔开之后，新模型只要能拆成现有的算子就能直接运行，新硬件只要实现了这批算子就能运行所有模型。

### 2.3 输入与输出

| | 内容 |
| --- | --- |
| **输入** | 用户的 Python 程序（模型定义、训练循环）和数据 |
| **输出（出口 A）** | 一次一次的算子调用，每次调用立刻执行 |
| **输出（出口 B）** | 一张计算图，交给图编译层 |

**这一层有两个出口，这一点决定了五层地图并不是一条直线。** 走出口 A（即时执行）时，每个算子调用经过分发器，直接找到一个事先写好的 kernel（属于第③层的算子库），再经第⑤层运行时提交给 GPU，**第②层图编译层被整个跳过**。走出口 B（抓图）时，计算图交给第②层，经过融合等优化之后再往下走。第 1 节说 GPU 软件栈里"图编译是可选的加速档"，指的就是存在出口 A 这条不经过编译的通路。

### 2.4 上下边界的接口

**上边界**是 Python 接口，对 PyTorch 来说就是 `torch.Tensor` 的方法、`torch.nn` 里的模块、`torch.optim` 里的优化器。这套接口的稳定性是框架的核心资产，用户代码依赖它。

**下边界**按两个出口分别有一套接口：

| 出口 | 接口形态 | PyTorch 里的具体名字 | 接到哪一层 |
| --- | --- | --- | --- |
| A：逐算子执行 | 算子的函数签名，加上按设备注册的实现 | ATen 算子库（约两千个算子，每个算子对各设备分别注册实现） | 第③层的预制 kernel，经第⑤层启动 |
| B：整图交付 | 一种图格式的中间表示 | FX 图、`torch.export` 导出的程序；跨框架的有 ONNX、StableHLO | 第②层图编译层 |

**下边界的核心是算子集的定义。** 框架层负责规定"有哪些算子、每个算子的语义是什么"，下层负责实现。算子集越大，用户写起来越方便，但每个新硬件要实现的东西越多。所以 PyTorch 在约两千个算子之外又定义了一个只有约两百个算子的**核心算子集**，其余算子都能分解成核心算子的组合，编译器和新硬件后端只需要支持核心集。

**例子：一个算子的分解。** 激活函数 SiLU 的定义是 `silu(x) = x × sigmoid(x)`。它在完整算子集里是一个独立的算子，但不在核心算子集里。某个新硬件的后端没有实现 SiLU，模型里却用到了它。框架在把图交给这个后端之前，先按登记好的分解规则把 `silu(x)` 换成两个核心算子：先算 `sigmoid(x)`，再和 `x` 相乘。后端只要实现了 sigmoid 和乘法，这个模型就能运行。后端少写了一个算子的实现，代价是原本一个 kernel 完成的事变成了两个 kernel，能否重新合并成一个要看下一层的融合。

### 2.5 这一层看得见什么、看不见什么

按第 1 节"信息衰减"的说法，每一层能做的事由它看得见的信息决定。

| 看得见 | 看不见 |
| --- | --- |
| 整个模型的结构、模块层次 | 算子内部的循环怎么展开 |
| 哪些张量要求梯度、训练还是推理 | 数据在片上存储里怎么放 |
| Python 的控制流（if、for） | 每个线程用了几个寄存器 |
| 用户指定的精度策略、随机数种子 | 某个 kernel 实际跑了多久（除非用工具测） |

## 3. 功能集合：这一层要做的七件事

| 功能 | 做什么 | 为什么只能在这一层做 |
| --- | --- | --- |
| **张量抽象** | 管理形状、数据类型、设备、视图关系 | 这是用户直接操作的对象，接口属于框架 |
| **算子分发** | 按设备、数据类型、是否求梯度，为每次调用选出具体实现 | 只有这一层同时知道调用者的意图和张量的属性 |
| **自动微分** | 记录前向过程，生成反向计算 | 需要知道哪些张量要求梯度，属于训练语义 |
| **混合精度策略** | 决定每个算子用 bf16 还是 fp32 计算 | 哪些算子对精度敏感是算法知识，下层无从判断 |
| **模块与参数管理** | 组织参数、保存和加载权重、在设备间移动 | 模块层次只存在于这一层 |
| **抓图与导出** | 把 Python 程序记录成计算图 | Python 的执行过程只有这一层能观察到 |
| **数据管道与训练外围** | 数据加载、优化器、学习率调度、分布式训练的封装 | 属于训练流程，和单个算子无关 |

**对"张量抽象"举一个能算的例子。** 一个形状为 4096×4096 的 bf16 张量，数据占 4096×4096×2 字节，约 32 MB。对它做转置 `x.T`，框架**不复制这 32 MB 数据**，只新建一个张量对象，让它指向同一块数据，并把两个维度的步长互换。这个新对象只有几百字节。这种共享数据的张量叫**视图**。它带来的后果要记住：转置之后的张量在内存里不再是连续排列的，后面的算子如果需要连续内存，就必须真的复制一次（`contiguous()`），那次复制才花掉 32 MB 的读写。**框架层的很多操作只改描述、不动数据，真正的搬运被推迟到某个要求连续内存的算子出现时才发生。**

## 4. 业界的典型项目

| 项目 | 主导方 | 默认工作方式 | 交给下层的图格式 | 特点 |
| --- | --- | --- | --- | --- |
| **PyTorch** | Meta 发起，现属 Linux 基金会 | 即时执行，可选 `torch.compile` 抓图 | FX 图 / ATen 算子 | 研究和生产的主流；出口 A、B 并存 |
| **JAX** | Google | 函数变换，`jit` 之后整体编译 | jaxpr，再转 StableHLO | 纯函数风格；和 XLA 编译器、TPU 结合最紧 |
| **TensorFlow** | Google | 2.x 起默认即时执行，`tf.function` 抓图 | GraphDef / StableHLO | 部署工具链完整，存量系统多 |
| **MindSpore** | 华为 | 图模式与动态图模式并存 | MindIR | 昇腾芯片的原生框架 |
| **PaddlePaddle** | 百度 | 动态图为主，可转静态图 | PIR | 国内产业应用多 |
| **MLX** | Apple | 即时执行，惰性求值 | 内部图 | 面向 Apple 芯片的统一内存架构 |

**读这张表的方法是看"默认工作方式"这一列。** 它决定了框架把多少信息留给下层的编译器：默认抓图的框架（JAX 在 `jit` 之后、MindSpore 的图模式）总是把完整的图交下去，编译器能做全局优化，但用户代码要遵守更多限制；默认即时执行的框架（PyTorch）对用户代码几乎没有限制，但要主动开启编译才能享受图层优化。

**例子：同一行代码在三种方式下的遭遇。** 代码是 `if x.sum() > 0: y = x * 2`，分支走不走取决于张量里的数值。在 PyTorch 的即时执行下，`x.sum()` 立刻被算出来，取回 CPU 做比较，分支照常执行，没有任何问题（只是多了一次等待 GPU 的同步）。在 `torch.compile` 下，抓图进行到这一行时无法确定走哪个分支，图在这里被切成两段分别编译。在 JAX 的 `jit` 下，这一行直接报错，必须改写成 `jnp.where(x.sum() > 0, x * 2, y)` 这样不含 Python 分支的形式。三种处理方式对应表中三种"默认工作方式"：越偏向编译的框架，对这类代码的限制越严格。

## 5. 拿 PyTorch 讲透（一）：一次 `x @ W` 调用经过的六站

这一小节跟踪一次最普通的矩阵乘调用，看框架在真正开始计算之前做了什么。设定：`x` 和 `W` 都是 GPU 上的 bf16 张量，`W` 是需要梯度的参数，代码运行在混合精度上下文里。

```python
with torch.autocast("cuda", dtype=torch.bfloat16):
    t1 = x @ W
```

**第 1 站：Python 绑定。** `@` 运算符被 Python 解释器翻译成对 `torch.matmul` 的调用。绑定代码把 Python 对象形式的参数解析成 C++ 的张量对象，然后进入 C++ 一侧。这一站之后，Python 解释器暂时不再参与。

**第 2 站：分发器计算"要经过哪些处理环节"。** 每个张量身上带着一组标记，说明它有哪些属性：在 CUDA 设备上、需要求梯度等等；当前线程的上下文里还有一组标记，比如"混合精度已开启"。分发器把输入张量的标记和上下文的标记合并，得到这次调用要依次经过的处理环节。本例合并的结果是三个环节：混合精度、自动微分、CUDA 后端。

**第 3 站：混合精度环节。** 这个环节检查矩阵乘是否属于"适合用低精度计算"的算子（矩阵乘属于），并把输入转换成 bf16。本例输入已经是 bf16，所以不做任何事，直接把调用转给下一个环节。

**第 4 站：自动微分环节。** 这个环节先把调用转给下一个环节，拿到结果之后，新建一个**反向节点**挂在结果张量上。反向节点里记录两样东西：将来求梯度要用的公式（矩阵乘的梯度是另外两次矩阵乘），以及公式里要用到的前向数据（本例是 `x` 和 `W` 的引用）。

**第 5 站：CUDA 后端环节。** 这是真正安排计算的地方。它做三件事：根据输入形状算出输出形状；向显存分配器申请输出所需的显存；调用算子库（矩阵乘调用的是 cuBLAS）。

**第 6 站：算子库提交 kernel。** cuBLAS 根据形状和数据类型挑选一个内部实现，通过运行时把 kernel 启动命令提交给 GPU。提交是异步的，CPU 这边不等 GPU 算完就返回。控制权一路返回到 Python，`t1` 拿到一个结果张量，而这个张量里的数据此刻可能还没算出来。

**把六站的时间加起来，得到一笔重要的账。** 第 1 到第 5 站加上第 6 站的提交动作，全部是 CPU 上的工作，合计是几微秒到十几微秒的量级。这笔开销和张量大小无关，每次算子调用都要付一次。它是否要紧，取决于 kernel 本身跑多久：

| 场景 | kernel 执行时间 | 框架的固定开销（按 10 微秒计） | 开销占比 |
| --- | --- | --- | --- |
| 4096×4096 的矩阵乘 | 约几毫秒 | 10 微秒 | 不到 1% |
| 对 1000 个元素做一次加法 | 约 10 微秒 | 10 微秒 | 约 50% |

**结论是：大算子的时间几乎全花在 GPU 上，框架开销可以忽略；大量小算子连续调用时，CPU 上的框架开销会和 GPU 计算时间一样大，甚至成为瓶颈。** 推理的解码阶段正是后一种情况（每步几百个小算子），所以才需要第②层的融合（减少算子个数）和第⑤层的 CUDA Graph（把一串启动录制下来重放）来消除这笔开销。

还要注意第 6 站的异步性带来的一个常见误会。**用 Python 的计时函数直接包住一行 GPU 代码，量到的只是前面这六站的 CPU 时间，GPU 上的计算时间没有被计入。** 要量真实时间，必须在计时结束前调用 `torch.cuda.synchronize()` 等 GPU 把已提交的工作做完，或者直接用性能分析工具。

## 6. 拿 PyTorch 讲透（二）：反向图是怎么记下来的

上一小节第 4 站提到每次调用会挂一个反向节点。这一小节看三个算子连起来之后，这些节点组成了什么，以及它们占了多少显存。

**设定**：`x` 的形状是 8192×4096（8192 个 token，隐藏维度 4096），bf16，一个这样的张量占 8192×4096×2 字节，即 64 MB。计算 `y = relu(x @ W + b)`，拆成三步：

```python
t1 = x @ W        # 矩阵乘
t2 = t1 + b       # 加偏置
y  = torch.relu(t2)
```

**每一步执行之后，自动微分记下了什么：**

| 步骤 | 挂上的反向节点 | 反向公式需要的前向数据 | 因此被保留的张量 |
| --- | --- | --- | --- |
| `t1 = x @ W` | 矩阵乘的反向 | 求 `W` 的梯度要用 `x`，求 `x` 的梯度要用 `W` | `x`（64 MB）、`W` |
| `t2 = t1 + b` | 加法的反向 | 加法的梯度就是把上游梯度原样传下去，不需要前向数据 | 无 |
| `y = relu(t2)` | relu 的反向 | 需要知道哪些位置大于零，从输出 `y` 就能看出来 | `y`（64 MB） |

三个反向节点之间用指针连起来：`y` 的节点指向 `t2` 的节点，`t2` 的节点指向 `t1` 的节点。**这条链就是反向图。** 调用 `loss.backward()` 时，框架从末端出发沿着这条链往回走，每到一个节点就执行它的反向公式。

**现在算显存。** 三步计算产生了三个 64 MB 的张量 `t1`、`t2`、`y`。其中 `t1` 和 `t2` 没有被任何反向节点保留，Python 变量一旦不再引用它们，显存立刻归还。`y` 被 relu 的反向节点保留，`x` 被矩阵乘的反向节点保留，这两个要一直留到反向传播执行完。所以这一层在训练时**长期占用**的激活显存是 2 个张量共 128 MB，而不是直觉上以为的 3 个或 4 个。

**把这个例子推广到整个模型，就得到训练显存的主要来源。** 一个有几十层的模型，每层都有若干个张量因为反向公式需要而被保留，合起来就是训练时的激活显存，它经常超过权重本身占用的显存。而在推理时，用 `torch.no_grad()` 关掉自动微分，第 4 站整个被跳过，没有任何张量因为反向而保留，显存占用大幅下降。**"哪些中间结果必须保留"这个信息只有框架层掌握，这是自动微分只能放在这一层（或紧挨着它的位置）的原因。**

这个例子还解释了一个实践中常见的现象：训练循环里把 `loss` 直接累加到一个 Python 变量里（`total += loss`），显存会越涨越高。原因是 `loss` 张量身上挂着整条反向图的末端节点，只要 `loss` 还被引用，整条链上所有被保留的张量都不能释放。正确的写法是 `total += loss.item()`，只取出数值，不保留张量。

## 7. 同一层的另一种设计：JAX 的函数变换

PyTorch 和 JAX 完成的是同一层的职责，但做法不同，对照起来能看清这一层的设计空间。

**PyTorch 的做法是"边执行边记录"。** 每个算子立刻执行，同时自动微分在旁边记下反向节点。用户代码可以是任意的 Python。

**JAX 的做法是"先变换函数，再执行"。** 用户把计算写成一个没有副作用的 Python 函数，然后用框架提供的变换去处理这个函数：`jax.grad(f)` 返回一个计算 `f` 的梯度的新函数，`jax.jit(f)` 返回一个经过编译的新函数。变换的实现方式是用一种特殊的占位对象代替真实数据去调用 `f` 一遍，记录下 `f` 对它们做了哪些运算，得到一份叫 jaxpr 的中间表示，然后交给 XLA 编译器。

**同一个计算的两种写法对照：**

```python
# PyTorch：边执行边记录
y = torch.relu(x @ W + b)
loss = y.sum()
loss.backward()            # 沿着记录下来的反向图往回走
g = W.grad

# JAX：先变换函数，再执行
def f(W, b, x):
    return jnp.maximum(x @ W + b, 0).sum()
g = jax.jit(jax.grad(f))(W, b, x)   # 求导和编译都是对函数的变换
```

| | PyTorch | JAX |
| --- | --- | --- |
| 默认出口 | 出口 A（逐算子执行） | `jit` 之后走出口 B（整图编译） |
| 用户代码的限制 | 几乎没有 | 函数不能有副作用；依赖张量数值的 Python 分支不能直接写 |
| 编译器拿到的信息 | 默认没有图；开启 `torch.compile` 后才有 | 总是完整的图 |
| 随机数 | 全局的随机数状态 | 必须显式传递随机数密钥 |
| 调试体验 | 随时打印、随时断点 | 编译后的函数内部不能直接打印 |

**两者的取舍可以用一句话概括：PyTorch 把灵活性放在默认位置，性能需要主动开启；JAX 把可编译性放在默认位置，灵活性需要用户遵守约束来换取。** 这和第 1 节讲的"GPU 栈运行时偏重、TPU 栈编译期偏重"是同一个取舍在框架层的体现。

## 8. 开发者视角

| 你想知道或控制什么 | 去哪里看或怎么做 |
| --- | --- |
| 某一行实际调用了哪些算子 | `torch.profiler` 的算子视图，列出每个算子的调用次数和耗时 |
| 框架开销占了多少 | 性能时间线上对比 CPU 侧算子的时长和它启动的 kernel 的时长；两者接近说明框架开销已经不可忽略 |
| 一个张量是不是视图、内存是否连续 | `x.is_contiguous()`；`x.data_ptr()` 相同说明共享数据 |
| 反向图长什么样 | 沿着 `y.grad_fn`、`y.grad_fn.next_functions` 逐级查看 |
| 显存为什么不释放 | 检查是否有张量带着反向图被长期引用；推理代码是否漏了 `torch.no_grad()` |
| 混合精度是否生效 | 在时间线上看矩阵乘 kernel 的名字和数据类型；检查 `autocast` 的作用范围 |
| 计时是否准确 | 计时结束前调用 `torch.cuda.synchronize()` |

**三个红旗信号**：性能时间线上 CPU 侧的算子条比 GPU 侧的 kernel 条还长（框架开销成了瓶颈）；显存占用随训练步数持续上涨（反向图被意外保留）；时间线上出现大量来回转换数据类型的 kernel（混合精度的范围设得不对，或者某个算子被强制回退到 fp32）。

## 9. 最新架构落点（知识截至 2026-08）

- **PyTorch 的两个出口都在被加强。** 出口 B 一侧，`torch.compile` 已是主线功能，`torch.export` 提供了面向部署的整图导出；出口 A 一侧，分发器和 Python 绑定的固定开销持续被压缩。对用户的含义是：默认写法仍然是即时执行，性能需求出现时再切换到出口 B。
- **核心算子集成为硬件后端的准入门槛。** 新的硬件后端和推理引擎越来越多地只对接那约两百个核心算子，其余算子靠分解得到。判断一个新硬件的软件成熟度时，可以直接问它对核心算子集的覆盖率。
- **跨框架的图格式在向 StableHLO 和 ONNX 两家集中。** JAX 和 TensorFlow 输出 StableHLO，PyTorch 也有到 StableHLO 的转换路径；ONNX 仍是推理部署一侧的通用格式。
- **大模型推理引擎在绕开框架层的一部分。** vLLM、TensorRT-LLM 这类引擎仍用框架加载权重和表达模型，但解码循环、批处理调度、KV 缓存管理都由引擎自己实现（模块 09 第 2 节）。原因正是第 5 节算过的那笔账：解码阶段全是小算子，框架的固定开销占比过高。
- **国产芯片的框架层有两条路线并存。** 一条是原生框架（MindSpore 对昇腾），另一条是给 PyTorch 写后端插件（`torch_npu` 一类）。后一条路线的工作量主要就在第 2.4 节说的算子集覆盖上。

## 11. 术语卡

### 分发器（dispatcher）
**定义**：框架内部按张量属性和当前上下文，为每次算子调用选择具体实现的查表机构。一次调用通常要依次经过几个处理环节（混合精度、自动微分、设备后端），每个环节做完自己的事再转给下一个。
**为什么存在**：同一个算子在不同设备、不同数据类型、是否求梯度的情况下，要做的事各不相同。没有分发器，每个算子的实现里就要写满条件判断；有了它，每种功能可以独立注册，新硬件后端只需注册自己那一列实现。
**语境例句**："这个算子在 NPU 后端没注册，回退到 CPU 了。" —— 意思是：分发器在目标设备上找不到这个算子的实现，只好把数据搬回 CPU 计算再搬回去，这一来一回的搬运会让这一步慢很多。

### 即时执行与抓图（eager / graph capture）
**定义**：框架的两种工作方式。即时执行是每行代码立刻运行对应的算子；抓图是先把一段程序记录成计算图，编译优化之后再运行。
**为什么存在**：即时执行便于调试但没有全局视野，抓图能做全局优化但对代码有限制。两种需求都真实存在，所以主流框架两种方式都提供。
**语境例句**："eager 下能跑，一 compile 就报错。" —— 意思是：代码里有抓图机制处理不了的写法（比如依赖张量数值的分支），即时执行时不受影响，抓图时才暴露。

### 反向图与反向节点（autograd graph）
**定义**：自动微分在前向计算时记录下来的数据结构。每次算子调用产生一个反向节点，里面有求梯度的公式和公式需要的前向数据；节点之间按数据依赖连成一条链，反向传播就是沿着这条链往回走。
**为什么存在**：梯度的计算需要前向过程中的部分中间结果，必须有一个地方记住"需要哪些、它们在哪"。这份记录同时也是训练显存的主要来源。
**语境例句**："显存一直涨，八成是哪里把带着图的张量存起来了。" —— 意思是：某个挂着反向节点的张量被长期引用，导致整条链上保留的中间结果都释放不掉。

### 算子集与核心算子集（opset）
**定义**：框架规定的全部算子及其语义的集合。PyTorch 的完整算子集约两千个，其中约两百个被指定为核心算子，其余算子都可以分解为核心算子的组合。
**为什么存在**：算子集是框架层和下层之间的合同。合同条目太多，新硬件的接入成本高；核心算子集把必须实现的条目压到最少，其余靠分解自动得到。
**语境例句**："他们的后端只支持 core ATen，别的靠 decomposition。" —— 意思是：这个后端只实现了核心算子，其他算子在进入后端之前先被框架拆成核心算子的组合。

### 视图（view）
**定义**：和另一个张量共享同一块数据、只是形状或步长不同的张量。转置、切片、改变形状在大多数情况下产生视图，不复制数据。
**为什么存在**：复制数据是昂贵的搬运。只改描述不动数据，让这些高频操作的代价接近于零。
**语境例句**："permute 之后记得 contiguous，不然后面的 view 会报错。" —— 意思是：转置之后的张量在内存里不连续，某些操作要求连续内存，需要先真的复制一次。

### 混合精度上下文（autocast）
**定义**：框架提供的一个作用范围。在这个范围内，框架按预先设定的名单，自动让适合低精度的算子用 bf16 或 fp16 计算，让对精度敏感的算子保持 fp32。
**为什么存在**：低精度计算更快、更省显存，但并非所有算子都能承受。哪些能、哪些不能是算法层面的知识，由框架层维护一份名单统一处理，用户不必逐个算子指定。
**语境例句**："这个 loss 在 autocast 里算出了 nan，把它挪到外面。" —— 意思是：损失函数里有对精度敏感的运算，在低精度下溢出了，应该让它在 fp32 下计算。
