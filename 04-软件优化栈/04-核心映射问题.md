# 核心的映射问题（整个计划的收束点）

> **所属模块**：模块 04 · 软件优化栈 ⭐ 收束点
> **状态**：🟨 学习中（第一版，知识截至 2026-01）
> **一句话主旨**：全库所有内容收拢成一个问题——**映射（mapping）：把一个嵌套循环（算子）的每一次迭代，安排到硬件的某个计算单元、某个时刻、某级存储上**。它只有四个决策维度（**切多大 / 什么顺序 / 数据放哪 / 谁来算**），SIMT 和脉动阵列只是这四个决策"由谁做、何时做"不同；而所有优化目标最终折叠成一句话：**在"装得下"的约束内，让最贵的那个资源（Tensor pipe / 阵列 / 带宽）永不空转**。

## 1. 映射的定义：四个决策维度

任何算子本质是个**嵌套循环**。matmul 就是：

```
for i in M: for j in N: for k in K:   C[i,j] += A[i,k] * B[k,j]
```

**映射 = 回答四个问题**（这就是 mapper/Timeloop 的形式化，02-03 提过）：

| 维度 | 问题 | 例 |
| --- | --- | --- |
| **① tiling（切分）** | 每层循环切成多大的块？ | BLOCK_M/N/K、阵列的 128 |
| **② ordering（顺序）** | 块间/块内按什么顺序走？ | K 内积序 vs split-K、输出行优先 vs swizzle 序 |
| **③ placement（放置）** | 每块数据驻留在哪级存储？ | A 进 shared、C 驻寄存器/TMEM——**即数据流选择** |
| **④ binding（绑定）** | 哪个计算单元算哪块？ | block→SM、warp→tile 行、PE(i,j)→c[i,j] |

> 🔑 **全库统一点之一**：02-03 §1.4 的承诺兑现——**GPU 的 tiling+"谁放哪级存储" 与脉动阵列的 stationary 数据流，是同一个 ③placement 决策的两种表达**：GPU 用存储层级（寄存器/shared/L2）写答案，脉动阵列用物理位置（PE 内/电线上/buffer）写答案。**"调度"（04-03）= 映射的③层叫法；"数据流"（02-03）= 映射的硬件叫法。一个问题，三个名字。**

## 2. 走一遍：matmul → GPU（六层分解）

`M=N=K=8192, bf16, H100` 从上往下每层做一次"切+绑"：

```
层级         切分决策                         绑定到              本库出处
──────────────────────────────────────────────────────────────────────
L1 grid      C 切成 128×256 的输出 tile       每 tile → 1 个 block  §01-02 占用率
             (8192/128)×(8192/256)=2048 块    → 132 个 SM 轮流领
             ② ordering: tile 按 L2-友好的
             swizzle 序发放（相邻块共享 A/B 行列→L2 命中）
──────────────────────────────────────────────────────────────────────
L2 K 循环    K 切成 64 一段，块内顺序累加      时间维（流水）        §02-04 tiling不等式
             ③ A(128×64)、B(64×256) tile
             → TMA 搬进 shared（双缓冲/num_stages=3）
──────────────────────────────────────────────────────────────────────
L3 block 内  128×256 再切给 2 个 warpgroup     每 warpgroup 一半     A2 §1.7
             ④ 生产者 warp 管 TMA，
             消费者 warpgroup 跑 wgmma（专化）
──────────────────────────────────────────────────────────────────────
L4 warpgroup wgmma 指令粒度 m64n256k16         Tensor Core           §03-01
             ③ C 累加器驻寄存器/TMEM（=OS 数据流！）
──────────────────────────────────────────────────────────────────────
L5 指令内    16×8×16 的 MMA 原子               TC 内部点积树         §03-01（黑盒）
──────────────────────────────────────────────────────────────────────
L6 收尾      epilogue（bias/激活）搭写回便车    LSU                  04-02
```

**验收账**（全是学过的判据）：AI≈1370≫300 → Tensor-bound ✅（A1）；shared 用量 vs 占用率 vs num_stages 三方分预算 ✅（§01-02）；C 驻留 = output-stationary ✅（02-03）；tile 对齐 → 无形状税 ✅（02-05）。

## 3. 同一个 matmul → 脉动阵列（TPU 式）

四个决策还在，但**大半提前到了设计期/编译期**：

| 决策 | GPU（运行时+③层软件） | 脉动阵列（设计期+②层编译器） |
| --- | --- | --- |
| ① tiling | autotune 搜 BLOCK_* | **外层由 XLA 定**（按 SRAM 容量），**最内层 128×128 焊死在硅片** |
| ② ordering | swizzle 序、split-K 可调 | 编译器排静态时刻表（§02-02 闭式公式） |
| ③ placement | 每 kernel 自选（shared/寄存器） | **焊死**：W 钉 PE（WS）、psum 走列线、激活走行线 |
| ④ binding | block→SM 动态领取 | **焊死**：c[i,j] 的第 k 份就在 PE 经过的那一拍 |

> 🔑 **一句话**：**脉动阵列 = 一个把 ③④ 焊死、②大半焊死、只留 ① 外层给编译器的"预制映射"**。它快，因为四个决策里三个不用再做；它死板，因为那三个决策改不了（形状税、§02-05）。**GPU 与 NPU 的全部差异 = 映射决策的"冻结时刻"不同**——这就是 00 分水岭（"谁先谁后何时定"）在映射语言下的复述。

## 4. attention 的映射：FA 到底"对"在哪

attention = `GEMM → softmax(行归约) → GEMM`，难点：**归约把两个 GEMM 隔开**（04-02：归约是融合的天然分界）。三种映射的对比：

| 映射方案 | ③placement 决策 | 结果 |
| --- | --- | --- |
| naive | S(N×N) 放 **HBM** | AI≈个位数 → HBM-bound（A2） |
| 只融 softmax | S 仍落 HBM 两次 | 略好，仍 memory-bound |
| **FlashAttention** | **S 的 tile 只活在 shared/寄存器**——用 online softmax 改写数学，让归约可分块 | AI≈N/2 → Tensor-bound（A2） |

> **FA 的本质（映射语言）**：它没有发明新计算，而是**为"S 永不落 HBM"这个 placement 目标，反向修改了 ordering（K/V 分块流式）和数学（online 归约）**。普通映射是"给定计算找最优放置"；FA 是"**给定放置目标，改写计算来配合**"——这就是它超出编译器能力（04-02）、必须人肉走私（04-01）的原因。FA3/FA4 后续所有演化（ping-pong、软件 exp）都只是在这个映射骨架上继续榨 ②ordering 和 ④binding（A1(04) 附录）。

## 5. 映射在优化什么：统一目标函数

四个决策维度，一个目标：

> **min 总时间 ≈ max(最贵资源的忙碌时间, 各级带宽的搬运时间)
> s.t. 每级存储"装得下"（②02-04 不等式）、形状税与 wave 量化已计入（02-05/A1）**

展开即全库反复用过的三步：
1. **先判 bound**（A1）：AI vs 各 pipe 平衡点 → 目标资源是 Tensor pipe 还是 HBM 还是别的；
2. **placement 造复用**（§01-04/02-03/02-04）：tiling+数据流把 AI 抬到目标 pipe 的平衡点之上；
3. **ordering+binding 藏延迟**（§01-02/A1(04)）：流水/专化/重叠让目标资源永不空转——从 ILP 到 TBO，五层同一配方。

**全库至此闭环**：硬件篇（01–03）给出"资源和代价的地图"，软件篇（04）给出"在地图上做四维决策的方法"，映射问题是两者的交点。

## 6. 开发者视角：映射思维的日常用法

拿到任何一个"XX 算子慢"的问题，四步映射体检（全是前文工具）：
1. **这算子的循环长什么样、AI 多少？**（A1 手算）→ 定目标资源
2. **现在的映射把数据放哪了？**（profiler：HBM 流量、L2/shared 命中）→ ③placement 对不对
3. **切分和顺序合理吗？**（tile 对齐？形状税？split-K 该开吗？）→ ①②
4. **目标资源在空转吗？为什么？**（SOL + stall 分解）→ ④binding/流水问题

反向也成立（看方案时）：**任何 kernel/编译器方案的宣传点，都能翻译回"它改了四维里的哪一维"**——"我们用了 persistent kernel"=改④binding；"我们上了 FP8"=改目标资源的平衡点；"我们重排了 tile 顺序提升 L2 命中"=改②ordering。**这是"顺畅对话"的终极形态：把黑话实时翻译成映射决策。**

## 7. 最新架构落点（时效锚点 · 知识截至 2026-01）

- **映射自动化的前沿**：Timeloop/MAESTRO（NPU 侧穷搜+能量模型）、Triton autotune（③层实测搜）、Inductor max-autotune、TVM Ansor（cost model）——**没有一家能全自动做 FA 级的"改数学配合放置"**，那仍是人的疆域。
- **硬件在替映射"减维"**：TMA（②搬运顺序交给引擎）、TMEM（③累加器放置定型）、cluster/DSM（④binding 多一层）、tcgen05 单线程发起——**每代硬件都在把常用映射决策固化成器件**，光谱持续右移。
- **NPU 侧**：XLA/CANN 的映射全在②层编译期；DaVinci 的 TIK/AscendC 把 placement 暴露给程序员（手动挡映射）。
