## 1. 基础词汇：先把本节要用的词讲清楚

**布局（layout）**。一个多维张量是逻辑概念，内存是一维的字节序列——布局就是"逻辑坐标 → 物理地址"的那个映射函数。最简单的两种：行主序（同一行的元素连续存放）和列主序（同一列连续）。要记住的立场：**布局改变的只是"谁挨着谁"，不改变任何数值**——但"谁挨着谁"恰恰决定了上一节讲的每一级切分（通道/slice/bank）怎么接待这批数据。

**切分（tiling）**。当数据比某级存储大，把它切成能装下的小块、分批过境的策略。和布局的分工一句话说清：**切分决定"哪批数据什么时候在这一级"，布局决定"在的这段时间里它怎么摆"**——一个管时间，一个管空间。两者在 tile 的边界上相遇（第 5 部分）。

**fragment（片段）**。Tensor Core 指令要求参与的 32 个（或 128 个）线程**各自持有矩阵的固定几个元素**，每个线程手里那份叫它的 fragment。关键在"固定"二字：哪个线程拿哪个元素是**指令规格书写死的**，软件没有商量余地——它是本节整条约束链的源头。

**`ldmatrix`**。一条专为喂 Tensor Core 设计的 shared→寄存器搬运指令：一个 warp 执行一条，就把若干个 8×8 的小矩阵按 fragment 的分布规则搬齐——每个线程提供一行的地址，硬件负责把数据**重新分发**到正确线程的寄存器里。它是"shared 里的摆法"和"寄存器里的分布"之间的转换器。

**swizzle（换座位）**。对 shared memory 布局做异或置换、让按行按列访问都不撞 bank 的技巧，01 模块第 4 节已详解。本节只用它的结论：swizzle 有几种标准模式（按置换周期叫 32 字节 / 64 字节 / 128 字节模式），**选哪种不是自由的**——马上会看到它被谁规定。

## 2. 立论：布局是约束满足问题的解

先把反方立场说清楚，因为它很常见：布局常被当成"逻辑上的维度变换"——`transpose`、`reshape`、`permute`，仿佛换个下标顺序而已。这个理解在框架层（PyTorch 的视图操作）是对的，但往下一层就失效了，用一个最小的对照实验说明：

同一个 128×128 的 bf16 矩阵放进 shared memory，两种"逻辑上等价"的摆法——直排（行主序）和 128 字节 swizzle。逻辑上没有任何区别：同样的元素、同样的行列语义，读它的代码都用 `(row, col)` 坐标。物理上天差地别：Tensor Core 的取数指令按列成组地要数据时，直排版一列 32 个元素全落在同一个 bank（01-04 算过的 32 路冲突，32 拍），swizzle 版散在 32 个 bank（1 拍）——**32 倍的差距，而"逻辑维度"一个字没变**。

所以本节的立论是：**布局的每个自由度都被上一节的某条物理切分盯着**——全局层的摆法被通道交织和 sector 粒度盯着，shared 层被 32 个 bank 盯着，寄存器层被 fragment 规格盯着。"选布局"的真实含义是：**在这些约束的交集里找一个全部满足的方案**。约束最硬的一条来自计算指令本身，下面从它开始，把约束怎么层层向外传导走一遍。

## 3. 约束传导链：从一条 mma 指令倒推出全部摆法

以最常用的一条 Tensor Core 指令 `mma.sync.m16n8k16`（16×8 输出、深度 16，bf16 输入）为例，从里往外走四步：

**第一步：指令立法——寄存器层的分布没得选。** PTX 文档为这条指令规定了精确的分布：16×8 的累加器 tile 拆到 32 个线程，**每个线程持有 4 个元素、位置由线程号唯一确定**（比如 0 号线程拿第 0 行和第 8 行的头两列——具体坐标查规格书，形式是死的）。为什么硬件要规定死？模块 03 讲过根源：Tensor Core 的乘加网络和寄存器堆的物理走线是定死的电路，"哪根线接哪个寄存器"没有可编程性。**这一层软件的自由度是零**——这就是"立法"的意思。

**第二步：`ldmatrix` 定了 shared 层的访问模式。** 数据要从 shared memory 进这些指定的寄存器。逐线程 `ld.shared` 也能搬，但每个线程要的 4 个元素散在 tile 各处，地址算术繁琐且必然撞 bank。专用指令 `ldmatrix` 把这事标准化：一个 warp 一条指令搬 4 个 8×8 块，**每个线程给出一个行首地址，硬件按 fragment 规则把行里的数据分发到各线程**。于是约束传到了 shared 层：32 个线程同拍给出的 32 个行首地址，必须落在 32 个不同的 bank——**"8×8 的行们在 shared 里怎么摆才能让行首散开"，这正是 swizzle 模式要解的方程**。直排必撞（行间隔是 2 的幂，行首全对齐到同几个 bank），128 字节 swizzle 恰好是让这组地址散开的解。所以 swizzle 模式不是风格选择：**它是 `ldmatrix` 访问模式的配套解，选错模式等于没 swizzle**。

**第三步：TMA 描述符必须复述同一个 swizzle。** 数据是 TMA 从显存搬进 shared 的（上一节 §4 的矩阵表）。TMA 落位时如果按直排写、`ldmatrix` 按 swizzle 读，读出来就是错位的垃圾数据。所以 tensor map 描述符里有一个 swizzle 模式字段，**必须填写与消费侧完全一致的模式**——搬运方在替计算方提前摆好座位。B2 精读里"TMA、shared 布局、wgmma 三方必须一致，错一方要么冲突要么算错"说的就是这一环。

**第四步：全局层的摆法决定 TMA 搬得顺不顺。** TMA 按描述符里的形状步长去显存取一个 box（tile）。约束到了最外层：这个 box 在全局内存里越连续，落到上一节讲的物理切分上越舒服——连续则 sector 利用率满、地址自然散布各通道；如果全局布局让 box 的每一行都相隔很远（比如从行主序矩阵里取一个"高瘦"的列条），一次 TMA 就变成一堆离散的短段，行缓冲和通道的并行度都吃不满。**GEMM 世界的行话 "K-major / MN-major"（操作数沿哪个维连续）就是在说这件事**：A、B 矩阵选哪种主序，决定 Tensor Core 时代的 tile 取数是整段还是碎段。

四步走完，把链读一遍：**mma 规定寄存器分布 → ldmatrix 把它翻译成 shared 的访问模式 → swizzle 是该模式下不撞 bank 的解 → TMA 描述符复述这个解 → 全局布局要让 TMA 的 box 连续**。每一环都是"下游的要求决定上游的摆法"——这就是"布局从计算指令倒推"的完整含义。CuTe 的 Layout 代数（04 模块第 6 节）本质上就是把这条链变成可组合、可验证的表达式，让"每一环对上没对上"从人肉对账变成编译期检查。

## 4. 布局动物园：按层级过一遍，每种摆法在解哪条约束

### 4.1 全局内存层：为"批发粒度"和"增长方式"而摆

**AoS → SoA**（01-04 讲过，放进本节框架一句话归位）：解的是 **sector 批发约束**——32 个线程同拍访问同一字段，SoA 让这些地址连成整段。

**卷积/视觉的张量格式：NCHW、NHWC、NC/32HW32**。同一个四维激活张量（批 N、通道 C、高 H、宽 W）的三种排法，各对应一代硬件的约束：NCHW（通道维在外，同通道的像素连续）配 FP32 时代的向量化访存；**NHWC**（通道维在最内，同像素的所有通道连续）配 Tensor Core——卷积在 Tensor Core 上被算成"沿 C 维做深度 k 的矩阵乘"，C 连续正好让 mma 的 K 维取数成整段，这就是"Tensor Core 上卷积要用 channels_last"的全部原因；NC/32HW32（通道切成 32 一组、组内塞到最内层）是 INT8 时代 cuDNN 的格式，让一条 32 宽的整数点积指令一口吃下连续 32 个通道。**同一份数据三种摆法，追着三代计算指令的取数形状走**——约束链第四环的活标本。

**paged KV cache**。decode 阶段 KV cache 的难处不在读写模式而在**增长方式**：每个请求的序列边生成边变长，几百个请求同时进行、随时有人结束释放。连续布局的下场是显存碎片——为最长可能长度预留则大量浪费。vLLM 把操作系统的页表搬了过来：**KV 按固定大小的页（如 16 个 token）分配，逻辑上连续的序列物理上散落各页，一张页表做翻译**。走查一个数：某请求生成到第 700 个 token，就持有 ⌈700/16⌉ = 44 页，物理上互不相邻；attention kernel 读 KV 时多做一次页表查找。它解的约束是**显存这一级的分配与碎片**——布局动物园里唯一主要为"管理"而非"带宽"设计的成员，代价（间接寻址）换来的是并发数翻倍量级的显存利用率。

**昇腾的 NZ 分形布局**。scratchpad 世界（模块 02/05）的对应物。昇腾的 Cube 单元一口吃 16×16 的 bf16 块，MTE 搬运引擎希望每次搬的块在源内存里连续。普通行主序（昇腾叫 ND）满足不了：16×16 块的 16 行散在 16 个远处。**NZ 格式的解法：把矩阵先切成 16×16 的小块，块内行主序连续存放，块与块再按列主序排**——于是任何一个 Cube 要吃的块都是内存里连续的 512 字节，MTE 一口整段搬走。名字里的"分形"就是"块内一种序、块间另一种序"的嵌套结构。**它和 GPU 的 swizzle 是同一个问题的两种解**：都是"计算单元按块吃数 → 存储按自己的粒度供数 → 中间需要一个摆法翻译"；区别只在 GPU 把翻译做在 shared memory 的座位表上（运行时硬件换算），昇腾把翻译做在数据格式本身上（搬进 scratchpad 前就摆好）——静态世界的一贯风格：把运行时问题变成编译期/格式问题。TPU 同理，数据在 HBM 里就按 (8, 128) 的 tile 组织，对齐 VPU 的寄存器形状和 MXU 的边长。

### 4.2 shared memory 层：为 32 个 bank 而摆

padding 和 swizzle（01-04 详解）在本节框架下归位：解的都是 **bank 切分约束**，区别是 padding 用空间换（3% 浪费 + 破坏 2 的幂对齐，于是和 `ldmatrix`/TMA 的对齐要求冲突），swizzle 用一次异或换（零浪费、保对齐）——**这就是为什么进入 Tensor Core 时代 padding 基本退场**：约束链第二、三环（ldmatrix 与 TMA）都要求 2 的幂对齐，padding 直接违宪，swizzle 成为唯一解。

### 4.3 寄存器层：立法层，无摆数自由

fragment 分布由指令规定（§3 第一步），软件唯一的"布局工作"是**对齐立法**：用 `ldmatrix`/`stmatrix`/`wgmma` 描述符这些"官方翻译"指令，而不是自己手搬。手搬不是不行，是既慢（散装 LDS + 必然的 bank 冲突）又脆（换一代指令分布就变）。CuTe 的 `partition_fragment_C` 存在的意义就是把这层"没有自由"用代数表达出来，让编译器替你守法。

## 5. 布局与切分的互动：在 tile 边界上相遇

两个概念各管一摊（切分管时间、布局管空间），但在两处必然相遇：

**相遇点一：tile 的尺寸要"摆得下且摆得好"**。切分选 tile 尺寸时，除了容量约束（02 模块的两边夹逼）还要过布局关：BK 这类维度必须是 `ldmatrix`/TMA 对齐粒度（16 字节量级）的整数倍，tile 行宽要配得上 swizzle 模式的周期——所以真实 kernel 的 tile 尺寸全是 16/32/64/128 这类数，不是审美，是约束交集里就剩这些整数解。04 模块 B4 里"BK 给成 24，tl.dot 静默退化"的坑，根源即此。

**相遇点二：布局决策会沿计算图传染**（04 模块第 2 节讲过的"转置传染"，在此归位）：上游算子选了 NHWC，下游算子要么跟着 NHWC、要么插一次物理重排——重排就是一次全量搬运，按上一节的账本要过整条 HBM 通道。所以框架的布局传播优化本质是：**在计算图尺度上求"全图重排次数最少"的布局指派**——约束满足问题从单 kernel 放大到了整张图。

## 6. 软件怎么表达这些决策（对应 04 模块第 6 节的海拔轴）

| 海拔 | 布局旋钮长什么样 |
| --- | --- |
| PyTorch | `x.to(memory_format=torch.channels_last)`（NHWC）、`.contiguous()`（强制物理重排）——只有全局层的粗旋钮 |
| Triton | 几乎无显式旋钮：shared 布局与 swizzle 由编译器从 `tl.dot` 反推——约束链被自动求解，代价是解得不好时你无处干预 |
| TileLang | `T.annotate_layout` / `T.use_swizzle`——shared 层的摆法开放为注解 |
| CuTe | `Layout`、`Swizzle<B,M,S>`、`composition`——整条约束链的每一环都是显式代数对象，全自由度 + 编译期对账 |
| 算子库/框架格式 | cuDNN 的张量格式枚举、vLLM 的 page size——把少数验证过的解做成选项 |

规律和 04-06 的海拔轴完全一致：**越往下，约束链的环节暴露得越多**；Triton 是"链全隐藏"，CuTe 是"链全显式"。

## 7. 开发者视角

- **验布局的三个回执**：shared 层看 Nsight 的 bank conflict 计数（该是 0 的 kernel 就该是 0）；寄存器层看 SASS 里是否出现 `LDSM`（ldmatrix 的 SASS 名）而非散装 LDS；全局层看 sectors/request 和 DRAM 利用率（01-04 与上一节的诊断表）。三个回执分别对应约束链的三环。
- **改布局是"贵"操作**：一次物理重排 = 全量数据过一遍 HBM。决定"要不要换布局"的算术很简单：重排成本（字节数 ÷ 带宽）对比换来的每次访问节省 × 访问次数——复用次数少的数据不值得为它重排。
- **听会判词**：听到 "channels_last / NHWC" 是全局层布局；听到 "swizzle / bank conflict" 是 shared 层；听到 "fragment / ldmatrix" 是寄存器层立法；听到 "paged / page size" 是显存分配层。四组词各归各层，混着说的方案要多问一句。

## 8. 最新架构落点（时效锚点 · 知识截至 2026-01）

- **Blackwell / tcgen05**：累加器进 TMEM 后，约束链的第一环换了立法者——tcgen05 规定的是 TMEM 内的摆法，寄存器 fragment 退出累加器舞台；shared 侧的 swizzle 家族随新的取数指令扩充（据 PTX 8.x 文档）。链的形状没变，每一环的具体解换代。
- **微缩放格式（MXFP4/MXFP8）**：数据和缩放因子按 32 个一组绑定存放——布局里第一次混进了"元数据"，摆法要同时伺候数值块和它的 scale 的取数路径。
- **昇腾**：CANN 近年在推动"ND 进 ND 出"（对用户隐藏 NZ，格式转换由框架内部消化）——布局作为约束解没变，变的是"谁替你解"，和 GPU 世界 Triton 隐藏 swizzle 是同一个方向。

## 9. 术语卡

### ldmatrix / stmatrix

**定义**：shared memory 与寄存器之间按 Tensor Core fragment 规则整 warp 搬运的专用指令（SASS 名 LDSM/STSM）：每线程提供一个 8×8 块的行地址，硬件把数据按 mma 规定的分布重新分发到各线程寄存器（stmatrix 为写方向）。

**为什么存在**：mma 的 fragment 分布是电路写死的，逐线程手搬既要繁琐的地址算术又必然撞 bank；ldmatrix 把"摆法翻译"做进硬件，一条指令完成整 warp 的取齐——它是约束链上 shared 层与寄存器层之间的官方转换器。

**语境例句**："SASS 里全是散装 LDS、一条 LDSM 都没有，怪不得喂不满 Tensor Core。"——意思是：编译器没走 fragment 专用搬运路径，shared 到寄存器这一跳在用慢速手搬。

### K-major / MN-major（GEMM 操作数主序）

**定义**：GEMM 的 A、B 操作数在内存里沿 K 维连续（K-major）还是沿 M/N 维连续的行话。决定 Tensor Core 按 K 深度取数时拿到的是整段还是跨步碎段。

**为什么存在**：mma/wgmma 沿 K 维成组吃数，K 连续则 tile 取数整段、TMA box 高效；主序不合适时要么转置要么用支持两种主序的指令变体（性能有差）。谈 GEMM kernel 不谈操作数主序，性能没法比。

**语境例句**："B 矩阵是 MN-major 的，wgmma 得走转置路径，慢了 8%。"——意思是：操作数主序与指令偏好不符，取数路径打了折扣。

### NHWC / channels_last（及张量格式家族）

**定义**：四维激活张量把通道维放最内层的布局（同一像素的所有通道连续），PyTorch 里叫 channels_last；同族还有 NCHW（FP32 时代）和 NC/32HW32（INT8 时代）。

**为什么存在**：Tensor Core 把卷积算成沿通道维的矩阵乘，通道连续让 K 维取数成整段——格式跟着计算指令的取数形状换代。用错格式不报错，只是每层卷积前后被框架插一次物理重排，性能默默漏走。

**语境例句**："模型转 channels_last 之后 conv 提速 30%，profile 里那些 permute kernel 也消失了。"——意思是：布局对齐 Tensor Core 的取数形状，且传染链上不再需要重排算子。

### paged KV cache（分页 KV 缓存）

**定义**：把 KV cache 按固定大小的页分配、用页表把逻辑连续的序列映射到物理离散页的布局（vLLM 引入，现为推理引擎标配）。

**为什么存在**：解的是显存分配约束而非带宽约束——序列动态增长、并发请求随时生灭，连续布局导致碎片或巨额预留；分页把利用率提到接近 100%，代价是 attention kernel 多一层页表间接寻址。

**语境例句**："page size 从 16 调到 32，页表开销减半，但尾页浪费涨了——又是一道形状税。"——意思是：页大小在间接寻址成本和最后一页的内部碎片之间做权衡，与 tile 量化同构。

### NZ 格式（昇腾分形布局）

**定义**：昇腾把矩阵切成 16×16 小块、块内行主序、块间列主序的嵌套布局（对照普通行主序 ND）。任何一个 Cube 单元要消费的块在内存里都是连续段。

**为什么存在**：Cube 一口吃 16×16、MTE 想整段搬——ND 布局下块的各行散落远处。NZ 在数据进 scratchpad 之前就把"块"摆成连续，是 GPU swizzle 的静态世界等价物：同一个"按块供数"问题，GPU 解在 shared 座位表上，昇腾解在数据格式上。

**语境例句**："这个算子输入要求 NZ，框架在前面插了个 TransData——把这次转换消掉能省 15%。"——意思是：格式不匹配触发了物理重排算子，布局传染的昇腾版。
