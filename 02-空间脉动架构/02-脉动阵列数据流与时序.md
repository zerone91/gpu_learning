# 脉动阵列的时序：为什么它不需要同步

> **所属模块**：模块 02 · 空间/脉动架构（本模块的题眼）
> **状态**：🟨 学习中（第二版：按《写作规范》全文重写。知识截至 2026-08）
> **本节主旨**：模块 01 用整整一节（同步全家桶）讲 GPU 的各种"等待与会合"机制，并留下一个悬念：为什么脉动阵列一个都不需要？本节正面回答。答案的核心是：**脉动阵列里每个数据"第几拍出现在哪个计算单元"，可以在芯片设计时就写成一个数学公式**——运行时没有任何"先后不确定"，因此"等一等、确认数据到了没有"这类动作根本无从谈起。同步没有被省略，而是**在设计期被提前消化掉了**。这一节讲清这个"确定性"的精确含义、它的三阶段执行过程、它换来了什么、又付出了什么。

## 1. 基础词汇：先把本节要用的词讲清楚

**静态调度（static scheduling）**。"调度"指决定"什么时候做什么"；"静态"指这些决定**在程序运行之前**（编译时甚至芯片设计时）就全部做完，运行时只是照章执行。反义词是动态调度——运行时看情况临时决定，GPU 的 warp 调度器（模块 01 第 2 节）就是典型的动态调度。

**确定性（determinism）**。同样的输入，每次运行的行为**逐拍完全相同**——第 100 拍谁在算什么，跑一万次都一样。GPU 做不到这一点（调度、缓存命中都有随机性），脉动阵列天然做到。

**灌入 / 满载 / 排空（fill / steady-state / drain）**。阵列执行一次计算的三个阶段：数据的"波前"逐步扫入阵列（灌入，此时后排 PE 还没活干）；全阵列每拍都在做有效计算（满载，效率峰值）；最后一批数据的"波尾"扫出阵列（排空，前排 PE 先闲下来）。

## 2. "定死"的精确含义：时序是一个可以写出来的公式

回到上一节那个 2×2 的逐拍例子。仔细看那张表会发现一个规律：输入 a[m][k]（结果矩阵第 m 行所需的第 k 个输入）到达 PE(k,n) 的拍数，**恰好等于 m + k + n**。验证一下：a00（m=0,k=0）第 0 拍在 PE(0,0)、第 1 拍在 PE(0,1)——公式给出 0 和 1，对；a01（m=0,k=1）第 1 拍在 PE(1,0)、第 2 拍在 PE(1,1)——公式给出 1 和 2，也对。结果 c[m][n] 完成的拍数同样有公式：m + n + (K-1)，K 是累加深度。

这不是巧合，是构造使然：数据每拍固定移一格、从固定位置进入、按固定的 skew 错开——三个"固定"叠加，**任何数据在任何时刻的位置都成了初始条件的确定函数**。把阵列从 2×2 放大到 128×128，公式照样成立，只是变量范围变大。

这个公式的存在，就是"时序在设计期定死"的全部含义。它带来一个 GPU 世界不可想象的性质：**芯片里没有任何一处需要在运行时"判断数据到了没有"**。数据到达某个 PE 的那一拍，是电路结构保证的，就像多米诺骨牌——第 37 张牌倒下的时刻在你摆牌时就注定了，不需要有人盯着第 36 张喊"倒了，该你了"。

## 3. 三个阶段，以及一笔摊销账

公式虽然优美，但有个内在的"启动成本"。数据斜着涌过阵列（上一节的 skew），必然存在波前和波尾：

- **灌入阶段**：第一批数据从左上角进入，波前要斜穿整个阵列才能让右下角的 PE 开工。对 N×N 的阵列，这大约要 2N 拍。此期间阵列利用率从 0 爬向 100%。
- **满载阶段**：波前已扫过全阵列、波尾还没进来，**每一拍全部 N² 个 PE 都在做有效乘加**——这是脉动阵列的"巡航状态"，前一节说的能效优势全部兑现在这个阶段。
- **排空阶段**：输入送完了，最后一批部分和还要流完剩下的路程，又是约 2N 拍，利用率从 100% 滑落回 0。

**例子：这笔固定开销什么时候要紧。** 128×128 的阵列，灌入加排空约 500 拍，是个与任务大小无关的固定成本。如果这次矩阵乘的累加深度 K = 128（送 128 拍数据就完了）：满载阶段只有约 128 拍，固定开销 500 拍反而是大头——**平均利用率不到 50%**。如果 K = 4096：满载 4096 拍，500 拍的头尾只占约 11%——利用率接近 90%。结论：**脉动阵列天生偏爱"深"的计算**，小而浅的矩阵喂不出它的效率。这和模块 01 附录里"MoE 的小 batch 喂不饱 GPU"是同一类现象：**固定成本要靠足够大的工作量摊薄**，只是这里的固定成本是灌入排空，那里是权重搬运。

## 4. 正面对账：GPU 的五种同步，这里为什么一个都不用

模块 01 第 5 节列过 GPU 的同步全家桶，每件工具为一种"运行时不确定性"而生。现在逐件对账，看确定性如何让它们全部失业：

**记分牌（追踪显存数据何时返回）——不需要。** GPU 需要它，因为显存延迟每次都不一样。脉动阵列里所有数据传递都是"到邻居，固定一拍"——**没有变长延迟的事件，就没有需要记账的对象**。

**块内屏障 `__syncthreads`（等各 warp 到齐）——不需要。** GPU 需要它，因为各 warp 被动态调度、进度不齐。脉动阵列全体 PE 共享一个时钟、每拍齐动，**根本不存在"进度"这个各自独立的东西**——所有 PE 的进度就是同一个拍数。

**内存栅栏（保证写入的可见顺序）——不需要。** GPU 需要它，因为线程通过共享内存通信、而弱内存模型不保证写入顺序。脉动阵列的 PE 之间**没有共享内存**——数据走点对点的专用电线，"可见性"就是电线上这一拍的电平，不存在顺序问题。

**原子操作（多个写者争一个地址）——不需要。** 每个部分和有且只有一条预定的流动路径（沿列向下），**任何存储位置在任何一拍最多只有一个写者**——这是布线保证的，无争可仲裁。

**mbarrier（等搬运引擎交货）——不需要。** 边缘缓冲区向阵列送数的节拍，也在同一张静态时刻表上——搬运和计算共享一个时钟表，无需握手。

> 把五条合起来，可以说出本模块最重要的一句话：**GPU 的同步原语本质上都是运行时的"询问"——到了吗？写完了吗？轮到我了吗？脉动阵列把所有这些问题的答案在设计期就写进了电线和时钟里，运行时无问可问。** 同步的成本没有消失，它变成了设计期的约束——下一小节就是这些约束的清单。

## 5. 代价清单：确定性用什么换来的

**代价一：只能算"可静态化"的计算。** 时序公式成立的前提是：数据的流动路径、迭代次数、访问模式**全都不依赖数据的值**。稠密矩阵乘完美符合（不管矩阵里的数是几，流法一模一样）。反例：带数据相关分支的计算（每个元素按自己的值走不同路径）——路径运行时才知道，公式无从写起。所以实际的 NPU 芯片总是在脉动阵列旁边**配一个通用的向量/标量处理器**，专门接住这些"排不进时刻表"的活（softmax、采样、控制逻辑）——TPU 的 VPU、昇腾的 Vector/Scalar 单元都是这个角色。

**代价二：形状刚性。** 公式按阵列的物理尺寸写死。矩阵维度不是阵列边长的整数倍时要填零凑整，填零的 PE 空转（上一节提过，本模块第 5 节细算这笔税）。

**代价三：时钟就是命门。** 全阵列一个时钟齐步走，时钟频率受最长的那根连线制约；任何一个 PE 慢一拍，全局时刻表就错乱——所以它必须用同步数字电路的硬保证来造，没有"某个单元慢点没关系，调度器绕开它"的弹性（GPU 有这个弹性）。

**代价四：性能没有"救回来"的机会。** GPU 上形状不好、访存不齐，还能靠调度和缓存兜住一部分；脉动阵列的时刻表印好了就是那样，**编译时算出来利用率 40%，跑出来就是 40%**——好消息是它也不会更差，确定性延迟本身在延迟敏感的服务里是个卖点。

## 6. 现实芯片的光谱：没有纯粹的两极

"全动态"和"全静态"是两个理想端点，真实芯片都在中间选位置：

```
全动态 ◄──────────────────────────────────────────────► 全静态
 早期 GPU      现代 GPU 的        Tensor Core       TPU 的        Groq
 (纯 SIMT)     异步流水线kernel    (SM 里的小        大脉动阵列     (整颗芯片、
               (软件把搬运计算     矩阵引擎，指令     (阵列内静态、   连芯片间网络
               的时序排成流水)     内部是静态的)      阵列外靠编译器) 都静态排定)
```

有意思的是**两头在互相靠近**：GPU 这边，模块 01 讲过的异步流水线（TMA、多级缓冲、warp 分工）本质上是**用软件把一段时序"排死"**——最重的负载上，GPU 在主动向右挪；而右边的 Groq 走到了极端——不但阵列，整颗芯片每条指令、每次存储访问、甚至多芯片之间的网络传输全部编译期排定，换来"同样的请求，延迟逐拍可复现"的确定性服务能力。**争夺的焦点是负载的规则程度**：越规则的计算（稠密大矩阵乘）越适合右边，夹杂分支和变长的真实负载（注意力里的 softmax、MoE 的路由）把天平拉向左边。

## 7. 开发者视角：性能分析从"跑了再看"变成"编译就知道"

时序全静态最直接的使用体感是：**性能问题的排查从运行时前移到编译期**。

| | GPU 世界（模块 01 的方式） | 脉动/静态世界 |
| --- | --- | --- |
| 想知道多快 | 跑起来用性能分析器测 | **编译器直接算出来**——时序公式就是成本模型，编译报告给出预计拍数 |
| 找瓶颈 | 停顿原因分解、逐级下钻 | 看编译报告：阵列利用率、填零比例、灌排占比、边缘带宽够不够 |
| 不确定性来源 | 调度、缓存、争用，处处都是 | **几乎只剩输入形状**——同形状跑一万次，拍数一致 |
| 优化的抓手 | 访存模式、占用率、流水深度 | 喂对形状（对齐且够深）、选对数据流（下一节）、让边缘缓冲跟上 |

**例子：编译器怎么在程序运行之前就算出耗时。** 任务：1024×1024×1024 的矩阵乘，跑在 128×128 的权重驻留阵列上。编译器的推算过程完全是算术：

1. 权重矩阵是 1024×1024，阵列一次装得下 128×128 的一块——要切成 (1024/128) × (1024/128) = **64 块权重**，逐块装载、逐块计算。
2. 每块权重装好后，1024 个输入行流过阵列——满载阶段 1024 拍；外加灌入排空约 2×128 = 256 拍（第 3 节）。每块合计约 1280 拍。
3. 总拍数 ≈ 64 块 × 1280 拍 ≈ **82000 拍**。按 1 GHz 时钟就是 82 微秒。
4. 平均利用率也顺手算出：有效计算占每块的 1024/1280 = **80%**——损失的 20% 全是灌排的固定开销，编译报告会把这个数直接打出来。

这四步里没有任何"要跑了才知道"的量。同一个负载在 GPU 上，缓存命中率、调度的运气都要实测；在这里，**82000 拍就是答案，跑一万次都是它**。这就是"性能分析前移到编译期"的具体含义——也顺便看出优化方向：想把 80% 提上去，要么加深 K（摊薄灌排），要么把多个小任务背靠背排流水（让上一块的排空和下一块的灌入重叠，成熟编译器都会做）。

给用 TPU/NPU 的人一句话：拿到性能问题，第一反应不是"上 profiler 看 stall"，而是**"看编译器把我的计算切成了什么形状的矩阵乘、利用率各是多少"**——九成的问题出在形状与切法上，这和 GPU 的排查习惯正好倒过来。

## 8. 最新架构落点（知识截至 2026-08）

- **谷歌 TPU**：从 2016 年第一代到 v7，脉动阵列 + 全静态编译（XLA）这个**机制**没变过——一个范式十年不用改，说明它在自己的适用域里已接近最优。代际进步在存储带宽、互连规模、阵列数量**以及阵列本身的边长**（v1–v5 是 128×128，v7 已放大到 256 量级，02-01 §6 有反推）。注意本节所有的公式（时序公式、灌排 2N 拍、编译期算耗时）都以边长 N 为参数，**换代只是换 N，推导一字不改**。
- **Groq**：静态化的完全体（第 6 节）。以"确定性延迟"作为商业卖点服务在线推理。
- **Tenstorrent、Cerebras**：走"许多小核 + 片上网络"的中间路线——每个核内部静态，核之间的网络有握手（局部弹性），印证光谱中段也站得住人。
- **GPU 侧的镜像**：Blackwell 的矩阵指令和专属存储让"指令内部的静态成分"越来越大——光谱两端持续互相渗透。

## 9. 术语卡

### 静态调度（static scheduling）
**定义**：全部"何时做什么"的决定在运行之前（编译期或设计期）做完，运行时照章执行。脉动阵列是硬件级静态调度的极端形态：时序直接焊在电路里。
**为什么存在**：省掉运行时决策的全部硬件（调度器、记分牌、仲裁电路）和全部同步开销；代价是只能服务"运行前可完全预知"的计算。
**语境例句**："Groq 连内存访问都是编译器排好的。" —— 意思是：那颗芯片把静态调度推到整芯片范围，没有缓存没有仲裁，性能在编译时就是确定的数字。

### 确定性延迟（deterministic latency）
**定义**：同样形状的输入，执行拍数每次完全一致的性质。静态调度的直接产物。
**为什么存在**（作为卖点）：在线服务关心"最慢的那次请求"（尾延迟）；动态系统的尾延迟难以保证，确定性系统的每一次都一样——服务质量承诺变得容易。
**语境例句**："这个场景对 P99 延迟卡得死，静态调度的芯片有天然优势。" —— 意思是：确定性消灭了延迟分布的长尾，第 99 百分位和中位数是同一个数。

### 灌入 / 满载 / 排空（fill / steady-state / drain）
**定义**：脉动阵列执行的三阶段：波前扫入（约 2N 拍，利用率爬坡）、全阵列有效计算（峰值）、波尾扫出（约 2N 拍，利用率滑落）。头尾是与任务大小无关的固定成本。
**为什么存在**：数据斜着流过阵列的几何必然——有波前就有铺满的过程，有波尾就有流干的过程。
**语境例句**："这些小矩阵乘在 MXU 上灌排占了一半时间。" —— 意思是：任务太浅（累加深度小），固定的灌入排空成本摊不薄，平均利用率被拖到一半以下——要么把小矩阵拼大，要么这活儿本就不适合大阵列。

### 伴生向量单元（TPU 的 VPU / 昇腾的 Vector 单元）
**定义**：矩阵阵列旁边配备的通用向量/标量处理器，负责接住无法静态排程的计算（softmax、逐元素变换、控制逻辑）。
**为什么存在**：代价清单第一条——阵列只吃规则计算，真实网络里总有不规则的部分，必须有人兜底。它的吞吐远低于阵列，所以"不规则部分占比"决定了这类芯片对某个模型的适配度。
**语境例句**："这个模型 softmax 占比太高，MXU 在等 VPU。" —— 意思是：不规则计算成了瓶颈，矩阵阵列的算力发挥不出来——正是这类芯片最怕的负载形态。
