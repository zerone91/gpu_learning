## 1. 基础词汇：先把本节要用的词讲清楚

**竞争（race condition）**。两个执行流访问同一个数据、其中至少一个在写，且先后顺序没有保证——结果取决于"谁碰巧跑得快"，每次运行可能不同。竞争是并行编程里最阴险的错误：程序不崩溃，只是**偶尔**算错。同步机制存在的首要目的就是消灭竞争。

**屏障（barrier）**。一种"等大家到齐"的机制：先到的执行流停下来等，直到约定范围内的所有成员都到达这个点，才一起放行。作用对象是**进度**。

**栅栏（fence，内存栅栏）**。一种"保证可见顺序"的机制：它不让任何人等待，只是保证"我在栅栏之前写的数据，别人在栅栏之后一定能看到最新值"。作用对象是**数据可见性**。屏障和栅栏管的是两件不同的事，第 3 节专门辨析。

**原子操作（atomic operation）**。把"读出一个值、修改、写回去"三步捆绑成一个不可分割的动作。比如 `atomicAdd(&counter, 1)`：即使一万个线程同时执行它，计数器也恰好加一万——因为硬件保证每次读-改-写中间不会被别人插队。没有原子性时，两个线程可能同时读到 5、各自加 1、都写回 6，丢失一次累加。

**作用域（scope）**。每个同步动作都有一个"生效范围"：warp 内（32 线程）、线程块内、整个 GPU、还是跨 GPU 与 CPU。范围越大，硬件要协调的部件越多，代价越贵——同一个原子加法，块内作用域和全局作用域的开销可以差一个数量级。用同步时"够用就好、范围从窄"是省钱的基本功。

## 2. 为什么异步必然带来同步：一个会出错的例子

设想一个常见协作：线程 0 负责把一个数写进 shared memory，其他线程随后读它。代码朴素地写成：

```
if (threadIdx.x == 0)  sh_val = compute();   // 线程 0 写
result = sh_val * 2;                          // 所有线程读
```

这段代码是**错的**，而且错得很典型。原因：第 2 节（02 warp 与调度）讲过，一个线程块里的各个 warp 是**各自独立被调度**的——线程 0 所在的 warp 可能还没轮到执行写入，别的 warp 就已经跑到了读取那一行，读到的是一个旧值或垃圾值。而且这个 bug 时隐时现：调度的先后每次不同，测试十次可能九次碰巧对。

修复只需一行：在写和读之间插入 `__syncthreads()`（下一节第一个成员），强制"全块到齐才继续"。这个小例子说明了本节的中心逻辑：**warp 异步推进带来了性能（02 节），也带来了"先后顺序不确定"；凡是需要确定顺序的地方，必须显式立一个会合点。** 硬件的每一种异步能力，都会催生一种对应的同步工具——这就是"全家桶"越来越大的原因（第 5 节）。

## 3. 先分清两件事：到齐，和看见

新手最容易混淆的一点：**"大家都到了这个点"和"我能看到你写的数据"是两个独立的保证**。

- 只保证**到齐**（纯屏障）：所有人都执行到了同一行，但硬件缓存里的数据可能还没互相同步——你到了，我却看不到你写的最新值。
- 只保证**看见**（纯栅栏）：我的写入对你可见了，但没人在等你——你可能还没执行到读取的地方，可见性保证暂时用不上。

真正安全的协作往往两者都要。常用的 `__syncthreads()` 之所以好用，就因为它是**二合一**的：既等全块到齐，又附带一个块级的内存栅栏。而单独的栅栏函数（`__threadfence` 系列）只管可见性、不管等待，用于无锁编程等特殊场景。

多说一句背景，帮助理解为什么"看见"需要专门保证：GPU 采用**弱内存模型**——在没有栅栏的情况下，硬件为了性能可以调整写入对外可见的顺序，你先写 A 后写 B，别的线程可能先看到 B 的新值而 A 还是旧的。这不是 bug，是性能换来的规则；栅栏就是你向硬件声明"这里的顺序我是认真的"。

## 4. 全家桶成员：一件一件认

按作用域从小到大排列。每件讲三点：是什么、为哪种异步而生、一个使用画面。

### 4.1 `__syncwarp()`：warp 内的会合

**是什么**：让 warp 内指定的线程（用一个 32 位掩码点名，通常是全体）在此聚齐并互相可见。
**为哪种异步而生**：上一节（03 分支发散）讲的独立线程调度——Volta 之后每个线程有自己的进度，warp 内 32 个线程不再保证天然齐步。凡是 warp 内线程要交换数据（比如经典的 warp 内归约），交换前必须显式聚齐。
**画面**：`__shfl_sync(0xffffffff, val, lane)` 这类带 `_sync` 后缀的函数，名字里的 sync 就是内建的 `__syncwarp`。

### 4.2 `__syncthreads()`：线程块内的会合（使用频率最高）

**是什么**：块内**所有**线程的屏障，附带块级内存栅栏（二合一，第 3 节）。
**为哪种异步而生**：块内各 warp 独立调度、进度不齐（第 2 节的例子）。典型场景是"分阶段协作"：全体把数据装进 shared memory → **syncthreads** → 全体使用这些数据 → **syncthreads** → 下一轮。两次同步分别保证"用之前装完了"和"下一轮覆盖之前用完了"。
**一个必须知道的陷阱**：`__syncthreads()` 要求块内**所有**线程都到达**同一个**调用点。如果把它写在 if 分支里、而块内有的线程不进这个分支——等齐永远凑不满，程序死锁（或行为未定义）。规则：**同步语句放在所有线程都会经过的路径上**。

### 4.3 `__threadfence()` 系列：只管可见、不管等待

**是什么**：纯内存栅栏，三个作用域版本：块内、全 GPU（`__threadfence()`）、跨 GPU 和 CPU（`__threadfence_system()`）。
**为哪种异步而生**：跨线程块的数据交接。块与块之间**没有**"等齐"的常规手段（它们可能根本不同时在跑），只能用"栅栏 + 原子标志"的模式交接数据：生产者写完数据 → 栅栏（保证数据先于标志可见）→ 原子地把标志置 1；消费者轮询标志，见 1 后再读数据。
**画面**：经典的"最后一个线程块做收尾"模式：每块做完局部归约，原子计数器加一，最后一个到达的块（计数器达到块总数）读取所有块的结果做总归约——中间的栅栏保证它读到的都是新值。

### 4.4 原子操作：会合点太贵时的轻量协调

**是什么**：不可分割的读-改-写（add、max、比较并交换等），可选块内/全局/系统作用域。
**为哪种异步而生**：成千上万个线程要更新同一个共享量（计数器、直方图、任务队列指针），不可能为每次更新开一次全员大会（屏障太贵），原子操作让每次更新自身安全即可。
**代价与对策**：所有线程打**同一个地址**的原子操作会在那个地址上排队串行——这是常见的性能陷阱。标准对策是**分层归约**：先在块内（shared memory 上的原子操作，便宜）汇总出一个局部值，每块只向全局地址提交一次——全局争用从"线程数"降到"块数"，通常是几个数量级的差别。

### 4.5 mbarrier：为硬件搬运引擎定制的新式屏障（Hopper 起）

前面四件工具协调的都是**线程之间**的关系。Hopper 引入 TMA 搬运引擎后（上一节 6.1）出现了新问题：**计算线程要等的对象不再是别的线程，而是一台硬件引擎**——"TMA 把这块数据搬完了没有？"老工具没法表达这种等待，于是有了 mbarrier。

**是什么**：一个放在 shared memory 里的小计数器对象，支持三种动作——"到达"（计数）、"等待"（阻塞直到条件满足）、以及关键的**"期待多少字节"**：使用者先声明"这一轮要等 N 个字节到货"，TMA 每搬完一段就自动向它汇报字节数，凑满 N 才放行等待者。
**为哪种异步而生**：异步搬运引擎。它让"线程等引擎"变得和"线程等线程"一样自然。
**画面：双缓冲流水线的心跳。** 上一节 02 讲过的流水线（算这块、搬下块）在硬件层就是靠一对 mbarrier 驱动的：每个缓冲区配两个屏障，"装满了"（TMA 向它汇报）和"用完了"（计算线程向它汇报）。搬运方等"用完了"才敢覆盖，计算方等"装满了"才敢开算——两个节拍器交替响，流水线就转起来了。还有一个精巧的细节值得知道：mbarrier 自带一个**相位位**（0/1 交替），每完成一轮自动翻面，于是同一个屏障对象可以在循环里**无限复用**而不需要重置——没有这个设计，每圈都要重建屏障，流水线就搭不起来了。

### 4.6 一张速查表收拢

| 工具 | 作用域 | 保证什么 | 为哪种异步买单 |
| --- | --- | --- | --- |
| `__syncwarp` | warp（32 线程） | 到齐 + warp 内可见 | 线程各有独立进度（Volta 起） |
| `__syncthreads` | 线程块 | 到齐 + 块内可见 | 块内各 warp 独立调度 |
| `__threadfence` 系 | 块 / GPU / 系统 | 仅可见性顺序 | 跨块交接数据（无法等齐，只能保序） |
| 原子操作 | 块 / GPU / 系统 | 单次读改写不可分割 | 海量线程更新同一地址 |
| mbarrier | 块（可跨簇） | 到齐 + 按字节计数 | 等待硬件搬运引擎（TMA） |

## 5. 一条规律：每添一种异步，就配一把新锁

把全家桶按出生年代排一遍，会看到清晰的因果：

- 早期 CUDA：只有 `__syncthreads`——因为当时唯一的异步就是"块内 warp 各自调度"。
- 2017 Volta：线程有了独立进度（03 节）→ 隐式的 warp 齐步失效 → **`__syncwarp` 和 `_sync` 后缀函数族诞生**。
- 2020 Ampere：cp.async 让数据搬运脱离线程独立进行 → 需要追踪"搬完没有" → **cp.async 配套的等待指令诞生**。
- 2022 Hopper：TMA 引擎 + 可跨 SM 的线程块簇 → **mbarrier、簇级同步诞生**。

规律：**同步工具的数量，是硬件异步程度的忠实倒影。** 看到新架构发布一个新的异步引擎，可以直接推断它旁边一定站着一个新的等待原语。反过来，读一个陌生 kernel 时数一数它用了几种同步，也就大致知道它把多少事情做成了异步。

## 6. 同步的代价，以及"多与少"的辩证法

同步不是免费的，三种典型成本：

**尾部等待**。屏障让先到的等最后到的——如果 warp 之间负载不均，快的全在陪慢的。热循环里一个 `__syncthreads` 可能占掉可观的时间（性能工具里 stall 原因显示为 "Barrier"）。对策是让屏障之间的工作量尽量均匀，或用范围更小的屏障。

**原子争用**。4.4 讲过：同地址原子操作串行化。对策是分层归约。

**过度同步与同步不足**。多余的屏障掐死了本可以重叠的工作；缺失的屏障造成竞争（比性能问题险恶得多——错得悄无声息）。竞争类 bug 有专门工具抓：`compute-sanitizer --tool racecheck`。

但要小心一个反例，说明"少同步"不是教条。FlashAttention-3 的实现里，两组计算线程**故意多加了一对屏障**，强制彼此错开半拍——目的是让"你做矩阵乘时我做 softmax、你做 softmax 时我做矩阵乘"，两种硬件单元（Tensor Core 和特殊函数单元）时刻都有人用。去掉这对屏障，两组线程各自随机推进，反而经常撞车抢同一个单元。**这里同步买到的不是安全，而是"错峰用资源"的秩序**——秩序带来的收益超过了同步本身的开销。正确的原则不是"越少越好"，而是：**每一个同步都应该能说出它买到了什么（安全，或秩序）；说不出的就删掉。**

## 7. 对照：为什么脉动阵列一个屏障都不用

模块 02 会详细讲另一类芯片（脉动阵列，谷歌 TPU 的核心结构），这里先把本节视角下的答案给出，作为两个模块之间的桥：

GPU 需要同步，根源是**时序在运行时才确定**：warp 谁先谁后看调度、数据何时到看缓存命中——先后不确定，所以要在关键处会合确认。而脉动阵列走了相反的路线：**每个数据在第几拍到达哪个计算单元，在芯片设计时就写死在电路里**，运行时没有任何不确定性。"B 做完了没有"这类问题，在那个世界里根本不会被提出——答案在硬件出厂前就注定了。**同步没有被优化掉，而是被提前到设计期消化掉了**。代价是死板：那种芯片只能高效执行时序可以完全预排的计算（规则的矩阵乘），遇到数据相关的分支就束手无策。这一对取舍（灵活但要同步 vs 死板但零同步）是两类芯片的分水岭，模块 00 和 02 会反复回到它。

## 8. 开发者视角

| 你想知道/控制什么 | 去哪里看/拧 |
| --- | --- |
| 同步等待占了多少时间 | Nsight Compute stall 分解里的 `Barrier`（等屏障）和 `Membar`（等栅栏） |
| 有没有竞争/漏同步 | `compute-sanitizer --tool racecheck`（抓 shared memory 竞争）和 `--tool synccheck`（抓非法同步用法） |
| 原子争用严重吗 | 原子指令的吞吐与重放（replay）计数 |
| 源码侧的工具箱 | 上文全家桶；写 Triton 时基本不用操心——编译器自动在 shared memory 的使用点插屏障，流水线的 mbarrier 由 `num_stages` 参数隐式生成 |

给 Triton 用户的一句话：你几乎不会手写任何同步，但**理解它们依然有用**——当 profile 显示大量 Barrier stall 时，你要能想到"是不是块内负载不均"或"num_stages 排出的流水线节拍卡住了"，而不是对着一个从没在自己代码里出现过的词发懵。

## 9. 最新架构落点（知识截至 2026-01）

- **Hopper/Blackwell**：mbarrier 家族持续扩展（簇级同步、与新一代 Tensor Core 指令配套的等待原语）。方向不变：异步越多，显式同步越细。
- **跨块同步**：需要"全网格等齐"的算法（迭代法等）可用 cooperative launch 机制做全 grid 屏障，开销在微秒级（约等于重启一次 kernel），仅在"必须保住寄存器/shared memory 里的状态"时才比拆成两个 kernel 划算。
- **AMD（CDNA 系）**：块内屏障对应 `s_barrier`；访存完成的等待走一套不同的机制——编译器插入 `s_waitcnt` 指令，语义是"等到未完成的访存数量降到 N 以下"。和 NVIDIA 的记分牌（02 节）解决同一问题，但 AMD 把等待指令明晃晃写在汇编里，调优者可以直接数——两家风格不同，原理同源。

## 10. 术语卡

### 屏障（barrier）与栅栏（fence）
**定义**：屏障让约定范围内的执行流互相等待、到齐放行，管"进度"；栅栏保证之前的写入对之后的读者可见，管"数据可见顺序"。`__syncthreads` 是两者的合体。
**为什么存在**：异步执行下进度和可见性都没有默认保证；两种保证正交，分开提供才能按需付费。
**语境例句**："这里只需要 fence，不需要 barrier。" —— 意思是：只要求"我写的对方能看到"（比如设置标志位前），不要求双方等齐——用更便宜的工具就够了。

### `__syncthreads()`
**定义**：线程块内全体线程的屏障加块级栅栏。块内协作（经 shared memory 交换数据）的标准会合点。
**为什么存在**：块内各 warp 独立调度、进度不齐，凡"先写后读"的接力都需要一个确定的交接点。
**语境例句**："别把 syncthreads 放在 if 里面。" —— 意思是：若块内有线程不进入该分支，屏障永远凑不齐人数，程序死锁——同步必须放在全体线程都经过的路径上。

### 原子操作（atomics）
**定义**：硬件保证不可分割的读-改-写操作（加、最大值、比较交换等），带作用域选择。
**为什么存在**：海量线程更新同一个量时，开全员大会（屏障）太贵；原子操作让每次更新自身安全，无需全局协调。
**语境例句**："直方图 kernel 慢在全局原子争用，先在 shared 里各自统计再汇总。" —— 意思是：所有线程打同一地址会串行排队，分层归约把全局争用从线程数降到块数。

### mbarrier
**定义**：Hopper 引入的、放在 shared memory 里的可编程屏障对象，支持到达/等待/按字节计数，自带相位位以便在循环中免重置复用。
**为什么存在**：TMA 搬运引擎独立于线程干活，需要一种"线程等引擎、按到货字节数放行"的机制——老工具只会"线程等线程"。它是异步流水线（num_stages）的硬件心跳。
**语境例句**："生产者到达时要带上 expect-tx 字节数。" —— 意思是：发起 TMA 搬运前先向 mbarrier 声明本轮的到货总量，引擎分批汇报、凑满才放行消费者——字节数写错会导致读到半成品数据。

### 作用域（scope）
**定义**：同步或原子操作的生效范围：warp、块、GPU、系统，逐级变贵。
**为什么存在**：范围越大要协调的硬件越多。按需选最小范围是同步的省钱基本功。
**语境例句**："这个 atomicAdd 用块内作用域就够了。" —— 意思是：参与更新的线程都在同一块内，没必要付全 GPU 一致性的开销，改用 `atomicAdd_block` 更快。

### 竞争（race condition）
**定义**：多个执行流无序地访问同一数据且至少一方在写，结果依赖偶然的执行顺序。
**为什么存在**（作为概念）：它是异步执行的原生风险，是所有同步工具要消灭的对象。最险恶之处在于间歇性——测试常过、上线偶错。
**语境例句**："这个 bug 十次跑八次是对的，先上 racecheck。" —— 意思是：间歇性错误是竞争的典型指纹，用 `compute-sanitizer --tool racecheck` 定位漏掉的同步点，别靠加打印碰运气。
