# PTX 与 SASS：GPU 的两层指令集

> **所属模块**：模块 01 · SIMT 核的物理实现
> **状态**：🟨 学习中（第二版：按《写作规范》全文重写。知识截至 2026-08）
> **本节主旨**：NVIDIA GPU 有**两层**指令集：PTX 是一份**稳定的、公开的、虚拟的**指令集——它描述一台理想化的 GPU，承诺"程序对它编译，未来任何一代真实 GPU 都能跑"；SASS 是**某一代芯片真实的机器码**——每代可以彻底改变、不公开文档。这个双层结构解决的是"软件要长寿、硬件要自由进化"的矛盾，也是 NVIDIA 生态护城河的技术根基。对做性能的人，本节要建立一个关键认知：**性能的真相全在 SASS 一层**——寄存器分配、指令调度、有没有用上 Tensor Core，都是从 PTX 编译到 SASS 的那一步（由一个叫 ptxas 的编译器）决定的。

## 1. 基础词汇：先把本节要用的词讲清楚

**指令集（ISA，Instruction Set Architecture）**。一块芯片能听懂的全部指令的清单和规则：有哪些指令、每条什么格式、语义是什么。它是软件和硬件之间的合同——软件按合同生成指令，硬件按合同执行。

**机器码（machine code）**。按某个指令集编码出来的二进制指令序列，芯片直接执行的东西。

**虚拟指令集**。不对应任何真实芯片的指令集——它描述一台"理想机器"，程序编译到它之后，还需要**再翻译一次**才能在真实芯片上跑。听起来多此一举，价值在第 2 节讲。

**JIT（Just-In-Time，即时编译）**。不在开发者的机器上提前完成翻译，而是在**用户运行程序的那一刻**、由驱动当场把虚拟指令翻译成本机机器码。

## 2. 为什么要两层：软件要长寿，硬件要自由

先看没有双层结构会发生什么。假设程序直接编译成某代芯片的机器码：换一代芯片，机器码格式变了，**所有已发布的软件全部作废**，要么重新编译、要么新芯片被迫兼容老格式。CPU 世界选了后者——x86 指令集背了四十年的历史包袱，每代芯片都要用一块专门的解码电路把老指令翻译成内部格式，付出的是芯片面积。

NVIDIA 选了另一条路，把"翻译"从硬件挪到了软件：

- **PTX**（Parallel Thread eXecution）：虚拟指令集。文档公开、语法稳定、**只增不删**——2010 年的 PTX 程序今天仍然合法。程序编译到 PTX 为止，就获得了"永久有效"的身份。
- **SASS**（Streaming ASSembler）：每一代芯片各自的真实机器码。编码不公开、代际之间可以不兼容地重来——硬件团队因此获得每代彻底重构微架构的自由（Volta 改线程调度、Hopper 加 warpgroup 指令、Blackwell 换新的矩阵指令族，SASS 都大改）。
- 两层之间的翻译由 **ptxas**（NVIDIA 的后端编译器）完成——它既存在于开发者的工具链里（提前翻译），也内置在**每一台用户机器的显卡驱动里**（运行时翻译）。

**例子：一个 2020 年发布的程序如何跑在 2025 年的卡上。** 开发者 2020 年编译程序时，工具链在可执行文件里同时打包了两样东西：当时几代 GPU 的 SASS 机器码，**外加一份 PTX**。2025 年用户在 Blackwell 卡上运行它：驱动发现文件里没有 Blackwell 的 SASS——于是取出那份 PTX，**用驱动内置的 ptxas 当场编译出 Blackwell 机器码**（首次运行慢几秒，结果会缓存到磁盘），之后正常执行。软件寿命和硬件进化就这样解耦了。这个"多代机器码 + PTX 兜底"的打包格式叫 **fat binary（胖二进制）**；发布软件时选择打包哪些代的 SASS、要不要带 PTX，就是在"启动速度"（有现成 SASS 就不用现场编译）和"未来兼容"（有 PTX 才能上新卡）之间做取舍。

## 3. 编译链条全景，以及 ptxas 为什么是"真正的编译器"

```
CUDA C / Triton 等源码
        │  ① 前端编译器（nvcc 的前半段 / Triton 的编译器）
        ▼
      PTX  ←—— 稳定边界：到这里为止一切都是"虚拟"的
        │  ② ptxas（后端编译器，性能的真正裁判）
        ▼
      SASS（绑定具体某代芯片）
```

第①步做的是语言层面的翻译，相对朴素。**真正决定性能的是第②步**，ptxas 在这里做三件大事，每件都直接对应前面几节讲过的硬件机制：

1. **寄存器分配**。关键事实：**PTX 里的寄存器是无限的**——它是虚拟机器，想用多少虚拟寄存器都行。而真实芯片每线程最多 255 个寄存器、且用量决定驻留数量（02 节占用率的第一约束）。把无限的虚拟寄存器塞进有限的物理寄存器、决定谁进寄存器谁溢出到显存——全是 ptxas 的裁决。
2. **指令调度与控制位**。02 节讲过，定长延迟的依赖靠编译器把"停顿几拍"写进每条指令的控制位。写这些控制位的就是 ptxas——它重排指令顺序、见缝插针地填充等待间隙（也就是制造指令级并行）、给变长操作分配记分牌格子。
3. **指令选择**。同一个 PTX 操作在真实芯片上可能有几种实现（普通读取还是 128 位向量读取？普通乘加循环还是 Tensor Core 矩阵指令？），选哪种由 ptxas 按目标芯片拍板。

**例子：一小段代码经过 ptxas 前后的样子。** 源码是 `d = a*b + a; e = data[i] * d;`（一次乘加，再乘上一个从显存读来的数）。两层指令大致如下（示意，非逐字节精确）：

```
PTX（ptxas 之前，虚拟）              SASS（ptxas 之后，真实）
────────────────────────            ─────────────────────────────────────
mul.f32  %f3, %f1, %f2              LDG.E R6, [R8]        [占用 0 号记分牌格子]
add.f32  %f4, %f3, %f1              FMUL  R4, R2, R3      [控制位：停顿 4 拍]
ld.global.f32 %f5, [%rd1]           FADD  R5, R4, R2      [控制位：停顿 4 拍]
mul.f32  %f6, %f5, %f4              FMUL  R7, R6, R5      [控制位：等 0 号格子]
```

对照着看，ptxas 的三件大事在四行里全部现身：**寄存器分配**——PTX 里的 `%f1、%f3、%f5` 是编号随便涨的虚拟寄存器，SASS 里变成了物理的 R2、R4、R6（这个 kernel 的每线程寄存器数由此定案）；**指令调度**——显存读取被**从第三行提到了第一行**（趁前面两条算术还在算，读取的几百拍等待被重叠掉一部分），且每条指令都写上了控制位（第 2 节讲过的停顿计数和记分牌格子）；**指令选择**——`ld.global` 落成了带缓存策略的 `LDG.E`。

由此得到本节最实用的推论：**看 PTX 调性能基本是错觉**。上面左列里没有真实的寄存器压力（虚拟寄存器无限）、没有控制位、没有指令重排——"性能三要素"全部产生于 ptxas 之后。要确认性能问题，**读 SASS**。还有一个日常有感的现象也由此解释：升级 CUDA 工具包后同样的代码变快了——因为 ptxas 变聪明了，同一份 PTX 编出了更好的 SASS（比如把读取提得更早、控制位排得更紧）。

## 4. 日常工具箱：什么时候看、怎么看

绝大多数时候你不需要读汇编。需要出手的典型场景和对应工具：

| 场景 | 做法 |
| --- | --- |
| 怀疑 Tensor Core 没用上 | 导出 SASS（`cuobjdump -sass 程序名`），搜矩阵指令（`HMMA`/`QMMA` 字样）——搜不到就是没用上，回头查数据类型和矩阵尺寸 |
| 怀疑寄存器溢出 | 编译加 `-Xptxas -v`，看输出的每线程寄存器数和 "spill" 字样（02 节讲过这个警报） |
| 怀疑向量化读取没生效 | SASS 里搜 `LDG.E.128`（128 位读取），没有就说明还在 32 位零售 |
| 想知道热点行对应哪些指令 | 编译加 `-lineinfo`，然后在 Nsight Compute 里用源码-SASS 对照视图——每行源码旁直接标出它的指令和停顿情况，**这是最常用、性价比最高的入口** |
| 写 Triton 时想验证生成质量 | `triton 编译产物的 .asm 字段`可直接导出 PTX 和 SASS 文本，同样搜关键指令 |

心法一句话：日常 95% 的需求靠 **`-Xptxas -v` + Nsight 的源码对照视图**解决；手读整段 SASS 只在"怀疑编译器没做对"时出手，且通常只是搜几个关键指令名，不是逐行精读。

## 5. 最新架构落点（知识截至 2026-08）

- **PTX 的演化方式是"只加不改"**：每代新硬件能力以新指令族的形式加入（Volta 的 mma、Hopper 的 wgmma 和 TMA 指令、Blackwell 的 tcgen05 族），旧指令永远保留。**因此追新架构特性最可靠的一手材料，就是 PTX 文档的新增章节**——比白皮书更精确，比逆向更权威。
- **SASS 每代重新编码**：某代的机器码不能在别代上跑，这正是 fat binary 存在的原因。
- **AMD 走了相反的路**：它的 GPU 指令集（CDNA/RDNA 系列）**公开完整文档**、程序直接编译到真实机器码，没有稳定的虚拟层——好处是完全透明（汇编里每条等待指令都看得见、可以手调），代价是二进制的跨代兼容性弱，主要靠源码级重新编译解决。两家的取舍：NVIDIA 卖"时间兼容"，AMD 卖"透明可控"。
- **这个双层结构正在往上长出第三层**。CuTe-DSL、Triton、TileLang 这批工具（模块 04 第 6 节）都是"用 Python 写、由自己的编译器下沉到 PTX"，**于是 PTX 从"编译链的中点"变成了"多条编译链的汇流点"**。更值得注意的是 NVIDIA 把 **CUDA Tile IR 做成了 Triton 的后端**——**厂商第一次直接介入第三方 DSL 的代码生成**。本节那句"性能的真相全在 SASS 一层"没有变，变的是"从源码到 PTX"这一段现在有很多条并行的路。
- **一个跟进新架构的实用提醒没变、而且更重要了**：§5 说过"追新架构特性最可靠的一手材料是 PTX 文档的新增章节"。Blackwell 的 `tcgen05` 一族、2-CTA 的 `cta_group` 修饰符、块缩放格式的相关指令，**全都是先出现在 PTX 文档里，白皮书往往几个月后才讲清楚。**

## 6. 术语卡

### PTX
**定义**：NVIDIA 的虚拟指令集。描述一台理想化的 SIMT 机器（寄存器无限、指令通用），文档公开、跨代稳定、只增不删。程序编译到 PTX 即获得对未来硬件的兼容性。
**为什么存在**：把"软件长寿"和"硬件自由进化"解耦——软件对稳定的虚拟层编程，真实芯片每代随便改，中间靠驱动里的编译器翻译。
**语境例句**："这个库只发布了 PTX，没带 Blackwell 的 cubin。" —— 意思是：在 Blackwell 卡上首次运行时驱动要现场编译（慢几秒但能跑）；若连 PTX 都没带，新卡直接跑不了。

### SASS
**定义**：某一代 NVIDIA 芯片的真实机器码。寄存器是物理的、指令带调度控制位、编码不公开，代际间可不兼容地重构。
**为什么存在**：不公开、不承诺兼容，硬件团队才能每代彻底重造微架构而不背历史包袱。
**语境例句**："在 SASS 里搜一下 HMMA。" —— 意思是：从机器码层面确认 Tensor Core 指令是否真的生成了——这是"有没有吃到 Tensor Core"最不会骗人的证据。

### ptxas
**定义**：把 PTX 编译成 SASS 的后端编译器，同时存在于开发工具链和每台机器的显卡驱动中。负责寄存器分配、指令调度（含控制位）、指令选择。
**为什么存在**：它是虚拟层与真实芯片之间的翻译官，也是性能的真正裁判——占用率、指令级并行、Tensor Core 的采用与否都在它手里定案。
**语境例句**："升级到新版 toolkit 后这个 kernel 白捡了 8% 性能。" —— 意思是：源码没动，是新版 ptxas 把同一份 PTX 编排得更好了——性能有一部分永远握在这个编译器手里。

### fat binary 与 JIT
**定义**：fat binary 是把多代 SASS 与一份 PTX 打包进同一个可执行文件的发布格式；JIT 指驱动在用户机器上把 PTX 现场编译成本机 SASS 的机制（结果缓存在磁盘）。
**为什么存在**：两者配合实现前向兼容——有现成 SASS 的代直接跑（快），没有的代靠 PTX 现场编译（能跑）。
**语境例句**："新卡上第一次启动卡了十几秒，之后就正常了。" —— 意思是：首次运行触发了 JIT 编译，结果已入缓存——这是 fat binary 里没带这代 SASS 的典型症状，不是 bug。

### `-lineinfo` 与源码-SASS 对照
**定义**：一个编译选项，让机器码里保留"每条指令来自哪行源码"的映射，供 Nsight Compute 的对照视图使用。
**为什么存在**：没有映射时，性能数据只能挂在整个 kernel 上；有了它，每一行源码旁边直接标出指令和停顿——把"哪里慢"精确到行。
**语境例句**："加上 -lineinfo 重跑一遍 ncu，看是哪一行在 Long Scoreboard。" —— 意思是：用行级对照把"在等显存"这个笼统结论定位到具体的那一次读取上。
