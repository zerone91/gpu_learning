## 1. 核心概念

### 1.1 费曼起点：一串复用放大器

§01 的第一性事实——**算术免费、数据远**。既然从 HBM 取一次那么贵，活路只有一条：**取回来多用几次再扔**。整个片上层次就是为"复用"服务的一串放大器，每级拿容量换带宽/延迟（H100 量级）：

| 级 | 容量 | 相对带宽 | 延迟(量级) | 作用域 | 谁管理 |
| --- | --- | --- | --- | --- | --- |
| **寄存器** | ~256 KB/SM | 最高（每拍喂满所有 ALU） | ~0（在流水线里） | 线程私有 | 编译器 |
| **shared / L1** | ~256 KB/SM（含 shared ≤228） | 很高（~十几 TB/s/SM） | ~20–30 拍 | block（shared）/ 自动（L1） | 程序员 / 硬件 |
| **L2** | ~50 MB | 中（全芯片聚合数 TB/s） | ~200 拍 | 全芯片 | 硬件 |
| **HBM** | 80 GB | ~3.35 TB/s | ~400–800 拍 | 全芯片 | 硬件 |

> 🔑 **带宽金字塔**：寄存器 ≫ shared ≫ L2 ≫ HBM，每下一级带宽掉 ~5–10×、延迟涨一截。**优化的全部命题 = 让复用发生在尽量高的那一级。** A1 里"卡在哪一级带宽"的下钻，量的就是你的字节实际堵在了金字塔的哪一层。

### 1.2 coalescing（访存合并）：warp 的 32 地址撞上 DRAM 突发粒度

§01 给了直觉，这里量化。两个物理事实：
1. **访存按段搬**：显存/缓存以 **sector = 32 字节** 为最小事务单位；一条 **cache line = 128 字节 = 4 个 sector**。取任何一个字节，都得把它所在的整个 sector 搬回来。
2. **warp 同拍发 32 个地址**：LSU 把这 32 个地址**合并**成"覆盖它们所需的最少 sector 数"。

**效率 = 请求的有效字节 / 实际搬运字节**，直接体现在指标 **`sectors per request`**：

| 访存模式（32 线程 × 4B） | 覆盖 | sectors/request | 效率 |
| --- | --- | --- | --- |
| 连续 `a[tid]`（对齐） | 128B = 1 line | **4**（理想） | 100% |
| 连续但**未对齐**（跨线） | 横跨 2 line | 5 | ~80% |
| 步长 2 `a[tid*2]` | 256B 里只用一半 | 8 | 50% |
| 完全分散 | 每线程各一 sector | **32**（最坏） | ~12.5% |

**推论**：
- **AoS vs SoA**：array-of-structs 让"同字段"跨线程呈大步长 → 不合并；**struct-of-arrays 让同字段连续 → 合并**。这是最常见的 layout 优化。
- **向量化访存**：每线程用 `float4`（128-bit / `LDG.128`）一次取 16B → warp 取 512B、指令数减 4 倍，且照样 100% 效率、还能提 MLP（§1.6）。
- **对齐**：基址对齐到 128B，避免 5-sector 的跨线惩罚。

### 1.3 bank conflict（bank 冲突）：shared 侧的另一道关

shared memory 被切成 **32 个 bank**，每个 bank **4 字节宽**，字地址交错映射：**地址 `a` → bank `(a/4) mod 32`**（连续的 32-bit 字轮流落到 0,1,…,31 号 bank）。

规则：一个 warp 的 32 个 shared 访问，**若各落在不同 bank（或全读同一地址=广播）→ 一拍完成**；**若 ≥2 个线程访问同一 bank 的不同地址 → 冲突，串行化**（N 路冲突 = N× 慢）。

经典例子：
- `shared[tid]` → 线程 i 落 bank i → **无冲突**。
- `shared[tid * 2]` → 线程 0 和 16 都落 bank 0（0 和 32 都 mod 32 = 0）→ **2 路冲突**。
- 二维 tile `sh[32][32]` 按**列**访问 `sh[k][tid]`：列内步长 32 → 所有线程都落**同一个 bank** → **32 路冲突（最惨）**。

修复：
- **padding**：声明 `sh[32][33]`（每行多补 1 个字）→ 列步长变 33，`33·i mod 32` 遍历所有 bank → **冲突消失**。代价是浪费一点 shared。
- **swizzling（异或置换）**：不加 padding，而是把地址按 XOR 模式重排，让访问天然散到各 bank。CUTLASS / tensor-core 的 shared 布局用它——省内存、还配合 TMA/wgmma。**现代高性能 kernel 的 shared 布局几乎都是 swizzle 而非 padding。**

> 🔑 coalescing 和 bank conflict 是**同一个思想的两面**：都在解决"warp 的 32 个并发访问怎么喂进硬件的分块粒度"——HBM 侧的块叫 sector，shared 侧的块叫 bank。**warp 内不齐 → 两边都串行化**（呼应 §03 的"warp 内不齐"主线）。

### 1.3+ 深挖：swizzle 的实现细节与代价

**为什么不用 padding，非要 swizzle？** padding（`sh[32][33]`）能消冲突，但有两个硬伤：
1. **浪费 shared**：多一列即 ~1/32；宽冲突要补更多。shared 是占用率的约束（§02），寸土寸金。
2. **破坏 2 的幂对齐**——致命。tensor-core 的 `ldmatrix`（shared→寄存器的矩阵加载）和 128-bit 向量访存**要求 2 的幂对齐**；padding 后行步长变成 33（非 2 的幂）→ **根本没法用 `ldmatrix`/wgmma**。**这就是 CUTLASS 的 tensor-core GEMM 一律用 swizzle 而非 padding 的决定性原因。**

**机制：XOR 是一个双射（置换）。** 不改变元素总数、不占额外内存，只是把"逻辑位置 → 物理位置"的映射打乱，让原本撞同 bank 的访问散开。

**手算一个例子**（32×32 的 4B tile，行主序）：
- 原始：`offset(r,c) = r*32 + c`，`bank = offset % 32 = c`（`r*32 mod 32 = 0`）。
  - 行访问（固定 r）：bank 0..31 各异 → 无冲突。
  - **列访问（固定 c，变 r）：全是 bank c → 32 路冲突。**
- swizzle：物理列 `c' = c XOR r`，即 `offset'(r,c) = r*32 + (c XOR r)`，`bank = (c XOR r) % 32`。
  - **固定 c、变 r**：`c XOR r` 遍历 0..31（与定值 XOR 是双射）→ **32 个不同 bank，冲突消失**。
  - **固定 r、变 c**：`c XOR r` 仍是 0..31 的一个排列 → bank 全异、且仍落在同一行的 32 个槽里（连续区）→ 行访问照样一拍完成。
- **零额外内存，列/行访问都无冲突。** 代价只是每次算地址多一个 XOR。

**CUTLASS / CuTe 的通式 `Swizzle<B, M, S>`**：
```
offset ^= ((offset >> S) & ((1<<B) - 1)) << M
```
- **M（MBase）**：低 M 位**不参与** swizzle——保住"最小连续块"（如一个 128-bit 向量 = 8 个 bf16），让向量访存不被打散。
- **B（BBits）**：swizzle 字段的位宽——跨多少个 bank/相位置换（2^B 种模式，常取 log2(bank 数)=... 之类的小值）。
- **S（SShift）**：两个被 XOR 的位段的距离——把"行选择位"XOR 进"bank 选择位"。
- 上面的 32×32 例子就是 `Swizzle<5, 0, 5>`：取高 5 位(r) XOR 进低 5 位(c)。真实 CUTLASS 里按 (tile 形状 × dtype × 向量宽度) 取具体的小 B/M/S（如 `Swizzle<3,3,3>` 之类）。

**现代：TMA 的硬件 swizzle（让 swizzle 近乎免费）。** Hopper 的 TMA 描述符支持 `SWIZZLE_{32B,64B,128B}` 模式——**搬运引擎在 `global→shared` 的过程中直接把数据按 swizzle 布局写入**，消费端 `ldmatrix`/wgmma 用匹配的 swizzle 读。于是 swizzle 由**硬件在拷贝时完成**，SM 上不再花地址运算指令——这是 Hopper/Blackwell 高性能 kernel 的标配。

**swizzle 的代价（老实列出）：**
1. **地址运算开销**：软件 swizzle 时每次 shared 访问多几条整数指令（XOR/shift/mask），压整数 pipe、增指令数（TMA 硬件 swizzle 可免掉这条）。
2. **复杂度 / 正确性风险**：写入端与**每一个**读取端的 swizzle 函数必须**完全一致**，位运算错一位 → 静默算错或冲突复现。极难手写 → 所以活在库里（CUTLASS `Swizzle<>` / CuTe layout）。
3. **强绑定具体布局**：一套 swizzle 只对特定 (tile 形状, dtype, 访问模式, 向量宽度) 最优，换组合要重新设计，非通用。
4. **只治 bank 冲突**：与 coalescing（HBM 侧）正交，别指望它解决全局访存问题。
5. **约束 tile 形状**：swizzle 周期与 tile 维度相互作用，有些形状干净、有些留残余冲突。

> 🔑 **一句话**：swizzle = **用几条 XOR 指令（或 TMA 免费）换掉 padding 的内存浪费 + 对齐破坏**，代价是复杂度和布局绑定。它是"让 shared 复用配合 tensor-core"的关键黏合剂，也是 CUTLASS/CuTe 最难读的部分之一。

### 1.4 一次 global load 的完整旅程

```
LSU 算 32 个地址 → 合并成 sector 请求
  → 查 L1（命中?→返回）
  → 未命中 → 查 L2（命中?→返回）
  → 未命中 → 发 HBM（~几百拍）
数据回来 → 写入目标寄存器 → 记分牌清屏障（§02）→ 依赖它的指令变就绪
```

期间该 warp 卡住（`Long Scoreboard`），调度器切别的 warp 顶上（§02）。**"算得快"在这条链上几乎不占时间，大头是这趟几百拍的往返**——这就是 memory-bound 的微观真相。

## 2. 关键机制 / 为什么这样设计

### 2.1 cp.async / TMA：从访存通路角度为何存在

看普通 load 想把数据搬进 shared 复用的老路径：
```
global → L1/L2 → 寄存器 → （再 STS 存进 shared）
```
数据**穿过寄存器**：既占寄存器（压 occupancy，§02 §2.2），线程还得**卡住等 load 回来**才能转存。两头都亏。于是：
- **`cp.async`（Ampere）**：`global → shared` **直连，绕过寄存器、不阻塞线程**（SASS `LDGSTS`）。省寄存器 + 异步。
- **TMA（Hopper）**：专用引擎做**多维块**的 `global↔shared` 批量搬运，自带边界与 **swizzle**，一个线程一条描述符搞定，把"32 线程各算地址"整个卸掉。

> 🔑 这就是 §02 §2.6 异步流水的**访存通路根因**：把"搬运"从"计算的寄存器/发射资源"里剥离出来，才能让计算和访存真正重叠。

### 2.2 喂满带宽的 Little 定律：MLP 与 occupancy 的另一面

§02 讲占用率藏"延迟"，这里是它的**带宽面**。要榨干 HBM：
> **在途字节 = 带宽 × 延迟 ≈ 3.35 TB/s × 500 ns ≈ 1.7 MB** 必须同时"在飞"。

一次访存事务才几十~几百字节 → 得**同时有上万个访存请求悬空**。而每个线程能挂的在途请求有限（受 **MSHR / LSU 队列**上限约束），所以需要 **足够多 warp × 每线程若干在途 load** 才凑得够——这就是"**MLP（memory-level parallelism，访存级并行）**"。

**这正是 A1 里"memory-bound 时占用率才重要"的机理**：memory-bound kernel 需要足够 occupancy（或每线程多发几个独立 load 提 MLP）来把在途请求堆到 1.7MB，否则带宽喂不满、SOL 的 Memory% 上不去。反过来，若 MLP 已够，再加 warp 也无益（§02 §2.1 的饱和）。

### 2.3 只读路径与 L2 驻留（进阶拨盘）

- **只读数据缓存**：`__restrict__` + `const`（或 `__ldg`）让编译器走**只读/纹理缓存**路径，减少 L1 压力、放宽别名分析。
- **L2 驻留控制（Ampere+）**：`cudaAccessPolicyWindow` 可把一段热数据**钉在 L2**（persisting），让反复访问的小表（如 embedding、KV 索引）常驻 L2 而非每次回 HBM——在 A1 的"卡 L2 还是 HBM"里能直接改变落点。

### 2.4 进阶四问（MSHR / swizzle-fragment / L2 persisting / TMA 描述符）

#### (1) MSHR 与在途请求上限，怎么估"喂满带宽的最小 occupancy"

- **MSHR（Miss Status Holding Register）**：追踪每个"未完成 miss"的表项，L1/L2 各有一组；**满了就不能再发新 miss，后续访存 stall**——这是 MLP 的物理上限。
- ⚠️ **精确数量各架构基本不公开**，只能靠微基准反推（如 Jia 等《Dissecting NVIDIA GPU via microbenchmarking》系列），量级是"每 SM L1 数十个 MSHR"。**别背数字，用方法。**
- **估算法（Little 定律，按 SM 摊）**：
  1. 全芯片在途字节 = BW×延迟 ≈ 3.35 TB/s × 500 ns ≈ **1.7 MB**。
  2. 每 SM 摊（H100 ~132 SM）≈ **~13 KB/SM 必须在飞**。
  3. 换成 warp-load：
     - 标量 4B、合并成 128B/warp-load → 需 ~13KB/128B ≈ **100 个在途 warp-load/SM** → 64 warp 槽位下要**每 warp ~1.6 个在途 load（MLP≈2）**。
     - **向量化 `float4`（512B/warp-load）** → 13KB/512B ≈ **25 个** → 连 32 warp（50% 占用）都够。
- 🔑 **结论**：**向量化 128-bit 访存能成倍降低"喂满带宽所需的 occupancy"**（每个在途请求多搬 4 倍字节）。所以 memory-bound kernel 先向量化，再谈提占用。真实上限被 MSHR 卡住时，光加 warp 也没用 → **实测法：扫 occupancy×向量宽，看 `DRAM Throughput` 何时不再涨，那个平台就是上限。**

#### (2) swizzle 怎么和 tensor-core fragment 对齐；CUTLASS shared layout 怎么读

- **三方必须协同设计**：TMA 写入布局 → `ldmatrix` 读取模式 → wgmma 需要的**寄存器 fragment**（每个线程持有矩阵的哪几个元素）。swizzle 的 XOR 模式是**专门挑的**，使得 `ldmatrix` 生成的那组"按行跨步"的地址正好落在**不同 bank**，同时读进来的数据恰好摆成 wgmma 要的 fragment。
- 三者绑定的变量：tile 的 major（K-major / MN-major）、dtype（bf16=2B / fp8=1B → 每 bank 几个元素）、`ldmatrix`/wgmma 的固定访问模式。**错配 → 要么 bank 冲突复现，要么 fragment 不对、算错。**
- **CuTe 怎么读**：共享布局写成 `Swizzle<B,M,S> ∘ Layout<Shape,Stride>`——底层 `(M,N):(stride)` 给逻辑→线性偏移，上面的 `Swizzle` 再置换。**你不用手推**，而是选一个**匹配的 atom**，如 `GMMA::Layout_K_SW128_Atom<bf16>`（含义：K-major、128B swizzle、bf16 的 wgmma 操作数布局），CuTe 保证它对 `ldmatrix`/wgmma 兼容且无冲突。atom 名里的 `SW128/64/32` = 与 TMA 描述符匹配的 swizzle 字节粒度。
- 🔑 **读法心法**：认出 `Sw<B,M,S> ∘ (shape:stride)` 结构，atom 名编码了 (swizzle 字节, major, dtype)。**swizzle 之所以是库 atom 而非手写，正因为它要同时满足"TMA 能写、ldmatrix 无冲突读、wgmma 直接用"三个约束。**

#### (3) L2 persisting 的容量/收益权衡与多 kernel 竞争

- **机制（Ampere+）**：`cudaAccessPolicyWindow` 把一段 global 标为 persisting，其访问优先留 L2；用 `cudaLimitPersistingL2CacheSize` **预留一块 L2 专供 persisting**（如 A100 最多 ~30MB / 40MB，H100 类似比例）。窗口带 `hitRatio`。
- **权衡**：
  - 预留给 persisting 的越多，留给普通 streaming 的 L2 越少 → 可能反伤别的访问。
  - **热区 ≤ 预留大小**才划算；若窗口 > 预留 → 抖动，须设 `hitRatio = 预留/窗口` 只随机缓存一部分，避免全抖。
  - **最佳场景**：小而热、跨多次/跨 kernel 反复读的数据——embedding 表、KV cache 索引、归一化统计、小权重。**大工作集或只读一次（streaming）→ 无用。**
- **多 kernel 竞争**：L2 全芯片共享，并发 kernel 争同一块预留区。规划：① 只钉"跨 kernel 复用"的数据；② 总钉住量 ≤ 预留；③ 用完把窗口 `num_bytes=0` 复位，别饿死后续 kernel；④ MPS/多租户下 persisting 是全局的，要协调。收益量级：HBM 读变 L2 命中 → 省 ~2–4× 延迟并卸 HBM 带宽。

#### (4) TMA 多维描述符如何影响 coalescing/对齐；OOB 填充代价

- **描述符 `CUtensorMap`**（`cuTensorMapEncodeTiled` 生成）：描述 global 里一个多维张量（≤5D）——基址、各维尺寸/步长、box(tile) 尺寸、dtype、swizzle 模式、OOB 填充值。
- **coalescing**：TMA **按整块搬**，经典"warp 32 地址合并"不再适用——**引擎自己生成高效的大而对齐的突发**。但仍看数据布局：**最内（连续）维对齐 global 连续内存 → 高效**；外维大步长 → 引擎发多笔较小突发（本质同 coalescing，只是引擎管）。
- **对齐硬约束**：global 基址与步长通常需 **16B 对齐**；shared 目标在 swizzle 模式下需 **128B 对齐**；**128B swizzle 要求内维是 swizzle 宽度的整数倍**。错了 → 描述符创建失败或性能塌。
- **OOB 填充**：TMA 支持 tile 悬在张量边界外（如 N 不整除 tile 的最后一块），**引擎自动把越界元素在 shared 里填 0**（或指定值），**无分支、无谓词**。代价拆两块：
  - **传输侧便宜**：越界部分不读 global，只在 shared 写零。
  - **计算侧仍付 tile 量化**：填零的行照样过 wgmma、产生零贡献 → 就是 A2 的 **tile 量化**浪费。
- 🔑 **对比 §03**：手写边界要谓词化 + 分支 → **控制发散**；**TMA 的 OOB 填零是无分支、无发散的**——把"边界发散"换成了"引擎零填 + tile 量化计算"。这是现代 kernel 处理 ragged 边界的标准做法。

## 4. 最新架构落点（时效锚点 · 知识截至 2026-01）

- **Hopper**：**TMA**（多维 + swizzle 的批量搬运）、**Thread Block Cluster + DSM**（簇内 block 互访 shared，在 shared 与 L2 间**多插一级复用**）、shared 上限 228KB、L2 ~50MB。
- **Blackwell**：**TMEM**（给 Tensor Core 的独立内存空间，又一层）、HBM3e（B200 192GB / B300 288GB，~8 TB/s）、NVLink5。金字塔每代在**增层**（§01 已记）。
- **向量化 128-bit 访存**仍是所有架构的通用铁律。
- **AMD（CDNA / MI300X）**：**LDS 64KB/CU、32 bank**（bank conflict 同理）；多一层 **Infinity Cache** 夹在 L2 与 HBM 间（A1 提过：定位要多问一句"卡 Infinity Cache 还是 HBM"）；HBM3 192GB。工具 rocprof / Omniperf。

## 5. 和其它模块的挂钩

- 复用放大器、"算得起取不起" → 承接 **§01 §4.5**
- `Sectors/Request` / 各级带宽定位 → **A1**（Memory Workload 下钻的机理）
- coalescing/bank conflict 都是"warp 内不齐"的代价 → **§03**（控制发散 vs 访存发散）
- cp.async / TMA / MLP → **§02 §2.6**、**§05 同步**
- shared 的手动复用 + swizzle + 双缓冲 → **对照脉动阵列 scratchpad + tiling** → **模块 02 第 04**
- tiling 决定复用发生在哪一级 → **模块 04 kernel 层 + 映射问题**

## 7. 我的困惑 / 待深挖

- ✅（已答，§2.4-1）MSHR 精确数各架构不公开（量级数十/SM）；用 Little 按 SM 摊估最小 occupancy，**结论：向量化 128-bit 成倍降低所需占用**；实测法扫占用×向量宽看 DRAM 平台。**遗留**：反推真实 MSHR 的微基准怎么设计？
- ✅（已答，§1.3+ / §2.4-2）swizzle=XOR 双射保 2 的幂对齐；`Swizzle<B,M,S>` 通式；TMA 硬件 swizzle；CuTe 选 `GMMA::Layout_*_SW*_Atom` 匹配 (major,dtype,swizzle)，三方(TMA/ldmatrix/wgmma)协同。**遗留**：atom 的 bit 级推导。
- ✅（已答，§2.4-3）L2 persisting：`cudaAccessPolicyWindow`+预留区；热区≤预留才划算、否则设 hitRatio 防抖；只钉跨 kernel 复用的小热区，用完复位。
- ✅（已答，§2.4-4）TMA 描述符：按整块搬（引擎管 coalescing）、16B/128B 对齐硬约束；OOB 引擎零填**无分支无发散**（对比 §03），但计算侧仍付 tile 量化（对比 A2）。
