# 附录 A1 · 占用率算例 与「受限于哪个位置」的定位方法

> **所属模块**：模块 01 · SIMT 核的物理实现（横跨 §01 SM 解剖 / §02 occupancy 的方法论附录）
> **状态**：🟨 学习中（第一版，知识截至 2026-01）
> **一句话主旨**：给定一个算子，先用"资源除法"算它的理论占用率，再用"算术强度 + 主导 pipe"做量级判断，最后用 Nsight Compute 的 Speed-of-Light → Workload → Warp-State 三级下钻，**精确定位它卡在哪个具体位置**（HBM / L2 / shared / FMA / Tensor / MUFU / 发射 / 延迟 / 同步 / 尾部）——"compute-bound / memory-bound"只是第一层，真正要答的是"bound 在哪一个部件"。

## 1. 各架构关键参数速查表（做任何占用率计算的地基）

> ⚠️ 数字为**据公开资料的量级**，实际以各架构白皮书 / `cudaOccupancyMaxActiveBlocksPerMultiprocessor` / Nsight 为准。占用率的**算法**跨架构不变，变的只是这几个常数。

| 每 SM/CU 资源 | A100 (GA100, SM80) | **H100 (GH100, SM90)** | Ada (AD102, SM89) | Blackwell (GB100, SM100) | AMD MI300X (CDNA3) |
| --- | --- | --- | --- | --- | --- |
| 32-bit 寄存器 / SM | 65536 (256KB) | 65536 | 65536 | 65536 | VGPR 文件/SIMD（另计） |
| Max warp / SM | 64 | 64 | 48 | 64 | wavefront：每 SIMD ~8–10 |
| Max 线程 / SM | 2048 | 2048 | 1536 | 2048 | — |
| Max block / SM | 32 | 32 | 24 | 32 | — |
| Shared / SM（可配上限） | 164 KB | 228 KB | 100 KB | ~228 KB | LDS 64 KB / CU |
| FP32 lane / SM | 64 | 128 | 128 | 128 | SIMD16 ×4 |
| Tensor / Matrix 引擎 | 4（3rd gen） | 4（4th gen, +TMA/wgmma） | 4（4th gen, +FP8） | 4（5th gen, +TMEM/FP4） | Matrix Core（MFMA） |
| Max 寄存器 / 线程 | 255 | 255 | 255 | 255 | — |

**读表要点**：占用率被"寄存器 / shared / warp·block 槽位"三条里最紧的一条卡住（§02 §1.3）。注意 **Ada 只有 48 warp/1536 线程**——同样 kernel 在 Ada 上的占用率天花板和 H100 不同，这是消费卡 vs 数据中心卡的一个常见坑。AMD 换了词（CU/wavefront/VGPR/LDS）但**除法完全一样**。

## 2. 三个"计算模式"的占用率算例（以 H100 为例）

### 例 1 · Element-wise（`y=2x`）—— 访存密集、几乎无 ILP

- 寄存器：~16–20 个/线程 → 65536/20 ≈ 3276 线程，被 **2048 线程上限**先封 → 寄存器不构成约束。
- shared：0。
- block=256 线程 → warp/block 槽位轻松满足。
- **理论占用率 = 100%**（三条约束都不紧）。
- ⚠️ 但占用率高**不等于**跑得快：它是 memory-bound，占用率的作用只是"挂足够多在途 load 喂满 HBM"。到 100% 后，性能由 HBM 带宽封顶，再无提升空间（→ 见 §3 定位）。

### 例 2 · FP32 分块 GEMM（非 Tensor Core，经典 shared-tiled）—— 计算密集、高 ILP

设 block=256 线程，每线程算一个 **8×8 微块**（64 个 FP32 累加器 → register blocking，制造高 ILP）：

- 寄存器：64 个累加器 + 操作数/索引/指针 ≈ 常被 `-maxrregcount` 或编译器定到 **~128 个/线程**。
  - → 驻留线程 = 65536 / 128 = **512 线程 = 16 warp** → block=256 则只 **2 个 block** 驻留。
  - → **占用率 = 512/2048 = 25%**，且**受限于寄存器**。
- shared：双缓冲的 A 片(128×8) + B 片(8×128)，FP32：(128×8 + 8×128)×4B ×2 buffer ≈ **16 KB/block**。228KB 能放 14 个 block → shared **不是**约束。
- **结论：寄存器-bound，占用率 25%——但这是刻意的**：高 ILP + 深流水已把延迟藏住（Volkov，§02 §2.3）。这里追求 100% 占用率反而要砍累加器、砍 ILP，得不偿失。

### 例 3 · Softmax / Reduction —— 访存密集 + 含超越函数

- 寄存器：中等（~32–48）→ 占用率可较高（50–100%）。
- shared：用于块内归约，几十~上百字节/线程量级，通常不紧。
- **占用率通常不是瓶颈**；真正的坑在别处：`exp()` 走 **MUFU/SFU pipe**（吞吐远低于 FMA），以及若未融合则反复读写 HBM。→ 这类算子最能体现"受限于具体位置"（见 §3.4）。

> 小结：**占用率算的是"能驻留多少"，但"该不该追高"取决于算子受限于什么**。所以必须有 §3 的瓶颈定位。

## 3. 核心方法：一个算子"受限于哪一个具体位置"

分两条腿走：**先分析法估量级，再 profiler 下钻定位。**

### 3.1 分析法：算术强度 + "compute-bound 到底 bound 在哪条 pipe"

第一层是经典 roofline：**算术强度 AI = FLOPs / 访存字节**，与**机器平衡点**（峰值 FLOP/s ÷ 峰值 B/s）比：AI 低于平衡点 → memory-bound，高于 → compute-bound。

但你要的粒度更细——**"compute-bound"必须问"bound 在哪条 pipe"**，因为不同 pipe 峰值差一两个数量级（以 H100 量级）：

| pipe | 峰值量级 | 对应 AI 平衡点（÷3.35TB/s HBM） |
| --- | --- | --- |
| FP32 FMA | ~67 TFLOP/s | ~**20** FLOP/byte |
| FP16/BF16 Tensor | ~990 TFLOP/s（稠密） | ~**300** FLOP/byte |
| FP8 Tensor | ~1979 TFLOP/s | ~**590** FLOP/byte |
| MUFU（exp/rsqrt…） | 约 FMA 的 1/4~1/8 | 极低——**softmax 易在此成瓶颈** |

**推论**：要吃到 Tensor Core，AI 得 >300——所以大 GEMM 必须重度 tiling（复用）、attention 必须融合（FlashAttention），否则一定 HBM-bound。**同理，"memory-bound"也要问 bound 在哪一级**（HBM / L2 / shared）。

**一个能手算的对照**（H100, FP16）：
- **大 GEMM** M=N=K=4096：FLOPs=2·4096³≈1.37e11；若各读一次 A/B/C，字节≈3·4096²·2≈1e8 → **AI≈1370 ≫ 300 → Tensor-pipe-bound**。
- **GEMV** M=4096,N=1,K=4096：FLOPs≈3.4e7；字节≈(MK+K+M)·2≈6.7e7 → **AI≈0.5 → HBM-bound**。
- 同为"矩阵乘"，一个卡 Tensor Core、一个卡 HBM——**这就是为什么 decode 阶段（GEMV 型）和 prefill 阶段（GEMM 型）的优化手段完全不同。**

### 3.2 瓶颈位置的完整清单（"bound 在哪"的可选项）

| 瓶颈位置 | 典型算子 | Nsight Compute 信号 |
| --- | --- | --- |
| **HBM 带宽** | elementwise、大 reduction、未融合 attention | Memory SOL 高、`DRAM Throughput`≈峰值、stall 多为 `Long Scoreboard` |
| **L2 带宽** | 中等复用、部分命中 L2 | L2 throughput 高而 DRAM 未满 |
| **Shared 带宽 / bank conflict** | shared 密集的 stencil/GEMM | Shared SOL 高、`Shared Bank Conflicts` 高 |
| **FP32/FMA pipe** | FP32 稠密 GEMM/卷积 | Compute SOL 高、`FMA` pipe util≈峰值 |
| **Tensor pipe** | 低精度 matmul | `Tensor` pipe active≈峰值 |
| **MUFU/SFU pipe** | softmax/gelu/exp 密集 | `XU`/SFU util 高（峰值低，易中招） |
| **指令发射 / dispatch** | 指令混杂、地址计算/开销指令多 | Issue Slot util 高，但各 pipe 都不满 → issue-bound |
| **延迟（占用率/ILP 不足）** | 低占用 + 长依赖链 | SOL 全低、`Eligible Warps`<1、stall `Long/Short Scoreboard`+`No Eligible` |
| **同步 barrier** | `__syncthreads` 频繁 | stall `Barrier` 高 |
| **尾部 / wave 量化** | grid 太小、block 数不是 SM 整数倍 | `Achieved` ≪ `Theoretical` occupancy、波数少 |

### 3.3 Nsight Compute 三级下钻（把瓶颈钉到部件）

> 这就是"如何评估受限于哪一个具体位置"的**可执行流程**。

1. **看 Speed-of-Light（SOL）**：`Compute (SM) Throughput %` vs `Memory Throughput %`，谁高就贴近谁的天花板。
   - **两个都低（<~60%）？→ 既非 compute 也非 memory bound，而是 latency-bound**（占用率/ILP 不足或依赖链长）→ 跳第 4 步。
2. **Memory 高 → 进「Memory Workload Analysis」**：看哪一级（DRAM / L2 / L1·shared）顶到峰值 → 那一级就是 bound。
3. **Compute 高 → 进「Compute Workload Analysis」**：看哪条 pipe（FMA / ALU / FP64 / Tensor / LSU / XU）顶峰 → 那条 pipe 就是 bound。
4. **两者都不高（latency-bound）→ 进「Warp State Statistics」**：看**主导 stall 原因**——
   - `Long Scoreboard` = 等 HBM 结果（访存延迟没藏住）
   - `Short Scoreboard` = 等 shared/MUFU 等较短变长依赖
   - `Wait` = 等定长依赖（ILP 不足，编译器 stall 位在生效）
   - `Barrier` = 等 `__syncthreads`
   - `No/Not Eligible`、`Not Selected` = 占用率不足 / 调度竞争
5. **交叉验证「Scheduler Statistics」**：`Eligible Warps Per Scheduler`（<1 说明缺牌）、`Issue Slot Utilization`。

**一句话决策树**：`SOL 谁高？ → 高的那侧钻到具体级/pipe；都不高 → 看 stall 原因定位延迟来源。`

### 3.4 融合如何"搬动"瓶颈：naive vs Flash attention

- **naive attention**：把 S=QKᵀ（N×N）**写回 HBM**，softmax 再读写它，最后 ×V。AI 极低 → **HBM-bound**，且 `exp` 压在 **MUFU pipe**。
- **FlashAttention**：融合，把 S 的 tile 留在 **shared/寄存器**，从不把 N×N 落 HBM → **AI 抬高，瓶颈从 HBM 搬到 Tensor pipe（QKᵀ、×V）+ MUFU（exp）**。
- 到了 FA-3（Hopper）：再用 §02 §2.6 的 **warp 专化 + ping-pong**，让 Tensor pipe 和 MUFU/softmax 重叠，把"MUFU 拖慢 Tensor"这个新瓶颈也缓解。

> 🔑 **本质**：优化的本质常常不是"消灭瓶颈"，而是**把瓶颈从便宜的资源（HBM）搬到贵的资源（Tensor pipe）**，直到贴着最贵的那条 pipe 的峰值——那才是这块硅片在这个算子上的真正上限。

## 5. 最新架构落点（时效锚点 · 知识截至 2026-01）

- **Blackwell（SM100）**：FP4 Tensor pipe 把 compute 平衡点进一步推高（AI 需更大才 compute-bound），**更逼着算子融合/提复用**；TMEM 把累加器移出寄存器 → 例 2 那类 GEMM 的"寄存器-bound 占用率"图景会松动。
- **Nsight Compute 的 SOL/Roofline 视图**持续跟进新 pipe（FP8/FP4 tensor、TMA），是判断"bound 在哪"的一等工具。
- **AMD**：用 `rocprof` / Omniperf，概念一一对应（CU 占用率、LDS、Matrix Core util、HBM/Infinity Cache 带宽）；MI300X 多了一层 **Infinity Cache**，相当于在 L2 和 HBM 间再插一级，定位时要多问一句"卡在 Infinity Cache 还是 HBM"。
