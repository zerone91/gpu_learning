## 1. 费曼第一步：先把问题讲给外行听（不许用行话）

想象一座**数学加工厂**：车间里的工人（算术单元）算一道乘法只要**一瞬间**。但原料（数据）不在车间，堆在**几百米外的仓库**（HBM 显存），派人去取一趟,来回要**走 400~600 步**（时钟周期）。

现在问题来了：如果车间**一次只做一个订单**——工人算一步（1 步），然后干等原料回来（400 步），再算一步……那么**工人有 400/401 的时间在发呆**，利用率 0.25%。你花大价钱买的算力，99.75% 在晒太阳。

**这就是那堵墙，GPU 的一切设计都是为了翻过它。** 行话叫它「**内存墙 / 延迟墙**」，但先别管名字——记住那个画面：**工人很快，仓库很远，一等就是几百步。**

> 📌 一个能省事的事实：现代 GPU 的算力和带宽严重不对称。H100 一秒能做 ~10¹⁴ 次浮点运算，但显存带宽"只有" ~3 TB/s，而且**单次访问延迟 ~400+ 周期**。在你等一次数据回来的时间里，算术单元本可以做上千次运算。**"算得起、取不起"是这颗芯片的第一性事实。**

## 2. 费曼第二步：翻墙有两条路，GPU 选了反直觉的那条

面对"工人快、仓库远"，人类只有两种翻墙思路：

### 路 A（CPU 的路）：想尽办法**避开**等待
- 在车间旁边建一个**大储物柜**（多级 cache），把常用原料囤在手边——**空间局部性**。
- 让**一个**工人变聪明：能预测接下来要用什么，提前派人去取（预取）；手头这步卡住了，就在**同一张订单**里找几步不相干的活先干（乱序执行 / 超标量）。
- 代价：为了让**单个**工人不闲着，得给他配一整套昂贵的辅助班子（分支预测器、乱序调度器、寄存器重命名）。**芯片上大半的晶体管花在了"管理"上，而不是"计算"上。** 这优化的是**单条订单的完成时间（延迟）**。

### 路 B（GPU 的路）：不避，**忍**——用海量并发把等待填满
- 不试图让任何一个工人变快。相反，**同时接下几千张订单**。
- 工人给订单 1 算一步，然后订单 1 去等原料的这 400 步里，工人**扭头去给订单 2、3、4…… 各算一步**。等他轮回到订单 1，原料早回来了。
- **工人从头到尾没停过手，可他谁也没"加速"——他只是永远有下一张能干的订单。** 这优化的是**单位时间吞掉多少订单（吞吐）**。

> **这就是 CPU 与 GPU 的真正分水岭**，不是"核多核少"这种表面差异，而是：
> **CPU 花晶体管去"消灭延迟"（让一条流水线尽快跑完）；GPU 花晶体管去"容忍延迟"（堆够多的独立流水线，谁停了都有人顶）。**
> 一个是"避"，一个是"忍"。SM 走的是"忍"。**记住这一句，后面每个部件都是它的推论。**

## 3. 中心类比：一场同时下 50 盘的车轮战

把"路 B"具象成一个画面，整节都靠它串起来：

> 一位大师同时和 50 个人下棋（车轮战 / simultaneous exhibition）。她在 1 号棋盘落一子（1 秒），然后**趁 1 号对手思考的那几分钟**，走到 2 号、3 号…… 一路把 50 盘各落一子。等她转回 1 号，对手已经落子了。**大师全程不停手，可她的思考速度一点没变——她只是永远有下一盘能走。**

这个类比里，每样东西都精确对应 SM 的一个部件，后面逐个兑现：

| 类比里的东西 | 对应 SM 里的 | 本质 |
| --- | --- | --- |
| 那位大师（一套发招的手 + 脑子） | 一个**子分区**的发射端 + 执行单元 | 唯一稀缺、要喂饱的资源 |
| 一盘棋 | 一个 **warp**（一束线程） | 一份可独立推进的工作 |
| 对手思考的几分钟 | **访存延迟** | 要被填满的空窗 |
| "得有 50 盘才够她不闲着" | **occupancy** | 并发量必须够大 |
| 每盘棋摆在自己的桌上、不收摊 | **寄存器堆常驻** | 切换免费的前提 |
| 大厅里桌子数量有限 | 寄存器/shared 是**固定资源** | occupancy 的天花板 |
| "对 32 盘同一开局的棋，喊一嗓子一起走" | **warp 锁步 / SIMT** | 摊薄发招的动作 |

## 4. 从类比长出硬件（每个部件都是被逼出来的）

### 4.1 到底要"多少盘棋"才够？—— 这不是拍脑袋，是 Little 定律

大师转一圈 50 盘要几分钟，正好等于对手思考的时间——所以她刚好不闲着。**盘数少了她会空等，多了是浪费桌子。** 这个"刚好"的数量能算出来：

> **要填满延迟所需的并发量 = 延迟 × 吞吐率**（排队论里的 **Little 定律**）。

套到显存上：要把 3 TB/s 的带宽喂满，且每次访问延迟 ~500 ns，那么**任一时刻必须有约 `3e12 × 500e-9 ≈ 1.5 MB` 的数据"在途"**（已发出、还没回来）。一次访问才搬几十~上百字节 → **你必须同时有成千上万个访存请求悬在空中**，才能榨干带宽。

**成千上万个并发请求，就得有成千上万个线程。** 这就是为什么一个 SM 要能同时驻留 **2048 个线程（64 个 warp）**——不是"多多益善"的口号，而是**被延迟和带宽的乘积逼出来的物理下限**。占用率（occupancy）不足，本质上就是"在途请求不够多、带宽喂不饱、延迟没藏住"。

> 🔑 **本质**：GPU 需要海量线程，不是因为"任务天生并行"，而是因为 **Little 定律**——要藏住几百周期的延迟、喂饱几 TB/s 的带宽，在途工作量必须足够大，而在途工作量只能靠"很多线程各自挂着一笔访存"堆出来。

### 4.2 为什么"切换棋盘"必须免费 → 巨大的寄存器堆

大师从 1 号走到 2 号，**几乎不花时间**。这是车轮战能成立的隐含前提：如果每次换盘都要把上一盘"收进盒子、下一盘从照片重新摆好"，那换盘的成本比对手思考还高，一切白搭。

秘诀是：**每盘棋自始至终摊在自己的桌上，从不收摊。** 大师换盘 = 换个人站过去，棋局状态一直在桌面上。

对应到硬件，"棋局状态"就是每个线程的**寄存器**（它算到一半的中间值、循环变量、指针……）。要让 warp 切换**零开销**，就绝不能做"保存现场 / 恢复现场"——**每个驻留线程的寄存器必须一直物理地待在寄存器堆里。** 于是：

> 寄存器堆得大到能**同时装下所有 2048 个线程的全部现场**。 2048 线程 × 每线程几十个寄存器 = 每 SM **65536 个 32-bit 寄存器 = 256 KB**——比 L1 还大。

**这里藏着一个最容易被误解、也最能体现本质的点：**

> 在 CPU 上，寄存器意味着「**快**」——数量极少（架构寄存器 ~32 个），是流水线最贴身的高速暂存。
> 在 GPU 上，寄存器意味着「**大 / 容量**」——数量巨大（65536 个），它是**决定能并发多少线程的容量资源**。
> **同一个词，两种芯片上扮演相反的角色。** 谁要是以为"GPU 寄存器多是为了更快"，就没抓住本质：它多，是为了**容纳整个线程动物园的现场，好让切换免费、好让延迟被藏住**。

由此还直接推出后面的 occupancy：一个线程的现场越"占地方"（用的寄存器越多），一张桌子摊得越大，大厅里能摆的桌子（能驻留的 warp）就越少。

### 4.3 为什么 32 个线程要绑成一束锁步走 → SIMT 是"控制开销的团购"

再看车轮战一个细节：假设 50 个对手里有 32 个人下的是**同一个开局、同一套棋谱**。大师没必要对这 32 盘各想一次，她可以**喊一嗓子"你们都走 e4"**，一个决策、32 盘同时落子。

这正是 GPU 最核心的取巧——**SIMT**。回到"路 B"：既然要跑几千个线程，如果给**每个**线程都配一套完整的"取指令→译码→调度"控制逻辑，那光是管理的开销就会把算术淹没（这正是 CPU 的病）。GPU 的解法是**团购控制开销**：

> 把 **32 个线程捆成一个 warp，共用一个程序计数器、共用一次取指和译码**。硬件只译码**一条**指令，就驱动 32 条数据通路同时算。**控制逻辑的成本被 32 个数据元素摊薄了。**

这一步是 GPU 高能效的**根**：省下来的控制晶体管全部拿去堆算术单元（ALU）。所以同样面积，GPU 的算术吞吐远高于 CPU——**代价是这 32 个线程必须步调一致（锁步）**。一旦它们在 `if/else` 上意见相左（分支发散），"喊一嗓子"就失效了，只能分批走，吞吐打折——这就是第 03 节的主题，而它的病根，正是此处这个"团购"设计。

> 🔑 **本质**：SIMT ≠ "GPU 天生并行"。它是一套**把昂贵的控制硬件（取指/译码/调度）在 32 条数据通路上摊薄**的经济方案。省下的晶体管变成算力，代价是"必须齐步走"。**SIMD 的执行效率，穿着 MIMD（每线程独立）的编程外衣。**

### 4.4 occupancy 的本质：一道"固定资源的除法"

现在把 4.1（要很多 warp）和 4.2（每个 warp 占资源）合起来，occupancy 就水落石出了。大厅里的资源是**死的**：

- 寄存器堆：**固定** 256 KB（65536 个寄存器）
- shared memory：**固定** ~228 KB
- warp 槽位：**固定** 64 个

而每个线程的**胃口**是活的：它用多少寄存器、这个 block 要多少 shared memory，由你的 kernel 决定。于是：

> **能同时驻留多少 warp = 固定资源 ÷ 每 warp 的胃口**，取三条约束里最紧的那个。

举个能算的例子：若每线程用 **64 个寄存器**，则 65536 ÷ 64 = 1024 个线程 = 32 个 warp 能驻留（占用率 32/64 = 50%）。若你把寄存器压到 **32 个**，立刻能驻留 2048 线程 = 64 warp（100%）。**一行代码多用了几个寄存器，就可能把你的并发量砍半，进而藏不住延迟。**

> 🔑 **本质**：occupancy 不是一个玄学指标，而是一道**零和的资源分配账**——寄存器、shared memory 是固定预算，线程的胃口去除它，得到并发度。**这是程序员和硬件之间最核心的一场谈判**，下一节（02）会把"高 occupancy 是否一定好"接着算。

### 4.5 访存层次 = 一串"复用放大器"；coalescing = warp 撞上突发访存

回到第 1 节那个不对称事实——**"算得起、取不起"**。既然从仓库取一次那么贵，唯一的活路就是：**取回来的东西，尽量多用几次再扔。** 整个片上存储层次，就是一串**复用的放大器**，每一级用"更小的容量"换"更高的带宽 / 更低的延迟"：

```
寄存器      ~256KB/SM   最快   ← 一个线程私有，复用发生在指令之间
shared/L1   ~228KB/SM   很快   ← 一个 block 共享，程序员手动搬数据进来复用
L2          ~50MB/芯片  中等   ← 全芯片共享，硬件自动
HBM         ~80GB       最慢   ← 那座远仓库
```

其中 **shared memory 是本质上最特别的一级**：它是**程序员手动管理的 cache**。硬件等于对你说："你比我的 LRU 启发式更清楚你的数据会怎么复用，这块 SRAM 交给你自己调度。" 这就是为什么它和 L1 是**同一块物理 SRAM 的两种用法**——同样的料，一半让你手动管（shared），一半让硬件自动管（L1）。

**coalescing（访存合并）** 也不是什么优化技巧，而是两个物理事实**必然的交汇**：
1. 显存（DRAM）不是按字节取的，一次事务搬一整个**突发段 / sector**（如 32 或 128 字节）。
2. 一个 warp 的 32 个线程**同一拍发出 32 个地址**。

于是：若这 32 个地址正好落在一两个 sector 里（相邻线程读相邻数据）→ 合并成一两笔事务，带宽利用接近 100%；若 32 个地址四散 → 最坏要 32 笔事务，**有效带宽掉到 1/32**。硬件里那个"合并器"（在 LSU 里）存在的唯一理由，就是把这 32 个请求尽量并成最少的 sector 访问。**"让相邻线程访问相邻地址"之所以是铁律，是因为 `warp=32 个同时的地址` 撞上了 `DRAM=按段突发`。**

### 4.6 那些"没点亮"的部件：判据是"有没有复用 / 有没有矩阵乘"

有了 4.5 的"复用"视角，第一节那个悬案（为什么 `y=2x` 用不上 shared memory 和 Tensor Core）现在有了**本质判据**，而不是"记住它用不上"：

- **shared memory 的存在意义是承载复用。** `y=2x` 里每个数据**读一次、算一次、写一次，复用度为 0**——没有任何东西值得"搬进来暂存反复用"，所以 shared memory 对它毫无价值。反过来，matmul 里一个数据要参与一整行/列的乘加（复用几十上百次），shared memory 才是命脉。**判据：有没有数据复用。**
- **Tensor Core 是一台只会算"小矩阵块乘加"的专用引擎**（内部是个小脉动阵列，模块 03 展开）。`y=2x` 根本没有矩阵乘，它自然全程空转。**判据：是不是矩阵乘 / 卷积这类结构。**

> 🔑 **本质**：一个算子会点亮 SM 的哪些部件，取决于它的**数据复用结构**和**运算形态**。element-wise（无复用、非矩阵）只用得上"ALU + 访存"这条最朴素的通路，于是它必然**受限于访存（memory-bound）**——这不是巧合，是它的数据结构决定的。

## 5. 把 `y[i] = 2 * x[i]` 完整走一遍（带着上面的"为什么"）

一百万个元素 → 每元素一个线程 → 每 32 线程一个 warp → warp 撒到各 SM 上驻留。在一个子分区里：

1. **调度器挑一个"就绪"的 warp**（4.1：手里得攥着几十个 warp 才有得挑），发出一条 load 指令。
2. **LSU 把这 32 个线程的地址合并**（4.5：相邻线程读相邻 `x`，合并成一两笔 sector 事务）发往 HBM。
3. **这个 warp 就此卡住等数据（~几百周期）——调度器眼皮不眨，立刻切到下一个就绪 warp**（4.2：切换免费，因为现场一直躺在寄存器堆里）。如此在几十个 warp 间轮转，**把这几百周期的空窗填满**。
4. 数据回来，**32 条 ALU lane 锁步各算一个 `2*x`**（4.3：一条指令喂满 32 通路）。
5. LSU 合并写回 32 个 `y`。该 warp 退休，后面的顶上。

**通篇真正在"算"的时间微不足道，绝大部分是在等访存、靠切换填满。** 于是这个 kernel 必然 memory-bound——它的性能天花板不在算力，而在你把带宽喂到了几成（回到 4.1 的 Little 定律）。**这句话不是背来的结论，是从头一路推下来的必然。**

## 6. 费曼自测：不用行话，你能讲出来吗？

费曼法的验收——如果下面每一问你都能用"车轮战"的大白话答上、并说出naive 解释在哪儿会崩，这一节才算真懂：

1. **GPU 为什么快？** ❌ 错误答法："因为核多。" ✅ 本质："因为它不追求单个任务快，而是堆够多的独立任务，谁停下等数据都有别人顶上——用并发填满延迟。核多只是这个策略的表象。"
2. **寄存器堆为什么那么大？** ❌ "为了更快。" ✅ "为了让切换免费——每个线程现场常驻不收摊；它是**容量**资源，不是速度资源，大小直接决定能并发多少线程。"
3. **occupancy 是什么？** ❌ "一个越高越好的指标。" ✅ "固定的寄存器/shared 预算，除以每线程的胃口，得到能驻留的 warp 数——一道零和的除法。"
4. **为什么要 warp 锁步？** ❌ "因为 GPU 是 SIMD。" ✅ "为了把昂贵的取指/译码控制开销在 32 条数据通路上团购摊薄，省下的晶体管拿去堆算力；代价是必须齐步走。"
5. **coalescing 为什么重要？** ❌ "一个访存优化技巧。" ✅ "因为 32 个线程同拍发 32 个地址，撞上 DRAM 按段突发——地址聚拢则一两笔事务，四散则最坏 1/32 带宽。是两个物理事实的必然交汇。"

## 7. 开发者视角：代码/工具里怎么摸到它

> **感知硬件只有三通道**：① **源码拨盘**（源码里唯一朝硬件的旋钮：launch config、`__shared__`、dtype、调哪个库）② **编译器回执**（`-Xptxas -v` 离线体检）③ **Profiler 探针**（Nsight 运行时示波器）。
> **硬件特性大多不是"写"出来的，是拨盘 + 访存模式"暗示"出来、再靠 profiler 症状反推的** ⇒ 学硬件的一大半实用目的，就是看懂 profiler 在说什么。

| SM 部件 / 特性 | ① 源码拨盘 | ② 编译器回执 | ③ Profiler 探针（Nsight Compute） |
| --- | --- | --- | --- |
| 藏延迟 / occupancy（§4.1、4.4） | launch config 的 **block 大小** | — | `Achieved Occupancy`；`Eligible Warps/Scheduler`；Stall `Long Scoreboard`（=在等显存，§4.5 的直接证据） |
| ALU / FMA lane（§4.3） | 算术表达式 | SASS 里的 `FFMA` | `Compute (SM) Throughput %`；FMA pipe util |
| 寄存器堆（§4.2） | 局部变量数；`__launch_bounds__`、`-maxrregcount` | `-Xptxas -v` → "Used N registers"、"**spill**"（溢出=现场装不下、被踢到显存，大凶） | `Registers Per Thread`；"limited by registers" |
| LSU / coalescing（§4.5） | **索引模式**（相邻线程是否相邻地址） | — | `Global Load/Store Efficiency`；`Sectors/Request`；`DRAM Throughput` |
| Shared Memory / L1（§4.5） | `__shared__` 声明；padding；carveout 配置 | 静态 shared 用量 | `Shared Bank Conflicts`；`L1 Hit Rate` |
| Tensor Core（§4.6） | 用 `wmma`/cuBLAS/CUTLASS/Triton 而非裸 `*`；喂 fp16/bf16/tf32；形状对齐 | SASS 里的 `HMMA`（没有=没用上） | `Tensor Pipe Active %`（为 0 就是白买） |

`y=2x` 的闭环：`-Xptxas -v` 报"每线程 8 寄存器、0 spill" → `ncu` 看到 occupancy 高、Compute 低、`DRAM Throughput` ~90%、主 stall 是 `Long Scoreboard` → **三证齐指 memory-bound**，和 §5 从头推出的结论对上。这就是"感知"闭环。

### 站位阶梯：你在栈的哪一层，"感官"完全不同

| 站位 | 拨盘 | 观测手段（感官） |
| --- | --- | --- |
| 框架层（PyTorch） | 算子选择、dtype、`torch.compile` | `torch.profiler`、`nvidia-smi`、看 kernel 名是否命中融合/TensorCore |
| Triton 层 | `BLOCK_SIZE`、`num_warps`、`num_stages` | `@triton.autotune` 结果、`do_bench` |
| CUDA C 层 | launch config、`__shared__`、`-maxrregcount` | 上面那张大表（Nsight Compute） |
| PTX/SASS 层 | 几乎不写，只读 | `cuobjdump -sass` / `nvdisasm` |

> 越往上拨盘越少越抽象、越难精确看见硬件；越往下旋钮越多、profiler 越精细、越费人。**算法侧日常主战场在上两层**，核心感官是 `torch.profiler` + Triton autotune，而非 SASS。这条阶梯就是**模块 04 软件栈**的骨架。
