## 1. 需要修正的事实错误（3 条）

### 1.1 ⚠️ TPU 的"128×128 阵列多年未变"已不成立

**涉及**：[02-01 §6 与术语卡](../02-空间脉动架构/01-MAC与PE阵列.md)、[02-02 §8](../02-空间脉动架构/02-脉动阵列数据流与时序.md)、[02-03 §7](../02-空间脉动架构/03-数据流复用分类.md)、[02-04 §2/§8](../02-空间脉动架构/04-片上存储与tiling.md)、[02-05 §7](../02-空间脉动架构/05-阵列利用率与padding.md)、[03-01 §5](../03-两者交汇与扩展/01-TensorCore.md)、[04-04 §3 表](../04-软件优化栈/04-核心映射问题.md)、[05-01 §2/§6/术语卡](../05-收敛-术语表与真实芯片/01-真实芯片对照.md)

**现状**：全库以"TPU 的 MXU = 128×128，从 v1 到 v7 核心结构基本未变"作为模块 02 的锚点实例，形状税的算例（130×130 → 26% 利用率）也建在 128 这个粒度上。

**问题**：TPU v7（Ironwood）的官方规格是**每芯片 2307 TFLOPS BF16 / 4614 TFLOPS FP8**（Google Cloud 文档），每芯片 2 个 TensorCore。把它反推一遍就能看出 128 这个数字撑不住：

> 2307 × 10¹² FLOP/s ÷ 2（每次 MAC 算 2 个 FLOP）= 1.15 × 10¹⁵ MAC/s
> ÷ 2 个 TensorCore = 5.77 × 10¹⁴ MAC/s 每核
> 若仍是 4 个 128×128 MXU（65536 MAC/拍），需要 **8.8 GHz** 时钟 —— 不可能
> 若是 8 个 256×256 MXU（524288 MAC/拍），需要 **约 1.1 GHz** —— 合理

多篇第三方架构分析直接给出 **256×256、每拍 65536 次 MAC** 的 MXU 规格。Google 官方文档不公布 MXU 尺寸，所以**建议的改法不是把 128 换成 256，而是把叙述改成"粒度是代际参数，不是常数"**：

- 保留 128×128 作为**教学原型**（它是 v1–v5 的真实形态，逐拍例子和形状税公式都不受影响），但明确标注这是哪一代。
- 在 02-01 §6 和 05-01 §6 补一句：v7 的 MXU 规模已明显放大（第三方分析给 256×256），**形状税的粒度随之翻倍——避税的对齐要求从 128 的倍数变成 256 的倍数**。这个推论对模块 02 第 5 节的"形状文化"很有分量：硬件粒度不是永恒的，模型侧的对齐纪律要跟着走。
- 02-01 §6 那句"阵列这个核心结构基本未变——说明该范式已接近最优"要弱化：**结构没变，尺寸变了**，而尺寸恰恰是形状税的唯一自变量。

**顺带一条同源的补充**：Ironwood 是**第一代在 MXU 里原生支持 FP8** 的 TPU。全库讲低精度时一直把 TPU 描述成"bf16 输入 + FP32 累加"（[08-02 §9](../08-微架构与物理实现/02-算术单元的物理实现·一个FMA由什么门组成.md)），这条也要更新。

### 1.2 ⚠️ "HBM4 靠加宽不靠加速"这个论断已被量产产品推翻

**涉及**：[07-02 §4 与 §12](../07-封装与存储的物理实现/02-HBM解剖·容量靠堆叠带宽靠base-die.md)

**现状**：§4 写 `HBM4：2048 根 × 8 Gbps ÷ 8 = 2.0 TB/s`，并据此立了一个很显眼的论点——"**HBM4 的每根引脚速率反而低于 HBM3E（8 对 9.6），带宽全部来自引脚数翻倍……它是靠加宽而不是靠加速换来的带宽**"。§12 的代际表也按这个口径写（HBM4 = 8 Gbps，HBM4E 才到 11.5 Gbps）。

**问题**：这个数字取的是 JEDEC 基线，而非产品实际值。

- JEDEC **JESD270-4 于 2025-04 批准**，规定 2048 位接口、每引脚 **6.4 Gbps 起、可扩展到 12+ Gbps**。8 Gbps 只是区间下沿。
- **HBM4 已于 2026-02 量产**（SK hynix 与三星同期）。三星的 HBM4 在 **sub-1V 核心电压下 11 Gb/s、高电压下可达 13 Gb/s**；NVIDIA VR200 用的 HBM4 跑 **11+ Gbps/pin，单堆叠带宽超过 3.0 TB/s**。
- 所以 HBM4 这一代是**加宽与加速同时发生**，单堆叠 3.0+ TB/s 而不是 2.0 TB/s。

**改法**：§4 的公式保留（它是对的），但把代入值改成区间（6.4 基线 / 产品 10–11+），并**撤掉"每引脚速率反而降低"这个论断**——它是整节里最抢眼的一句话，错得也最显眼。§12 的五行代际表相应整体前移一档。

**同一节另外两处需要一并修**：

1. **base die 工艺不是统一的 4nm**。§1、§4、§7、§12 都写"HBM4 起 base die 改用 4 纳米逻辑工艺"。实际是**各家不同**：三星用自家 4nm 代工；**SK hynix 与台积电合作，用的是 12nm 逻辑**。论证本身（PHY 要跑高速必须换逻辑工艺）完全成立，只是不该把"4nm"写成行业统一节点。
2. **HBM4 的通道数翻倍没提**。§5 讲通道/伪通道时只说"HBM3E 堆叠对外呈现十几条通道"。HBM4 把独立通道从 **16 条翻到 32 条**（伪通道 32→64）。这条对 §5 的立论（"它不增加带宽，增加的是把带宽用满的概率"）是正面证据，值得补上。

### 1.3 ⚠️ shared memory 容量口径全库不一致

**涉及**：[01-01 §4.5 及结构图、术语卡](../01-SIMT核的物理实现/01-SM-CU内部解剖.md)、[01-02 §4.2](../01-SIMT核的物理实现/02-warp锁步执行与occupancy.md)、[01-04 §2 表](../01-SIMT核的物理实现/04-访存通路.md)、[A1 §2 表](../01-SIMT核的物理实现/A1-算例·占用率与瓶颈定位.md) vs [08-03 §5/§8](../08-微架构与物理实现/03-片上存储的物理实现·从6T单元到寄存器堆.md)、[08-01 §7](../08-微架构与物理实现/01-数字设计地基·从RTL到硅.md)

**现状**：

- 模块 01 一系列节：H100 每 SM 的片上快速存储 = **约 228 KB**（01-01 §4.5 原文："每个 SM 有约 228 KB 的片上快速存储，物理上是同一块 SRAM"）。
- 模块 08：Hopper 每 SM 统一 SRAM = **256 KB**（08-03 §5："每个 SM 里有一块统一的片上 SRAM（Hopper 是 256 KB）"）。

**正确的说法是两者都对，但指的是两件事**：物理上的统一 L1/shared SRAM 是 **256 KB**；其中**可被配置成 shared memory 的上限**是 228 KB（单个 block 可申请上限 227 KB），剩下的必须留给 L1。

**改法**：模块 01 那几处把"片上快速存储 = 228 KB"改成"**片上统一 SRAM 256 KB，其中 shared memory 的可配上限约 228 KB**"。A1 §2 的表格标题已经写了"（可配上限）"，是对的，只要正文口径跟上就行。这条不影响任何占用率算例（那些算的本来就是 shared 的可配上限），但它让 01-01 §4.5 和 08-03 §5 读起来像在说两件事。

## 2. 时效性更新（8 条，全部来自 2026-01 之后）

### 2.1 🔥 Rubin CPX：全库主线论点第一次有了硬件级的回应

**这是本次 review 里最值得补的一条。**

全库反复论证的一条主线是：**prefill 是计算受限、decode 是带宽受限，两个阶段是同一个算子的两种命运**（[A2 §4](../01-SIMT核的物理实现/A2-案例·FlashAttention与MoE-GroupGEMM瓶颈剖析.md) 的横向对照表、[04-05 §2 链一/链三](../04-软件优化栈/05-与算法侧的接口.md)）。2025-09 之后，NVIDIA 把这个论点直接做成了两颗不同的芯片：

- **Rubin CPX**：单 die，**128 GB GDDR7（不是 HBM）**，30 PFLOPS NVFP4，PCIe Gen6，专供 **prefill**——重算力、轻带宽、成本低。
- **Rubin 本体**：HBM4，专供 **decode**——重带宽。
- **Vera Rubin NVL144 CPX 机架** = 144 Rubin + 144 Rubin CPX + 36 Vera CPU，8 EF NVFP4、100 TB 快存、1.7 PB/s。预计 2026 年底供货。

**为什么值得专门补**：

1. 它是"分离式推理（disaggregated prefill/decode）"从软件调度策略上升为**硬件产品形态**的第一个大规模案例——这条正好接在 [04-A1 §3.3 的 TBO/SBO](../04-软件优化栈/A1-业界高质量kernel技术图谱.md) 之后，把"藏延迟在栈的每层各现一次身"那张表再往上加一层：**系统层之上还有一层"按瓶颈类型拆硬件"**。
2. 它给 [07-02 §3.1 的 GDDR vs HBM 对照表](../07-封装与存储的物理实现/02-HBM解剖·容量靠堆叠带宽靠base-die.md) 提供了一个此前没有的反例：那张表的结论是"AI 加速器不用 GDDR 凑数"，而 CPX 恰恰**主动选了 GDDR7**——因为 prefill 的算术强度高，它根本不需要 HBM 的带宽，只需要便宜的容量。这不推翻那张表，反而印证了它的立论（少而快 vs 多而慢是按负载选的）。
3. 它给 [04-05 §5 的翻译表](../04-软件优化栈/05-与算法侧的接口.md)（"你的话在 infra 同事耳朵里是什么"）加了一行新的现实约束：**"prefill 和 decode 的形状可以分开优化"从软件假设变成了部署拓扑问题**。

**建议落点**：A2 §6 最新架构落点 + 04-A1 §5 + 07-02 §3.1 各补一段；如果想做大，值得在模块 03 加一个小节讲"按阶段拆硬件"。

### 2.3 🔥 2-CTA MMA（`cta_group::2`）：Blackwell 的一个重要机制全库缺席

FA-4 论文列出的三条关键技术里，KB 覆盖了两条，缺的第三条是：**利用 tensor memory 与 2-CTA MMA 模式，减少 shared memory 流量和反向传播里的 atomic add**。

**这个机制是什么**（可直接写进笔记）：

- Blackwell 的 `tcgen05.mma` 支持 `cta_group::2` 模式：**同一个 cluster 内 `%cluster_ctarank` 只差最低位的一对 CTA**（一奇一偶）配对，共同完成一条更大的矩阵指令。
- 分工是：**A 操作数在两个 CTA 之间复制，B 与累加器 D 在两个 SM 之间分片**，每个 CTA 各持一半 TMEM。例如一条 256×256×16 的 MMA，每个 CTA 只装载 A、B 各自的 128×16 切片，各持有 128×256 的累加器。
- **收益**：同样的 FLOP，**操作数搬运量减半**——相对两个 CTA 各做各的 MMA。
- 只需要**一对 CTA 里的一个线程**发出这条指令，但对端 CTA 必须保持活跃。

**为什么值得补**：

1. [03-01 §4 的四代演化表](../03-两者交汇与扩展/01-TensorCore.md) 里，Blackwell 那一行现在只写了"单线程发起 + 累加器进 TMEM"。2-CTA 是这一代**第三个**方向性变化，而且是最有意思的一个——**矩阵引擎第一次跨出了单个 SM 的边界**。
2. [08-03 §6 那张"绕开寄存器堆"的四步演进表](../08-微架构与物理实现/03-片上存储的物理实现·从6T单元到寄存器堆.md) 可以加第五步：**跨 SM 共享操作数**。这条演进线的叙事（"能规则化、能批量化的数据流被逐个挪出寄存器堆"）正好延伸成"……最后连 SM 边界都被挪开了"。
3. 它给 [Hopper 线程块簇（cluster）](../01-SIMT核的物理实现/07-调度全景.md) 这个特性补上了**它真正的杀手级用途**——KB 现在讲 cluster 主要讲 DSMEM 和 TMA 多播，而 2-CTA MMA 是让"簇内必须同时驻留"这条调度约束真正值回票价的那个应用。

### 2.6 稀疏注意力从研究进入生产：DeepSeek DSA

**涉及**：[A2 §2.3 与 §4](../01-SIMT核的物理实现/A2-案例·FlashAttention与MoE-GroupGEMM瓶颈剖析.md)、[04-05 §6 业界成例](../04-软件优化栈/05-与算法侧的接口.md)

**现状**：A2 §2.3 的结论是"decode 的算术强度 ≈ 1，上限就是读 KV cache 的带宽"，04-05 §6 的成例清单是 GQA → MLA → 投机解码 → 线性注意力。

**新增**：DeepSeek-V3.2 的 **DSA（DeepSeek Sparse Attention）** 是这条线上的下一步，而且机制很干净：

1. 一个**轻量索引器（lightning indexer）**用低秩投影给上下文里每个 token 块打一个相关度分数，**开销只有完整注意力的 1–5%**。
2. 只从 HBM **加载 top-K 块**（固定 top-2048 token），在稀疏选择上跑标准注意力。
3. 效果：128K 上下文下注意力计算砍约 **98%**，每次 query 的活跃 KV 足迹降到约 **0.6 GB**。

**为什么它值得进 04-05 §6 的清单**：GQA/MLA 砍的是**每个 token 的 KV 字节数**，DSA 砍的是**参与计算的 token 数**——这是同一个"减小被除数"策略的**第二个正交维度**。用 KB 自己的语言说：GQA 改的是 KV cache 的宽度，DSA 改的是它的长度。

**还有一个与模块 08 的漂亮呼应**：DSA 的 kernel 形态是"索引器 + 按块 gather"，而 [08-07 §4](../08-微架构与物理实现/07-NPU侧的微架构·阵列RTL与配套器件.md) 刚讲过"gather 在 AGU 上表达不了，是稀疏在 NPU 上难做的硬件根源"。**稀疏注意力成为主流，会直接放大 GPU 相对静态调度芯片的优势**——这条推论正好落在模块 00 那条"争夺焦点是负载的规则程度"的光谱上。

### 2.7 kernel 语言层：海拔轴中段已经拥挤

**涉及**：[04-06 §10 最新架构落点](../04-软件优化栈/06-并行编程语言与算子库.md)、[04-03 §8](../04-软件优化栈/03-kernel层.md)

## 4. 结构性空白（5 处，按"值不值得补"排序）

### 4.1 🔥 数据的一生缺了上游：host → device 这一段

[06-01 §2](../06-数据视角/01-存储层级与搬运指令全图.md) 的旅程是从"**另一个节点的 GPU 显存**"开始的。但真实数据的一生更长：磁盘/对象存储 → 主机内存 → 显存。这一段涉及的东西不少，且全部是生产环境的日常痛点：

- DataLoader 与 **pinned memory**（06-01 §6.1 的表里已经提了锁页内存一行，但没展开）
- **GPUDirect Storage（GDS）**：NVMe 直写显存，绕开主机内存
- 主机侧 NUMA 与 PCIe 拓扑（哪块网卡/哪块盘挨着哪张卡）
- **Grace-Hopper 的 NVLink-C2C**（06-01 §7 提了一句 900 GB/s）如何改变"显存放不下就 offload"的成本结构

**建议**：在模块 06 加第 3 节，或在 06-01 §2 的旅程前面接一段。这条补上之后，模块 06 才真的叫"数据的一生"。

### 4.2 上下文并行 / 序列并行缺席

[03-02 §1](../03-两者交汇与扩展/02-NoC多核多芯片.md) 的并行策略清单是 TP / EP / PP / DP 四种，按通信密度排序。长上下文时代还有第五种已经标配的策略——**上下文并行（context parallelism）/ 序列并行**，把序列维切给多卡，通信模式是 ring attention 式的 **KV 环形传递**。

它值得补的理由不只是"少了一个名词"：它的通信模式和另外四种都不同（**不是 all-reduce，是环形点对点**），所以它在 §3 那张"策略住在哪一层"的居住安排表里的位置也不同——**通信量随序列长度而非模型尺寸增长**，这让它的分层判据要单独算一遍。

### 4.3 可靠性 / 失效模型整条线缺席

[08-08](../08-微架构与物理实现/08-从RTL到tapeout·流程如何反向塑造架构.md) 讲了良率、分档、屏蔽，[08-03 §5](../08-微架构与物理实现/03-片上存储的物理实现·从6T单元到寄存器堆.md) 讲了 ECC 的读-改-写，[08-06](../08-微架构与物理实现/06-能量与时钟的账本·功耗墙与供电.md) 讲了温度与漏电。但**芯片装进万卡集群之后的失效行为**完全没写：

- Xid 错误的分类与含义
- ECC 可纠正 / 不可纠正错误的累积与换卡判据（08-08 §8 的表里提了一句"持续增长是换卡信号"，但没展开）
- NVLink 链路降级（从满带宽掉到部分 lane）
- **静默数据损坏（SDC）**——这是大规模训练里最阴险的一类，且和 08-06 的电压跌落、08-01 的时序 marginal 直接同源

**建议**：在模块 08 加第 9 节，或在 08-08 里扩一个小节。这条的价值在于它是**前八节所有物理约束在生产环境里的汇合点**——温度、电压、工艺偏差、良率余量，最后全都表现为"这张卡是不是该换了"。

### 4.4 块缩放格式的"喂数通路"没有独立成节

[08-02 §6](../08-微架构与物理实现/02-算术单元的物理实现·一个FMA由什么门组成.md) 讲了 MXFP4/NVFP4 的元数据开销（6.25% vs 12.5%）和块边界形状税；[06-02 §9](../06-数据视角/02-摆数的学问·布局与切分.md) 提了一句"布局里第一次混进了元数据"。但**"scale 和它对应的 16/32 个元素怎么一起被搬进 Tensor Core"这条通路**没有一处完整讲过。

这是 2026 年 kernel 层最实在的一块新工作量：它同时给 TMA 描述符、shared memory 布局、swizzle 模式都加了新约束。**06-02 §3 那条"约束传导链"（mma 规定 fragment → ldmatrix → swizzle → TMA 描述符 → 全局布局）现在多了一条平行的 scale 通路**，而两条链必须严丝合缝地对上。这是把那一节的立论推进一代的自然方向。

（README 明确写了"量化/数据格式主动跳过"——但这条是**数据通路问题不是数值问题**，落在库的范围内。）

### 4.5 模块 02 / 03 的「最新架构落点」栏是全库最薄的一批

除了 §1.1 讲的 TPU 尺寸问题，这两个模块的落点栏内容也偏少（02-01 §6 只有四条、03-01 §7 只有四条），且都停在 2026-01。考虑到 2026 年 NPU 侧的变化（Ironwood 的 FP8 与 SparseCore、昇腾 CloudMatrix、UALink 落地），这两栏值得整体重写一遍。

**另外一个 02 模块的具体缺口**：**TPU 的 SparseCore 全库没提**。Ironwood 每芯片有 **2 个 TensorCore + 4 个 SparseCore**（双 chiplet，每 chiplet 1 TensorCore + 2 SparseCore + 96 GB HBM）。SparseCore 专管 embedding 查表这类不规则负载——它恰好是 [02-02 §5 "伴生向量单元"](../02-空间脉动架构/02-脉动阵列数据流与时序.md) 那条论证（"阵列只吃规则计算，真实网络里总有不规则的部分，必须有人兜底"）的**第二个实物例证**，而且比 VPU 更有说服力（VPU 兜的是逐元素运算，SparseCore 兜的是彻底不规则的 gather）。
