# 为什么要搬，以及最朴素的搬法：线程自己搬

> **所属模块**：模块 14 · 数据搬运（第一部分 · GPU 的数据搬运）
> **状态**：🟨 学习中（2026-10 按新目录重写。知识截至 2026-09）
> **一句话主旨**：乘加电路只能从片上取操作数，显存一个来回要几百拍，所以数据必须先搬到片上。最朴素的搬法是每个线程自己发读取指令、自己算地址、靠记分牌知道数据到了。记分牌只能在"目的寄存器被写入"那一刻报完成，所以在路上的数据必须事先占好寄存器。计算一代比一代快、往返延迟却不变，要提前发出去的数据越来越多，寄存器装不下——后面每一代搬运机制，都是从这里开始改的。

## 1. 基础词汇

**线程、warp、SM**。CUDA 程序里每个线程是一条独立的执行流。硬件把 32 个线程绑成一组，叫 **warp**：一个 warp 的 32 个线程每次执行同一条指令，各自用自己的数据。**SM**（Streaming Multiprocessor）是 GPU 里一个独立的计算单元，H100 有 132 个；一个 SM 上同时驻留几十个 warp，由 4 个 warp 调度器轮流挑选执行。

**发射（issue）**。warp 调度器每拍从自己管的 warp 里挑一个，把它的下一条指令送进执行单元，这个动作叫发射。两条性质本节反复用到：一个 warp 的指令**按程序顺序**发射，前一条发不出去，后面的也只能等；一条指令替整个 warp 的 32 个线程各做一份，但只算发射一次。

**寄存器**。紧贴执行单元的一小块存储，每个线程有自己的一组，每个 4 字节。H100 每个 SM 有 65 536 个，合 256 KB，由驻留在这个 SM 上的所有线程分；每个线程最多用 255 个。

**shared memory**。每个 SM 内部一块由程序显式管理的 SRAM，H100 上最多 228 KB，同一个线程块的线程都能读写。它是"搬进来、反复用"的落脚点。

**显存（HBM）与 L2**。显存是 GPU 芯片旁边的几颗 DRAM 堆叠（HBM，高带宽存储），H100 上共 80 GB。L2 是全芯片 132 个 SM 共用的一级缓存，50 MB，夹在 SM 和显存之间。

**拍**。一个 GPU 时钟周期。H100 约 1.8 GHz，一拍约 0.55 纳秒。

**分块（tile）**。把大矩阵切成能放进片上存储的小块，一块一块搬进来算。本节的例子固定为：矩阵乘的输出分块 128 × 128，沿 K 方向每次推进 64，每推进一次要搬 A 的一个 128 × 64 分块和 B 的一个 128 × 64 分块。元素是 bf16（2 字节），所以**每个分块 128 × 64 × 2 = 16 KB，每推进一次搬 32 KB**。线程块是 128 个线程（4 个 warp）。

## 2. 为什么必须搬

### 2.1 操作数只能从片上来

一条乘加指令在一个 warp 上执行时，32 条通道每拍各要 3 个操作数，合计 96 个 4 字节的数，而且下一拍还要 96 个新的。能做到"每拍都供得上"的，只有专属于这些执行单元、做成多端口的寄存器堆。GPU 的计算指令因此只认片上的几种存储：普通算术指令（`FFMA` 等）读寄存器，也能直接读常量缓存里的一个数；矩阵指令读寄存器或 shared memory；Blackwell 的矩阵指令还能读一块叫 TMEM 的专用片上存储。**没有任何一条计算指令能把显存地址当操作数。**

够不着显存，原因不在距离。图 1-1 是一颗 Pascal P100 的封装照片：显存堆叠和 GPU 芯片之间只隔一毫米左右。真正的原因是**沿途的站**：越往外的存储被越多的单元共用，每一级都要先查"数据在不在我这里"、再排队等通路空出来。L1 查一次几十拍；L2 分成几十片散在全芯片上，请求要穿过片上网络找到管这个地址的那一片；显存要先由控制器排队，再把 DRAM 里对应的一行打开、读出一列。每一站十几到上百拍，加起来就是几百拍。

![Pascal P100 的封装：中间是 GPU 芯片，左右两侧各有两块显存堆叠，紧贴着芯片](./figures/14-01-p100-package.jpg)

> **图 1-1**　一句话：显存（HBM）就紧挨在 GPU 芯片旁边，可从计算单元发出读取到数据回来仍然要几百拍——慢在沿途要经过的站，不在距离。
>
> **先知道一件事**：这是近红外光下拍的照片，能透过外壳看到硅片本身。照片里的东西都装在同一块封装基板上，和插在主板上的内存条不是一回事。
>
> **按这个顺序看**：
> 1. 先看正中间印着 NVIDIA 字样的大矩形：这是 GPU 芯片本身（GP100），约 22.5 × 27.5 毫米，SM、L2、显存控制器都在里面。
> 2. 再看它左右两侧各两块带细密格纹的竖长矩形：这是 4 个 HBM 显存堆叠，每个是几层 DRAM 芯片摞在一起，约 7.5 × 11.5 毫米。格纹是 DRAM 内部的存储阵列。
> 3. 看堆叠和 GPU 芯片之间的缝：不到 1 毫米。它们之间用硅中介层上几千根很短的导线相连，信号走过这段距离只要零点几纳秒，不到一拍。
> 4. 最外圈的银色框和两侧成排的小黑块是封装外壳和供电用的电感，与本节无关。
>
> **看懂的标志**：能回答"既然显存离得这么近，为什么还要等几百拍"——因为一次读取要依次经过 L1 查找、片上网络、L2 查找、显存控制器排队、DRAM 开行读列，再原路返回；每一站都有查找和排队，导线本身的时间可以忽略。
>
> **与正文的对照**：这是 2016 年的 P100。H100 把堆叠增加到 5 个可用（共 80 GB），结构相同。
>
> 来源：[Nvidia@16nm@Pascal@GP100@Tesla P100@T Taiwan 1912A1 PN9G70.S6W GP100-897-A1 DSCx01@SWIR.jpg](https://commons.wikimedia.org/wiki/File:Nvidia@16nm@Pascal@GP100@Tesla_P100@T_Taiwan_1912A1_PN9G70.S6W_GP100-897-A1_DSCx01@SWIR.jpg)，作者 FritzchensFritz，许可 CC0。

### 2.2 等一次显存要多久，这段时间值多少计算

两篇 Hopper 微基准论文给出的实测：shared memory 约 29 拍，L1 命中约 40 拍，L2 命中约 260～470 拍，走到显存约 480～730 拍。L2 和显存给的是范围，因为 H100 的 L2 分成两个分区，请求落在本侧分区还是对侧分区，差出近两百拍。

把"480～730 拍"换算成"这段时间本来能算多少"。H100 一个 SM 的矩阵单元每拍做 2048 次 bf16 乘加（整卡 989 TFLOPS ÷ 132 个 SM ÷ 1.83 GHz ÷ 每次乘加算 2 次运算）。等一次显存的工夫：

> 2048 次/拍 × 480～730 拍 ≈ **98 万～150 万次乘加**

而一个 128 × 128 × 64 的分块总共 128 × 128 × 64 ≈ **105 万次乘加**。**干等一次显存往返，就白扔了一整个分块的计算。**

![四级存储的延迟阶梯：寄存器、shared memory 在虚线以上，L2 和显存在虚线以下；右侧把一次显存往返换算成乘加次数](./figures/14-01-latency-ladder.svg)

> **图 1-2**　一句话：乘加电路只能从虚线以上的两级取数；虚线以下的显存远到什么程度——等它一次的工夫，矩阵单元本来能算完一整个分块。
>
> **先知道一件事**：这里比的是**延迟**（发出请求到数据回来要等多久），不是**带宽**（每秒能搬多少）。读取是流水化的，同一时刻可以有很多笔在路上，所以延迟长不等于每秒搬得少。
>
> **按这个顺序看**：
> 1. 左边从上到下四个方框，离执行单元越来越远。右边的横条是取一个数要等的拍数；为了让 1 拍和 700 拍画在一张图上，横条用的是对数长度，读旁边的数字。
> 2. 上面两个绿框旁边的方括号：计算指令的操作数只能从这两级来。寄存器的读取已经算进执行流水线，不单独计时；shared memory 约 29 拍。
> 3. 红色虚线以下是 L2 和显存。计算指令没有通到这里的路，数据必须先被搬上来。
> 4. 右边蓝框做的换算：每拍 2048 次乘加，乘上 500～700 拍，是 100 万～140 万次；一个 128×128×64 分块约 105 万次。两者相当。
>
> **看懂的标志**：能说出"搬运"在 GPU 上为什么是和计算同样重要的问题——不提前把数搬上来，矩阵单元等一次显存的时间里本来能做完一整块活。
>
> **与正文的对照**：延迟数字取自 Luo 等（arXiv:2402.13499，H800：L2 263 拍、显存 479 拍、shared memory 29 拍）和 Jarmusch 等（arXiv:2501.12084，H100：本侧 L2 分区 295 / 554 拍，对侧 470 / 728 拍）。
>
> 来源：本库自绘。

### 2.3 所以先搬进来，再反复用

最直接的反面例子：矩阵乘的三重循环，最内层每次从显存读一个 A 元素和一个 B 元素，乘起来累加。每次迭代付出一次显存往返，换来一次乘加——这 500 多拍里矩阵单元本来能做 100 万次。

换一种写法：先把 A 的 128 × 64 分块搬进 shared memory，再从 shared memory 反复取。算 128 × 128 的输出分块时，A 分块里的每个元素要被用 128 次（和 B 的 128 列各乘一次）。**一次显存往返的代价被 128 次使用摊薄**，后面 127 次每次只付 shared memory 的 29 拍。

这就是 GPU 程序的基本结构：**搬一块进来，在片上用很多次，再搬下一块**。块该切多大是模块 11 第 4 节的问题；本模块只研究"搬一块进来"这个动作。

### 2.4 任何搬法都要回答三个问题

不管用什么机制搬，都要回答三个问题：

1. **谁发起**：由谁发出"去搬"的指令？每个线程各发各的，还是一个线程替大家发，还是根本不需要 SM 上的线程？
2. **地址从哪来**：一个 128 × 64 的分块在显存里不是连续的一段——每行 128 字节连在一起，行与行之间隔着整个矩阵的一行宽。要搬它，就得算出每一行（甚至每个线程负责的每一小段）的起点。这些乘法和加法由谁来做？
3. **完成怎么知道**：要用数据的人怎么知道数据已经到了？

除此之外是**传输本身**：数据在路上走的那几百拍、以及每秒能走多少字节。这一项由存储系统决定（HBM 的带宽、L2 的大小与分区），对搬运机制来说是给定的条件——机制能做的只有两件事：把这几百拍藏在计算后面，以及让足够多的数据同时在路上，把带宽吃满。

本模块第一部分就是看 GPU 一代代怎么改这三个答案。这一节先看最早、也是最朴素的那一组答案。

## 3. 最朴素的搬法：线程自己搬

### 3.1 代码长什么样

把 A 的 16 KB 分块从显存搬进 shared memory，最直接的写法是让线程块的 128 个线程分工：每个线程每次读 16 字节（一个 `uint4`，8 个 bf16），读进自己的寄存器，再写进 shared memory。16 KB ÷ 16 字节 = 1024 次，每个线程做 8 次。

```cpp
// gA 指向 A 分块在显存里的左上角，lda 是 A 一整行的元素个数
// 128 × 64 的 bf16 分块：每行 64 个元素 = 128 字节 = 8 个 uint4
__shared__ uint4 sA[128 * 8];
int t = threadIdx.x;                       // 0..127
#pragma unroll
for (int i = 0; i < 8; ++i) {
    int idx = i * 128 + t;                 // 这个线程负责的第 i 个 16 字节
    int row = idx / 8, col = idx % 8;      // 在分块里的第几行、行内第几段
    uint4 v = reinterpret_cast<const uint4*>(gA + row * lda)[col];   // 读：显存 → 寄存器
    sA[idx] = v;                                                     // 写：寄存器 → shared
}
__syncthreads();                           // 等所有线程都写完，才能开始用 sA
```

编译成机器码（SASS）后，循环的每一轮是三类指令：几条整数乘加算出这一段的显存地址（`IMAD`），一条 16 字节的全局读取（`LDG.E.128`），一条 16 字节的 shared memory 写入（`STS.128`）。

### 3.2 三个问题在这里的答案

**谁发起：每个线程。** 128 个线程全部参与，每个线程发 8 条读、8 条写。按 warp 计，4 个 warp 各发 8 次读、8 次写，共 64 次发射。

**地址从哪来：每个线程自己算。** 代码里的 `row`、`col`、`gA + row * lda` 都是这个线程自己用整数指令算出来的，结果存在它自己的寄存器里。算出 32 个地址之后，SM 里的访存单元（LSU）还要做一件事——**合并（coalescing）**：显存和缓存之间按 32 字节一段搬数据，访存单元把一个 warp 的 32 个地址归并成"覆盖它们所需的最少段数"。上面的写法里，一个 warp 的 32 个线程读的是相邻的 32 个 16 字节，正好是连续的 512 字节，归并成 16 段，一个字节也不浪费。如果地址是散开的，同样搬 512 字节有用数据，要多搬很多段。图 1-3 用每线程 4 字节的情形画出了四种排法的差别。

![四种访问模式下，32 个线程各读 4 字节需要搬几个 32 字节段：对齐连续 4 段、整体偏一格 5 段、跨步 2 为 8 段、随机 32 段](./figures/14-01-coalescing.svg)

> **图 1-3**　一句话：同样是一个 warp 的 32 个线程各读 4 字节，地址怎么排，决定了硬件要搬 4 个段还是 32 个段。
>
> **先知道一件事**：显存和缓存之间搬数据的最小单位是 32 字节，叫一个段（sector）。哪怕只要其中 4 个字节，也得把整段搬过来。
>
> **按这个顺序看**：
> 1. 每行是一种访问模式。每个粗框是一个 32 字节段，框里 8 个小格各是 4 字节；蓝格是有线程要的，白格是跟着一起搬、但没人要的。
> 2. 第①行：32 个线程读连续的 128 字节，起点正好对齐在段边界上，4 段全是有用数据。
> 3. 第②行：整体往后挪一格，128 字节跨进了第 5 段，多搬 1 段。
> 4. 第③行：隔一个读一个，有用数据散在 8 段里，一半白搬。
> 5. 第④行：地址完全打乱，每段只碰一格，要搬 32 段，八分之七白搬。
>
> **看懂的标志**：能回答"为什么让相邻线程读相邻地址"——访存单元只能把落进同一段的地址合在一起，相邻线程读相邻地址时，一个 warp 的请求合成最少的段，搬来的每个字节都有用。
>
> **与正文的对照**：正文的例子是每线程 16 字节，一个 warp 读连续 512 字节，相当于第①行放大 4 倍：16 段，全部有用。合并只在同一个 warp 内做，两个 warp 的地址即使首尾相接也不会合在一起。
>
> 来源：本库自绘。

**完成怎么知道：记分牌。** 这是本节的重点，第 4 部分专门讲。在讲它之前，先看一条读取指令发出去之后，在硬件上走了哪几站。

### 3.3 一条读取指令走过的路

图 1-4 是一条 `LDG` 从发射到数据回到寄存器的全程。它在 SM 内部先经过访存单元（算地址、合并），然后查 L1：命中就约 40 拍返回。没命中的请求先在 L1 旁边一张叫 **MSHR**（缺失登记表）的小表上登记"我要哪一段、谁在等它"——两个 warp 要同一段时只往下发一次请求，数据回来按表分发——然后经片上网络去 L2，没命中再去显存。

![一条 LDG 从发射到数据回到寄存器的路径，三个出口分别约 40、260、480 拍](./figures/14-01-ldg-path.svg)

> **图 1-4**　一句话：一条从显存读数的指令依次经过发射、算地址、合并、查 L1、查 L2、查显存这几站，数据在哪一站被找到，决定了这次读取要等 40 拍还是 480 拍。
>
> **先知道一件事**：一条浮点乘加几拍就算完，所以"等 480 拍"意味着这段时间本来够做上百条运算。
>
> **按这个顺序看**：
> 1. 从左往右是一条读取指令的行程，每个白框是一站，框里最后一行红字是这一站的拍数。底部横轴是从发射算起的累计拍数。
> 2. 蓝色大框是 SM 内部的三站：① 调度器把指令交给访存单元；② 32 个线程各算出一个 64 位地址；③ 把 32 个地址归并成若干个 32 字节段的请求，需要几段就占几拍。
> 3. 第 ④ 站查 L1："要的这一段在不在本 SM 的缓存里"。在，走绿色的出口甲，约 40 拍；不在，请求登记进缺失登记表（MSHR），往右走。
> 4. 橙色大框是 L2，全芯片共用、分成几十片。请求要先经片上网络找到管这个地址的那一片，命中走出口乙，约 260 拍。
> 5. 红色大框是显存：控制器排队、DRAM 开行、读列、再走回来，约 480 拍，是出口丙。回程顺路在 L2、L1 各留一份。
> 6. 左下第 ⑧ 站：数据写进目标寄存器。**这一刻**就是下一部分要讲的"完成"——记分牌在这里减一。
>
> **看懂的标志**：能回答"为什么编译器没法把'这条读取要等几拍'直接写进指令里"——同一条指令这次在出口甲结束、下次走到出口丙，相差十几倍，编译时算不出来，只能在运行时记账。
>
> **与正文的对照**：40、260、480 取自 Luo 等对 H800 的实测；H100 走对侧 L2 分区时显存约 730 拍（§2.2）。发射、算地址、合并三段是量级估计。
>
> 来源：本库自绘。

图里最后一句话引出了下一部分的问题：**延迟在编译时不知道，那后面要用这个数据的指令，怎么知道什么时候可以执行？**

## 4. 记分牌：数据到没到，硬件怎么知道

### 4.1 编译器能算的，和算不出的

GPU 把"后一条指令要用前一条的结果"这种依赖分成两类，处理办法完全不同。

**延迟固定的指令**，比如浮点乘加，结果几拍后可用是写死在硬件里的。编译器知道这个数，就直接在指令里写一个**停顿计数**："发完我之后，这个 warp 隔 4 拍再发下一条。"硬件只需要倒数，不需要任何比较逻辑。

**延迟不固定的指令**，典型就是访存：40 拍到 730 拍都有可能。编译器写不出数字，只能让硬件在运行时记账。这套记账机制，NVIDIA 的性能工具里叫 **scoreboard（记分牌）**，硬件上是每个 warp 的一组小计数器。

### 4.2 硬件里有什么、谁让它加、谁让它减、谁来查

按公开的逆向研究（Jia 等对 Volta 的微基准分析；NVIDIA 没有公布这部分编码），Volta 起每个 warp 有 **6 个计数器**，编号 0～5。每条机器指令是 128 位，其中约 21 位是编译器写的调度控制位，与记分牌相关的有三个字段：

- **写登记号**（3 位）：这条指令的结果写回时，记在几号计数器上；
- **读登记号**（3 位）：这条指令读完源寄存器时，记在几号计数器上（§4.3 讲它的用处）；
- **等待掩码**（6 位）：这条指令发射前，必须等哪几号计数器归零。

运作过程是三个动作，图 1-5 把它们画在一起：

1. **加一**：一条 `LDG` 发射时，硬件把它写登记号指定的那个计数器加一。
2. **减一**：数据回来、写进这条 `LDG` 的目的寄存器的那一拍，硬件把那个计数器减一。**对读取来说，硬件能报告的完成事件只有这一个：目的寄存器被写入。**
3. **查零**：warp 调度器每拍挑 warp 之前，看每个 warp 的下一条指令的等待掩码，掩码里点到的计数器只要有一个不是零，这个 warp 本拍就不参加挑选。

![记分牌的三个动作：LDG 发射时 2 号计数器加一，数据写进 R2 时减一，调度器查 FFMA 要等的 2 号是否为零](./figures/14-01-scoreboard.svg)

> **图 1-5**　一句话：记分牌就是每个 warp 的 6 个计数器——读取发出时加一，数据写进寄存器时减一，要用这个数据的指令等它归零才能发射；哪条指令记哪个号、等哪个号，全由编译器事先写在指令里。
>
> **先知道一件事**：每条机器指令除了"做什么运算"之外，还带着几个编译器填写的小字段，专门告诉硬件这条指令和前后指令的依赖关系。硬件不分析程序，只照这些字段办事。
>
> **按这个顺序看**：
> 1. 左边是一个 warp 的三条指令（为了好读，省略了地址描述符等修饰）。红框 `LDG` 把 x[i] 读进寄存器 R2，它的控制位写着"登记到 2 号"。
> 2. 中间是这个 warp 的 6 个计数器。`LDG` 发射的同一拍，2 号从 0 变成 1（箭头 ①）。读取请求同时发往右上的存储系统。
> 3. 右上：几十到几百拍后，数据回来写进 R2，2 号减回 0（箭头 ②）。
> 4. 左下蓝框 `FFMA` 要用 R2，它的控制位写着"等待 2 号"。右下的调度器每拍查 2 号（箭头 ③）：不为零，这个 warp 落选，调度器去发别的 warp 的指令；为零，`FFMA` 可以发射。
> 5. 左边中间那条 `IMAD.WIDE` 不用 R2，等的是 1 号，所以它在 `LDG` 之后照常发射。但它之后的 `FFMA` 一旦卡住，这个 warp 后面所有指令都跟着卡——同一个 warp 只能按顺序发射。
>
> **看懂的标志**：能回答"记分牌怎么知道 FFMA 要等的是 R2"——它不知道。硬件里只有 6 个计数器，没有任何寄存器编号。是编译器看出 `LDG` 写 R2、`FFMA` 读 R2，于是给前者填"登记 2 号"，给后者填"等待 2 号"；寄存器和计数器的对应关系只存在于编译器的这次分配里。
>
> **与正文的对照**：6 个计数器与控制位布局来自对 Volta 的逆向研究，Hopper 与 Blackwell 上未逐位核实；指令取自 §4.4 走查的真实反汇编。
>
> 来源：本库自绘。

回到 §0 里关于记分牌的两个问题：

**它怎么"对应到寄存器"？** 两层意思要分开。第一层，硬件不按寄存器记账，它只有 6 个计数器；"R2 归 2 号管"是编译器分配的，硬件不知道。第二层，计数器减一的时机绑在寄存器上：对一条读取来说，"完成"就是"它的目的寄存器被写入"，硬件没有别的完成事件可报。所以说记分牌的完成通知**挂在寄存器上**——不是说它按寄存器分格子，而是说数据必须落进寄存器，这笔账才能销。

**等数据的 warp 怎么用它？** 它什么也不用做，也没有"等待"这条指令可写。等待完全是被动的：这个 warp 的下一条指令带着等待掩码，调度器查到计数器不为零，就跳过这个 warp。这个 warp 停在原地，直到数据写进寄存器、计数器归零，它重新变成可以被挑选的状态。等待期间，调度器用别的 warp 的指令填满发射口——**掩盖延迟靠的是同一个 SM 上的其它 warp，不是这个 warp 自己。**

还有一点：**一个计数器可以同时记好几笔**。两条读取登记到同一个号，计数器就是 2，两笔都回来才归零。6 个计数器之所以够用，是因为编译器可以把"会被同一处等待的几笔"合记在一个号上。SASS 里另有一条 `DEPBAR` 指令，能显式地"等某号计数器降到 N 以下"——下一节的 `cp.async` 就靠它。

### 4.3 读登记号：另一种"等"

读取指令的问题是"结果什么时候写回"；写出指令（`STS`、`STG`）有个相反的问题：它的源数据什么时候从寄存器里读走。一条 `STS` 发射后，访存单元要过几拍才真正从源寄存器取数。如果后面紧跟一条指令要覆盖这个寄存器——比如把下一块数据读进同一组寄存器——就必须等 `STS` 先读完。读登记号就管这件事：`STS` 读完源寄存器时，对应计数器减一，后面要覆盖这个寄存器的指令等它归零。

这个细节在 §5.2 会用到：线程自己搬的时候，同一组寄存器反复充当中转站，每一轮都要经过"读取写进来 → STS 读出去 → 下一次读取再写进来"，两种等待交替出现。

### 4.4 走查：一个逐元素 kernel 的真实机器码

把上面的机制放进一个最小的真实例子：`y[i] = a * x[i] + b`。

```cpp
__global__ void axpb(const float* __restrict__ x, float* y, float a, float b, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + b;
}
```

用 CUDA 12.8 的 ptxas 编到 sm_90（Hopper），`cuobjdump -sass` 反汇编，再按逆向研究的布局把每条指令的控制位解出来（解码的可信度旁证：每条要用某个结果的指令，等待掩码里正好点着那个结果登记的号）：

| # | 指令 | 在干什么 | 控制位 |
| --- | --- | --- | --- |
| 1～4 | `LDC` / `S2R` / `S2UR` / `LDC` | 取栈指针、线程号、块号、`blockDim.x` | 写登记 1，各有停顿 |
| 5 | `IMAD R7, R7, UR4, R0` | 算下标 `i` | 等待 {1} |
| 6～8 | `ULDC` / `ISETP.GE` / `@P0 EXIT` | 取 `n`、判越界、越界线程退出 | |
| 9～12 | `LDC.64` × 3、`ULDC.64` | 取 `x`、`y` 的基址和 `a`、`b` | 写登记 0、1、2 |
| 13 | `IMAD.WIDE R2, R7, 0x4, R2` | **算读取地址** `x + 4i` | 等待 {0} |
| 14 | `LDG.E.CONSTANT R2, desc[UR4][R2.64]` | **读 `x[i]` 进 R2** | **写登记 2** |
| 15 | `IMAD.WIDE R4, R7, 0x4, R4` | **算写回地址** `y + 4i` | 等待 {1} |
| 16 | `FFMA R7, R2, R8, R9` | **唯一的计算** `a·x[i] + b` | **等待 {2}** |
| 17 | `STG.E desc[UR4][R4.64], R7` | 写回 `y[i]` | 不登记 |
| 18 | `EXIT` | 结束 | |

按控制位里的停顿计数，把"这个 warp 独占调度器"时的发射时刻推出来：

| 拍 | 事件 |
| --- | --- |
| 0～63 | 发射第 1～13 条：确认身份、算下标、判越界、取参数、算读取地址 |
| **64** | **发射 `LDG`，2 号计数器 0 → 1** |
| 65 | 发射第 15 条（算写回地址）——它等的是 1 号，照常发 |
| 69 | 轮到 `FFMA`，查 2 号：是 1。**这个 warp 落选** |
| 70～543 | 这个 warp 一条指令也发不出，调度器去发别的 warp |
| 544 | 数据写进 R2，2 号 1 → 0，这个 warp 重新可选 |
| 545～551 | 发射 `FFMA`、`STG`、`EXIT` |

![一个 warp 执行 y = a·x + b 的逐拍时间线：第 64 拍发出读取，第 69 到 544 拍挂起，第 545 拍才能计算](./figures/14-01-warp-wait-timeline.svg)

> **图 1-6**　一句话：这个 warp 一生 551 拍，其中 475 拍在等一笔显存读取；真正在算数的只有第 545 拍那一条乘加。
>
> **先知道一件事**：图里的"屏障 2"就是正文说的 2 号计数器。读取发出时加一，数据写回寄存器时减一，要用数据的指令等它归零。
>
> **按这个顺序看**：
> 1. 横轴是拍数。左边 0～64 拍和右边 544 拍之后画得宽，中间那段被压扁了，否则整张图只剩一条长线。
> 2. 第一行是这个 warp 发射了哪些指令：左边一串蓝点在算下标、算地址、判越界；红点是第 64 拍的 `LDG`；右边绿点是数据回来后才发得出的 `FFMA`。
> 3. 第二行是 2 号计数器：第 64 拍从 0 变 1，一直保持到第 544 拍数据写回才变回 0。
> 4. 第三行是这个 warp 的状态：红色那段就是挂起，横跨 475 拍。
> 5. 第四行：这段时间调度器去发别的 warp 的指令。驻留的 warp 够多，执行单元才不空转。
>
> **看懂的标志**：能回答"这个 kernel 想快，该从哪下手"——那 475 拍本身缩不短，只能让这段时间里有别的 warp 在干活，或者让每条读取多搬一些数据，用更少的指令凑够同时在路上的数据量。
>
> **与正文的对照**：发射时刻按控制位里的停顿计数、在"本 warp 独占调度器"的假设下推出；480 拍取的是 H800 实测的显存延迟。
>
> 来源：本库自绘。

从这个走查里读出三件事：

1. **18 条指令只有 1 条在算数。** 其余在确认身份、取参数、算地址、访存。地址那两条 `IMAD.WIDE` 每个线程各算一遍，是"地址从哪来"这个问题在机器码里的样子。
2. **编译器把无关的指令塞进了等待的缝里。** 第 15 条算写回地址，和读到的数无关，被排在 `LDG` 之后、`FFMA` 之前，它的执行时间叠进了等待里。
3. **第 9～12 条里取 `a`、`b` 的那条常量读取也登记在 2 号上。** 所以 `FFMA` 实际在等两笔都回来；常量读取几十拍就回来，最后压住它的仍是显存那一笔。

### 4.5 等待靠谁填：其它 warp

单个 warp 等待时什么也做不了，填空只能靠同一个 SM 上的其它 warp。一个 SM 最多驻留 64 个 warp；每个线程用的寄存器越多，能驻留的 warp 越少——65 536 个寄存器 ÷ 每线程 64 个 ÷ 32 = 32 个 warp，每线程 128 个就只剩 16 个。

对逐元素这种每个线程只用十几个寄存器的 kernel，这套办法很好用：驻留几十个 warp，每个手上挂一两笔读取，延迟就藏住了。问题出在下一部分的 kernel 上。

## 5. 这个办法哪里疼

### 5.1 四笔账

用 §1 的矩阵乘例子：128 个线程，每推进一次 K 要搬 A、B 两个分块共 32 KB。H100 上算这一步要 128 × 128 × 64 ÷ 2048 = **512 拍**。把"线程自己搬"的成本按三个问题加上传输，拆成四笔：

| 这笔账 | 线程自己搬的情况 | 花的是谁的资源 |
| --- | --- | --- |
| **① 发起** | 128 个线程全员参与。32 KB ÷ 16 字节 = 2048 次线程级读取，每个线程 16 条 `LDG` + 16 条 `STS`；按 warp 计 128 次发射 | 线程、发射机会 |
| **② 地址** | 每个线程用整数指令自己算，每次读取前一两条；地址结果占几个寄存器 | 发射机会、寄存器 |
| **③ 传输** | 32 KB，延迟 480～730 拍，带宽由 HBM 和 L2 决定 | 存储系统（不占 SM） |
| **④ 完成通知** | 记分牌：数据写进寄存器才算完成，所以在路上的数据必须先占好寄存器——每个线程每一级 32 KB ÷ 128 线程 = 256 字节 = **64 个寄存器** | 寄存器 |

先排除一个容易高估的项：发射机会。①②两项合计约 250 次 warp 级发射（128 次读写，加上每次读取前一两条地址计算），而 512 拍里一个 SM 的 4 个调度器一共有 2048 个发射机会——搬运只占约 12%，不是瓶颈。真正疼的是 ④，其次是 ① 里的"全员参与"。

### 5.2 最疼的一笔：完成挂在寄存器上

**问题的形状。** 要把 480～730 拍藏起来，算第 k 块的时候，后面几块就得已经在路上。设"提前 d 级"——算第 k 块时，第 k+1 到 k+d 块已经发出读取。要盖住一次往返，需要 d × 每块计算时间 ≥ 往返延迟。

**线程自己搬时，在路上的数据只能停在寄存器里。** 记分牌只认"目的寄存器被写入"，所以每一笔在路上的读取都得事先指定一个目的寄存器，并且在数据回来、被 `STS` 写走之前一直占着它。每多提前一级，就多占一份：本例是每线程 64 个寄存器。

**算一下放得下几级。** 128 × 128 的 fp32 累加结果要一直留在寄存器里，128 个线程每人 128 个。每线程上限 255 个：

> 128（累加器）+ 64（提前一级）= 192，放得下
> 128 + 64 × 2 = 256，超过 255，放不下第二级

（改成 256 个线程能把每人的份额摊薄，多放一两级，但这些寄存器仍出自同一个 256 KB 的寄存器堆，和累加器、和能驻留的 warp 数抢同一份预算。）而这些寄存器只是中转站：数据最终要去的是 shared memory，在寄存器里停的这几百拍，它们什么计算也不参与。

Ampere 之前，CUTLASS 的矩阵乘主循环正是这个形状——下一块先读进寄存器，算完当前块再写进 shared memory，shared memory 开两份轮换：

```cpp
regs = LDG(tile[1]);                 // 序幕：tile[0] 已经在 smem[0]，tile[1] 提前读进寄存器
for (k = 0; k < K_TILES; ++k) {
    compute(smem[k % 2]);            // 算当前块：H100 上约 512 拍
    STS(smem[(k + 1) % 2], regs);    // 把提前读的那块写进另一份 smem —— 记分牌在这里等 LDG 回来
    __syncthreads();
    regs = LDG(tile[k + 2]);         // 再提前读下一块，写进同一组寄存器 —— 读登记号保证 STS 已经读走
}
```

这里提前的级数 d = 1：`LDG` 在 `compute` 之前发出，必须在 `compute` 算完之前回来。

**为什么 Volta 上够用，后来不够。** 往返延迟这些年一直是几百拍，变的是每块的计算时间。同一个 128 × 128 × 64 分块，一个 SM 要算多少拍：

| 架构 | 每 SM 每拍乘加 | 算一块要多少拍 | 按 730 拍算要提前几级 |
| --- | --- | --- | --- |
| V100（2017） | 512 | 2048 | 1 级，绰绰有余 |
| A100（2020） | 1024 | 1024 | 1 级，余量很小 |
| H100（2022） | 2048 | 512 | 至少 2 级 |
| B200（2024） | 约 4096（按公开峰值估算） | 约 256 | 至少 3 级 |

（每 SM 每拍乘加 = 整卡 16 位矩阵峰值 ÷ SM 数 ÷ 时钟 ÷ 2：V100 为 125 TFLOPS ÷ 80 ÷ 1.53 GHz ÷ 2 ≈ 512，A100 为 312 ÷ 108 ÷ 1.41 ÷ 2 ≈ 1024。带宽吃紧时排队会让延迟更长，要的级数还要更多。）

![各代算一个 128×128×64 分块的拍数，与 480～730 拍的显存往返对比，以及需要提前的级数](./figures/14-01-prefetch-depth.svg)

> **图 1-7**　一句话：矩阵单元一代比一代快，算一块的时间从 2048 拍缩到约 256 拍，显存往返却一直是几百拍；于是要提前发起的级数从 1 级涨到 3 级以上，而线程自己搬时，寄存器只放得下 1 级。
>
> **先知道一件事**："提前 d 级"指算第 k 块时，第 k+1 到 k+d 块的读取已经发出。每一级在路上的数据都要有地方停；线程自己搬时，停的地方只能是寄存器。
>
> **按这个顺序看**：
> 1. 每一行是一代 GPU，蓝色横条是一个 SM 算完一个 128×128×64 分块要多少拍（假设这个 SM 只跑这一个分块）。
> 2. 红色竖带是一次显存往返，480～730 拍，各代大致不变。
> 3. 对比横条和竖带：V100 的横条远远越过竖带——算一块的时间里，下一块早就回来了，提前 1 级就够。A100 的横条刚过竖带，1 级勉强够。H100 和 B200 的横条落在竖带左边，1 级盖不住。
> 4. 右列是按 730 拍算出的最少级数：d × 每块拍数 ≥ 730。
> 5. 底部灰框里的红字：本例中一级就要每线程 64 个寄存器，加上 128 个累加器，只放得下一级。
>
> **看懂的标志**：能回答"记分牌按寄存器盯得这么准，为什么反而成了瓶颈"——问题不在准不准，而在它只能在数据落进寄存器时销账，在路上的数据于是都要预占寄存器；计算越快，要同时在路上的数据越多，寄存器装不下。
>
> **与正文的对照**：B200 的每拍乘加次数由公开的整卡峰值按 SM 数反推，是估算；730 拍是 H100 走对侧 L2 分区时的实测上限（§2.2）。
>
> 来源：本库自绘。

这就回答了一个容易想反的问题。记分牌盯的是单个寄存器，看上去是"最精细"的完成通知，后面几代的机制反而"粗"：Ampere 按"一组指令"等，Hopper 按"一共多少字节"等。精细与否不是要点。**要点是完成通知挂在什么东西上——挂在寄存器上，在路上的数据就只能停在寄存器里；挂在 shared memory 上，在路上的数据就能直接停在它最终要去的地方。** 下一节的 `cp.async` 就是这么改的。

### 5.3 带宽越涨越疼：Little 定律

§5.2 是从"藏住延迟"的角度看；从"吃满带宽"的角度看是同一件事。排队论里的 Little 定律说：一条管道里同时装着的货 = 进货速度 × 每件货在管道里待的时间。放到显存上：

> 同时在路上的字节数 = 带宽 × 往返延迟

H100 的显存带宽 3.35 TB/s，往返 480～730 拍约合 260～400 纳秒，相乘得 **0.9～1.3 MB**：任何时刻全芯片必须有这么多数据在路上，带宽才跑得满。摊到 132 个 SM，每个 SM 约 **7～10 KB**。B200 的带宽涨到 8 TB/s，若往返延迟同量级，每个 SM 要挂着的数据翻一倍多。

**HBM 一代代提高的是带宽，不是延迟**：它靠的是把总线做宽（每个堆叠 1024 位）、多放几个堆叠，同时开更多条路，而不是让每一笔走得更快。延迟不变、带宽翻倍，同时在路上的数据就得翻倍。线程自己搬时这些数据全都停在寄存器里，所以**带宽越高，寄存器这笔账越紧**。

### 5.4 另外两处疼

**数据绕道寄存器。** 数据从显存到 shared memory，中途在寄存器里停一下，所以每 16 字节要两条指令（`LDG` + `STS`），而且 `STS` 得等 `LDG` 回来——发 `STS` 的正是要做计算的那些 warp，它们会在这里被记分牌挡住。

**全员参与。** 128 个线程都要发读取、算地址、发写入，没有哪个 warp 能专心计算。想让一部分 warp 只管搬、另一部分只管算，在这个搬法里做不到：记分牌只让发出读取的那个 warp 自己等，别的 warp 看不见这笔账。

### 5.5 后面每一代改的是哪一处

把上面几处疼对回三个问题，就是本模块第一部分后面几节的顺序：

| 疼在哪 | 改的是哪个问题的答案 | 谁来改 | 章节 |
| --- | --- | --- | --- |
| 在路上的数据占寄存器；数据绕道寄存器 | 完成怎么知道：不再挂在寄存器上 | Ampere 的 `cp.async`：显存直达 shared memory | 02 |
| 全员参与；每个线程自己算地址 | 谁发起、地址从哪来：一个线程下单，引擎算地址；完成记在 shared memory 里谁都能看的计数器上 | Hopper 的 TMA 与 mbarrier | 03 |
| 矩阵单元的数据还要从 shared memory 再搬一跳 | 搬运引擎多管一跳 | Blackwell 的 TMEM 与 `tcgen05.cp` | 04 |

NPU 走的是另一条路（第二部分），跨出芯片的搬运另有一套机制（第三部分）。

需要说明的是，**线程自己搬不会被淘汰**。后面那些机制都假设数据是规整的块；按索引跳着读（gather）、查表、零散的小读取，只有线程自己算地址才表达得出来。今天的 Hopper 和 Blackwell kernel 里，几种搬法同时在用，各管一段。

## 7. 最新架构落点（知识截至 2026-09）

- **NVIDIA**：从 Volta 到 Blackwell，普通 `LDG` 的完成通知一直是记分牌，机制没有变；变的是旁边加了新的搬法（后面三节）。Blackwell 的矩阵单元每 SM 吞吐又约翻倍，§5.2 的那张表在它上面更陡。
- **AMD（CDNA，如 MI300）**：同样是计数器记账，但等待是**显式的一条指令**：`s_waitcnt vmcnt(N)` 表示"等到在路上的向量访存只剩 N 笔"。NVIDIA 把等待写在下一条指令的控制位里，AMD 单独插一条等待指令；两者都不按寄存器分格子，都是数在路上的笔数。
- **NPU（昇腾、TPU）**：计算单元根本不从显存取数，也没有"线程发读取"这回事，搬运从一开始就交给专门的搬运单元。第二部分讲。

## 9. 术语卡

### 记分牌（scoreboard，依赖屏障）
**定义**：GPU 跟踪"延迟不固定的指令什么时候出结果"的机制。Volta 起每个 warp 有 6 个计数器；访存指令发射时把编译器指定的那个计数器加一，数据写进目的寄存器时减一，要用这个数据的指令在控制位里声明等待那个计数器，调度器查到它不为零就不发这个 warp。
**为什么存在**：访存的延迟从 40 拍到 700 多拍不等，编译器无法在指令里写死"等几拍"，只能由硬件在运行时记账。没有它，要么每次都按最坏情况等，要么用错还没回来的数据。
**语境例句**："这个 kernel 一半时间卡在 long scoreboard 上。" —— 意思是：warp 大部分时间在等访存的计数器归零，读取的延迟没被其它 warp 的计算盖住。

### 停顿计数（stall count）
**定义**：编译器写在每条指令控制位里的一个小数字，表示"发完这条之后，这个 warp 隔几拍再发下一条"。用于延迟固定的指令，比如浮点乘加。
**为什么存在**：延迟固定的依赖在编译时就算得清，直接写成数字，硬件只要倒数，省掉了比较逻辑。延迟不固定的那一类才交给记分牌。
**语境例句**："这两条 FFMA 之间编译器塞了 4 拍停顿。" —— 意思是：后一条要用前一条的结果，乘加流水线要 4 拍才出数，所以编译器让这个 warp 隔 4 拍再发。

### 访存合并（coalescing）
**定义**：SM 的访存单元把一个 warp 里 32 个线程的地址归并成尽量少的 32 字节段请求。相邻线程读相邻地址时段数最少，地址散开时段数最多。
**为什么存在**：显存和缓存之间按段搬数据，32 个线程各发一个请求会把同一段搬好多次。合并让一个 warp 的一次读取只搬它真正覆盖的那几段。
**语境例句**："这里是按列读的，没合并上，一个请求要 32 个 sector。" —— 意思是：同一个 warp 的线程读的地址相隔一整行，每个线程落在不同的段里，一次读取搬了 32 段，大部分字节白搬。

### 在途字节与 Little 定律（bytes in flight）
**定义**：任一时刻已经发出、还没回来的读取所涉及的字节数。Little 定律给出跑满带宽所需的在途字节：带宽 × 往返延迟。H100 约为 0.9～1.3 MB，每个 SM 约 7～10 KB。
**为什么存在**：延迟是物理上的几百拍，带宽要跑满，就必须同时有足够多的读取在路上。这个数决定了需要多少 warp、每个 warp 挂几笔读取、以及在途数据停在哪里。
**语境例句**："带宽只跑到一半，在途字节不够。" —— 意思是：同时在路上的读取太少，管道没灌满；要么多挂几笔，要么每笔多搬一些。

### 寄存器预取（register prefetch）
**定义**：Ampere 之前矩阵乘主循环的标准写法：算当前块的同时，把下一块从显存读进寄存器；算完再把寄存器里的数据写进 shared memory 的另一份缓冲。CUTLASS 里叫两级流水（`MmaPipelined`）。
**为什么存在**：记分牌只能在数据写进寄存器时销账，提前发出的读取只能落进寄存器。这是在这个约束下能写出的最深流水——每多一级多占一整份寄存器，所以通常只提前一级。
**语境例句**："sm70 上只能走 pipelined，sm80 才有 multistage。" —— 意思是：Volta 上只能提前一级、在途数据停在寄存器里；Ampere 有了 `cp.async`，在途数据直接停在 shared memory，才能提前好几级。

## 10. 我的困惑 / 待深挖

- 6 个计数器和控制位布局来自对 Volta 的逆向研究，Hopper、Blackwell 上是否原样沿用，没有逐位核实。
- 缺失登记表（MSHR）的行数 NVIDIA 没有公开；它是"一个 SM 最多能挂多少笔读取"的硬上限，与 Little 定律算出的每 SM 7～10 KB 是否吻合，待找实测。
- B200 每 SM 每拍的矩阵乘加次数是按整卡峰值反推的估算，往返延迟也假设与 H100 同量级，待用 Blackwell 微基准（arXiv:2507.10789）核对。
- 负载下的显存延迟：§2.2 的数字都是空载实测，带宽吃紧时排队会拉长多少，影响 §5.2 表里的级数。
