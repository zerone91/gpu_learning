# 模块 14 · 数据搬运：load/store、异步拷贝与 DMA

模块 10～13 讲的是"算"的部件；这个模块讲"搬"的部件。计算单元只认寄存器或片上缓冲里的数，数据从显存、从主机、从别的卡过来，每一跳都要有人去搬。**谁来搬、地址从哪来、搬完了怎么通知用数的人**——这三个问题的不同答案，就是 load/store、cp.async、TMA、NPU 的 MTE、copy engine、RDMA 这些名字的全部区别。

> 📍 **这个模块是搬运机制的正式归宿。** 全库此前在多处讲过它的片段（10-01 §4.4 LSU、10-04 §3 与 §6 合并和 TMA、10-05 §4.5 mbarrier、10-08 §5.3 TMA 的汇编、11-04 §5 双缓冲与 MTE、13-04 §7 与 13-06 §5 的电路形态、50-01 §4～5 搬运指令矩阵、50-03 §3 主机侧 DMA）。那些地方保留简述并链接到这里；这里把机制讲完整，并把 GPU 与 NPU 两派放在一起对照。

## 划分框架：两根轴

第 01 节给出两根轴。

**第一根轴是发起者**，排成一条光谱：**从"每个线程亲自搬、每个地址自己算"，到"交给一个引擎、只下一张订单"**。越往右，计算单元越省事，但表达能力越受限、同步越要显式。光谱上的四类机制各占一节（02～05）。

**第二根轴是途中变换**：数据在搬运途中能不能顺手换个摆法（转置、swizzle、分形格式、im2col），这件事由哪一跳的哪个部件做。它和发起者正交，四类机制各有一部分能力，所以单独成一节（06）。第 07 节回到整体做对照与选型。

| 类别 | 谁发起 | 地址怎么来 | 完成怎么知道 | 典型半径 | 章节 |
| --- | --- | --- | --- | --- | --- |
| **load/store** | 每个线程 | 每个线程各算一个 | 记分牌：用到这个寄存器时自动等 | 寄存器 ↔ shared / L1 / L2 / 显存 | 02 |
| **异步拷贝** | 每个线程 | 每个线程各算一个 | 显式分组等待（commit / wait group） | 显存 → shared，绕过寄存器 | 03 |
| **描述符 DMA** | 一个线程下单，引擎执行 | 一张张量描述符 + 坐标 | 事务计数屏障（mbarrier）或流水线标志（flag） | 显存 ↔ shared / 片上缓冲，簇内多播 | 04 |
| **片外 DMA** | 主机、驱动或网卡 | 描述符 / 命令队列 | 事件、流顺序、完成队列 | 主机 ↔ 显存、卡 ↔ 卡、节点 ↔ 节点 | 05 |

| 途中变换发生在哪一跳 | GPU 上由谁做 | NPU（昇腾）上由谁做 | 章节 |
| --- | --- | --- | --- |
| 寄存器内 | 线程：`shfl`、`prmt`、`movmatrix` | 向量单元 | 06 |
| 片上缓冲 → 寄存器 / 计算缓冲 | `ldmatrix` / `stmatrix`（含 `.trans`） | MTE1：img2col、转置 | 06 |
| 显存 ↔ 片上缓冲 | TMA：swizzle、im2col、box 切块、越界填充 | MTE2：ND → NZ；FixPipe：NZ → ND 并带量化 | 06 |
| 片外 | copy engine：2D / 3D 带步长拷贝 | SDMA | 06 |

## 小节

- 🟨 [01 · 搬运的全景：谁发起、地址怎么来、完成怎么知道](./01-搬运的全景·谁发起、地址怎么来、完成怎么知道.md)
  - 为什么计算单元不能直接用显存里的数，必须先搬？一次搬运的代价由哪几部分组成（发起、地址生成、传输、通知）？
  - 三个问题怎么把六七个名字排成一条光谱？为什么硬件一代代往光谱右边走（Volta 只有 load/store → Ampere 加 cp.async → Hopper 加 TMA → Blackwell 加 tcgen05.cp）？
  - NPU 为什么从一开始就站在光谱最右边？这和模块 11 讲的"时序在设计期定死"是什么关系？
  - 走查：一个 GEMM 的 A 矩阵 tile，从显存到进入矩阵单元，在 GPU 和昇腾上分别经过哪几跳、每一跳用的是哪类机制。

- 🟨 [02 · load/store：线程亲自搬](./02-load-store·线程亲自搬.md)
  - 一条 `LDG` 从发射到数据回到寄存器，经过哪些部件（LSU、地址生成、合并、L1/tag、MSHR、L2、显存控制器）？每一段大约多少拍？
  - 合并（coalescing）按什么规则把 32 个地址并成几次 sector 请求？向量化访存（`LDG.128`）为什么能省发射槽？
  - 发出去以后线程怎么"等"：记分牌、依赖的寄存器、为什么靠别的 warp 掩盖延迟（接模块 10 第 2 节的 occupancy）。
  - 缓存提示（`.ca` / `.cg` / `.cs`、L2 驻留控制）改变的是什么。store 为什么通常不用等。
  - 局限：搬运数据要占寄存器、占发射槽、占线程——这就是往右走的动机。
  - 走查：一个逐元素 kernel 的 SASS，逐条看地址计算、访存和等待。

- 🟨 [03 · 异步拷贝：cp.async，绕过寄存器](./03-异步拷贝·cp.async绕过寄存器.md)
  - `cp.async`（SASS 里是 `LDGSTS`）比 load + store 两步省掉了什么？为什么"不经过寄存器"就能多开流水级？
  - commit group / wait group 的语义：为什么需要显式分组、等错了组会怎样。
  - 多级流水（multistage）怎么用它写出来：一个 3～4 级的 GEMM 主循环。越界填零（zfill）怎么处理边界 tile。
  - 局限：地址还是每个线程自己算，一次最多 16 字节——线程数和指令数没有真正减下来。
  - 走查：CUTLASS 或 Triton 在 Ampere 上生成的一个 pipelined GEMM 主循环。

- 🟨 [04 · 描述符 DMA：TMA 与 NPU 的 MTE](./04-描述符DMA·TMA与NPU的MTE.md)
  - TMA 的订单里写了什么：tensor map（基址、维度、步长、元素类型、box 大小、swizzle 模式、越界填充），以及每次只传的坐标。为什么描述符要在主机侧提前编好？
  - 引擎内部做了什么：地址生成、边界裁剪、swizzle、按 box 拆成请求；im2col 模式为卷积做了什么。
  - 完成通知：mbarrier 的"期望字节数"（expect_tx）机制，生产者—消费者两个屏障怎么轮转（接模块 10 第 5 节）。
  - 另外两种业务：簇内多播（一次读、多个 CTA 收）和归约写回（`cp.reduce.async.bulk`）。
  - NPU 一侧：昇腾的 MTE1/MTE2/MTE3 三条搬运流水各管哪一段，`set_flag` / `wait_flag` 如何在搬运流水和计算流水之间握手；TPU 的 DMA 与同步标志。和 TMA 比，相同的是什么、不同的是什么。
  - Blackwell 的新变化：TMA 的 gather 模式、`tcgen05.cp`（shared → TMEM）。
  - 走查：FlashAttention-3 的 producer warp 如何用 TMA + mbarrier 喂 consumer warpgroup（接模块 40 附录 B2）。

- 🟨 [05 · 片外 DMA：copy engine、P2P 与 RDMA](./05-片外DMA·copy-engine、P2P与RDMA.md)
  - copy engine 是什么、一张卡有几个、它和 SM 的关系（为什么说 GPU 里有两个"DMA 引擎"）。
  - `cudaMemcpyAsync` 从调用到完成的全过程：命令写进队列、引擎取命令、经 PCIe 或 NVLink 传输、事件完成。为什么源端必须是锁页内存（接模块 50 第 3 节）。
  - 卡间 P2P：copy engine 搬与 SM 直接 load/store 对端显存，两条路各适合什么。集合通信里 SM 搬与 copy engine 搬的取舍。
  - 网卡作为发起者：GPUDirect RDMA 的一次写走查，完成队列怎么通知；GPUDirect Storage 把盘也接进来。
  - NPU 与其它加速器的对应物（昇腾的 SDMA、TPU 的 ICI DMA）。
  - 走查：一次训练 step 里的 H2D 预取、梯度 all-reduce、checkpoint 写盘，各由谁搬、怎么和计算重叠。

- 🟨 [06 · 搬运途中的变形：硬件做的 layout 变换](./06-搬运途中的变形·硬件做的layout变换.md)
  - 为什么要在搬运途中变换，而不是搬完再单独变一趟？多一趟读写的代价怎么算。
  - 按跳逐级看：寄存器内（`shfl`、`prmt`、`movmatrix`）、shared → 寄存器（`ldmatrix` / `stmatrix` 与 `.trans`）、显存 → shared（TMA 的 swizzle、im2col、box、越界填充）、片外（copy engine 的带步长拷贝能做什么、不能做什么）。
  - NPU 一侧：昇腾 MTE2 的 ND → NZ 分形转换、MTE1 的 img2col 与转置、FixPipe 写出时的 NZ → ND 与量化。为什么 NPU 把变换放进搬运引擎，GPU 把相当一部分留给线程。
  - 硬件做不到的变换怎么办：多一趟 kernel、在寄存器里拼、改上游的摆法。
  - 走查：同一个卷积或 attention 的 tile，在 Hopper 和昇腾上每一次变换发生在哪一跳、由哪个部件完成。

- 🟨 [07 · 对照与选型：同一块数据的四种搬法](./07-对照与选型·同一块数据的四种搬法.md)
  - 同一个 GEMM tile 分别用 load/store、cp.async、TMA 搬进 shared，线程数、指令数、寄存器占用、可达带宽怎么变？
  - 选型判据：什么时候老老实实用 load/store（不规则访问、gather、小数据），什么时候上 TMA（规则的大块张量）；需要的变换能不能在搬运时顺手做掉，还是必须多一趟。
  - 开发者视角：在 PyTorch / Triton / CUDA C / SASS 各层分别怎么选中某种搬运方式，Nsight Compute 里看哪些指标判断"搬运是不是瓶颈、是哪一类搬运"。
  - 最新架构落点与术语卡。

## 和其它模块的接口

- **模块 10（SIMT 核）**：LSU、合并、记分牌、mbarrier 的基础在那里；本模块把它们串成完整的搬运机制。
- **模块 11（空间脉动架构）**：第 4 节的双缓冲是"搬运藏进计算"的原型；本模块第 04 节讲 NPU 上执行这件事的引擎。
- **模块 13（微架构与物理实现）**：第 04 节讲 TMA 与 mbarrier 的电路形态，第 06 节讲 NPU DMA 引擎的硬件；本模块讲它们对外的行为和用法。
- **模块 30（互连）**：搬运走的路。本模块讲发起方，模块 30 讲链路。
- **模块 40（软件优化栈）**：第 4 节的手排流水、附录 B2 与 B4 的代码精读，是本模块机制在代码里的样子。
- **模块 50（数据视角）**：第 1 节的搬运指令矩阵是全景地图，本模块是地图上每个格子的展开；第 2 节讲为什么要这样摆（布局是硬件约束的解），本模块第 06 节讲由谁、在哪一跳把数摆成那样。
